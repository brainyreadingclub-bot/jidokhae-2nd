### 1-3. "순서 #50 → #49 → #53" — 결과는 맞지만 **이유가 다르다**

GitHub의 `MERGEABLE`은 **각 PR을 base와 1:1로만** 본다. 셋을 차례로 넣었을 때 안 깨지는지는 보지 않는다. 그래서 직접 시뮬레이션했다(브랜치·ref를 만들지 않는 `merge-tree`):

```
$ git merge-tree --write-tree origin/main pr/50        → d42669d  (충돌 없음)
$ git merge-tree --write-tree <main+50> pr/49          → 45a823a  (Auto-merging kst.ts, notification.ts)
$ git merge-tree --write-tree <main+50+49> pr/53       → 0681b15  (Auto-merging notification.ts)
```

**세 개 다 순서대로 충돌 없이 들어간다.** 런북의 "상호 무충돌" 주장은 결과적으로 참이다.

다만 **순서를 강제하는 것은 코드 의존이 아니다.** #49가 쓰는 `PARTICIPATED_STATUSES`는 이미 `origin/main:jidokhae-web/src/lib/registration-status.ts`에 있고, #50은 그 파일을 **수정(M)**할 뿐이다. 즉 #50 없이 #49만 머지해도 빌드는 된다. 순서를 강제하는 진짜 이유는 아래 하나다.

### 5-3. env ↔ 머지 순서가 뒤집혀 있다

런북 §1-1은 *"PR #50 머지 확인 → env 6개 교체 + 재배포"*다. 그런데 같은 문서 47행이 이미 답을 적어놨다 — **"env는 빌드 시점 주입, 교체 후 재배포 필요."**

그렇다면:

| 순서 | 그 사이에 사는 조합 | 위험 |
|---|---|---|
| 런북대로 (머지 → env → 재배포) | **새 코드 + 구 템플릿 ID** — 재배포 완료까지 | REMIND·PROMOTED가 `#{결제상태}`를 보내는데 구 템플릿엔 그 변수가 없다 → 발송 실패 |
| **env 먼저 → 머지** | 없음. env를 바꿔도 **재배포 전까지 구 배포는 구 env로 계속 돈다** | 머지가 일으키는 빌드가 새 env를 집어가며 **코드와 ID가 동시에** 바뀐다 |

런북 29행의 경고 *"#50 없이 env만 바꾸면 리마인드·승격·환불 알림톡이 실패한다"* 는 **성립하지 않는다.** env만 바꾼 상태는 재배포 전까지 존재하지 않기 때문이다(47행과 자기모순). 실제로 위험한 것은 그 반대인 "코드만 먼저"다.

실질 노출도 따져보면: REMIND는 19:00 크론, REFUNDED는 18:30 크론이라 오전 작업이면 안 걸린다. 그러나 **REGISTRATION_CONFIRM은 이벤트**라 아무 때나 뜬다(최근 30일 49건 ≒ 하루 1.6건). CONFIRM_V2는 변수가 구 코드와 같아서 실패하진 않지만, 창을 아예 안 만드는 편이 낫다.

> **런북에 넣을 것** — §1의 1번을 **"env 6개 + 신규 2개를 먼저 Production에 넣는다 → 그다음 PR #50 → #49 → (#53 base 변경) → #53 머지. 머지가 일으키는 빌드가 새 env를 집어간다"** 로.

### 5-4. §2 점검에 **실발송 1건 확인**이 빠졌다

대조표 §배포순서 5번(*"배포 후 실제 발송 1건 확인 — `notifications` status가 `sent`인지"*)이 런북으로 옮겨오지 않았다. 이게 **변수 대조가 맞았는지 확인하는 유일한 실증 수단**이다. 화면 점검 7개는 전부 UI만 본다.

> **런북 §2에 넣을 것** — `🤖 notifications 최근 행 status 확인 — sent인가. failed면 error_message로 어느 변수가 막혔는지 본다`
> (조회 SQL: `select type, status, error_message, created_at from notifications order by created_at desc limit 10;`)

### 5-5. 롤백 §3의 "env는 되돌릴 필요 없음"에 조건이 빠졌다

플래그만 끄는 롤백이면 맞다. 그러나 **코드를 revert하는 롤백이면 틀린다** — 구 코드 + V2 env 조합이 되어 REMIND/PROMOTED가 다시 막힌다.

> **런북 §3에 넣을 것** — `코드(PR 3건)를 revert하는 경우에는 env 템플릿 ID도 V1으로 함께 되돌린다. 플래그만 끄는 롤백에는 해당 없음.`

### 5-6. 이건 결함이 **아니다** — 알림톡 착지 경로

알림톡 버튼은 `/my`(3종)와 `/meetings/#{모임ID}`(2종)로 간다(`검토문서/2026-08-11-알림톡-전체-시안.md` 56·80·109·130·205행). `next_ui`를 켜도 이 두 경로는 `(next)`로 리다이렉트되지 않아 **구 스킨 화면에 착지한다.**

지적하지 않는다 — **신규 UI 자신이 같은 곳으로 보낸다.** `(next)/me/page.tsx:73,85`가 `/my`로, `components/next/MeetView.tsx:9`에 *"상세·신청은 구경로(`/meetings/[id]`) 재사용 — 결제 로직 무변경(스펙 §6)"* 이라고 적혀 있다. **1단계의 의도된 범위**다. `/my`는 서재·물어보기 섹션도 그대로 렌더한다(`(main)/my/page.tsx:19–28`) → BOOK_ASK 착지도 동작한다.

### 5-7. 이미 알려진 것 (켜는 날 게이트 아님)

- **호칭 닉네임 통일**(DECISIONS 2026-08-07)은 머지 후에도 미적용 — 알림톡은 여전히 `real_name || nickname`(`notification.ts:161,206,253,287,323,357`). V2 문안이 이미 승인됐고 코드 한 줄 방향 뒤집기라, 켜고 난 뒤 별건으로 처리하면 된다
- **발송 실패 시 중복 방지 인덱스가 자리를 차지해 재시도 불가** — 검증 프로필에 인지된 문제. BOOK_ASK/WELCOME에도 같은 구조가 그대로 적용된다(둘 다 partial UNIQUE). 첫 발송이 변수 오류로 실패하면 **같은 대상에게 다시 못 보낸다** → §5-4의 실발송 확인이 더 중요해지는 이유
