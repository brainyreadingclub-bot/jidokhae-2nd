# 알림톡 6번째 템플릿(물어보기) 문안 — 심사 제출용

> 2026-08-02 | Spec | 작성: 총괄 | 결정 필요: 단무지님

## 왜 이 템플릿인가

물어보기(책 담기)의 **주 진입점**이다. 2026-07-16 전문가 패널 5명이 만장일치로 내린 결론 — 회원은 모임 사이에 앱을 잘 안 켜므로 인앱 UI는 응답률 천장이 구조적으로 낮고, 이미 돌아가는 카카오 알림톡이 유일한 실질 도달 수단이다. 인앱 스트립은 안전망일 뿐이다.

카카오 심사가 **외부 대기시간**이라 우리가 줄일 수 없다. 그래서 다른 작업보다 먼저 큐에 넣는다.

## 벤치마킹 (2026-08-03) — 전제가 틀렸다

초안은 "친근한 톤 = 광고성 분류 리스크"를 전제로 안내형을 권했다. **이 전제가 틀렸다.** 카카오 공식 심사 가이드와 실무 사례를 조사한 결과, 심사가 보는 축은 **말투가 아니라 내용**이다.

### 심사가 실제로 보는 것

카카오 공식 가이드의 정보성 인정 요령은 **"고객이 먼저 특정 액션을 완료하고 그에 대한 결과 또는 진행 과정"** 안내이며, **발송 근거를 본문에 명기**할 것을 요구한다. 반려 대상은 특가·할인, 동의 없는 쿠폰, **앱 설치 유도**, 개인정보 등록 요구, 변수만으로 구성된 메시지다. **말투에 대한 제약은 없다.**

실제로 널리 쓰이는 표준 리뷰 요청 템플릿은 직접 요청형이다:

> "안녕하세요. #{고객명} 님 주문하신 고객님의 소중한 상품이 배송완료 되었습니다. #{업체명}은/는 #{고객명} 님의 소중한 리뷰를 기다리고 있습니다. **만족하셨다면 리뷰를 남겨주세요.**"

"~해주세요"라는 직접 요청이 그대로 승인되어 통용된다. 우리 케이스(참여 완료 → 후속 기록 요청)는 이 리뷰 요청과 **구조가 동일**하고, 오히려 유리하다 — 적립금·쿠폰 같은 대가가 아예 없기 때문이다.

### 그래서 바뀐 결론

- **A안이 안전하고 B안이 위험하다는 구분은 근거가 없다.** 둘 다 혜택 언급이 없어 심사 관점에서 동등하다.
- 대신 **두 초안 모두 빠뜨린 것**이 있다 — ① 발송 근거 명기 ② 목적 명시. 공식 가이드가 요구하는 항목인데 A·B 어디에도 없었다. **이게 실제 반려 위험 요소였다.**
- 따라서 톤은 심사가 아니라 **회원 경험 기준으로** 고르면 된다.

> 한계: 트레바리·문토·넷플연가 등 동종 서비스의 실제 알림톡 원문은 공개돼 있지 않아 확보하지 못했다. 위 근거는 카카오 공식 심사 가이드와 커머스 리뷰 요청 템플릿 사례다.

## 최종안 (권장)

벤치마킹에서 확인한 필수 요소(발송 근거 + 목적 명시)를 넣고, 톤은 담백하게 두되 요청은 분명히 한다.

```
#{회원명}님, 지독해입니다.

#{모임일} 『#{모임명}』에 참여하신 분께 안내드립니다.

모임에서 읽으신 책을 회원님의 서재에 담아 두실 수 있습니다.
아래 버튼을 눌러 책을 담아주세요.

담아 두신 책은 마이페이지에서 다시 보실 수 있습니다.

▪ 이 안내는 모임당 한 번만 발송됩니다.
```

- **버튼 2개** (기존 5종과 동일한 구성)
  - `채널 추가` (AC)
  - `책 담기` (WL) → `https://brainy-club.com/my` (PC·모바일 동일)

**문장별 근거**

| 문장 | 왜 넣었나 |
|---|---|
| "참여하신 분께 안내드립니다" | **발송 근거 명기** — 공식 가이드 요구사항. 회원도 "왜 나한테 왔지?"를 즉시 안다 |
| "담아 두실 수 있습니다" | **목적 명시** — 이 메시지가 무엇을 위한 것인지 |
| "아래 버튼을 눌러 책을 담아주세요" | 표준 리뷰 요청 템플릿과 같은 직접 요청. 4050 비IT에게 "무엇을 하면 되는지"를 모호하게 남기지 않는다 |
| "마이페이지에서 다시 보실 수 있습니다" | 버튼을 놓쳐도 도달 경로가 있음. **앱 설치 유도로 읽히지 않도록 웹 경로 표현만 사용.** "언제든"은 쓰지 않는다 — 서재 섹션은 콜드스타트 B안상 조건부 렌더라 항상 보이지는 않는다(아래 §착지 지점) |
| "모임당 한 번만 발송됩니다" | 알림 피로에 민감한 서비스라는 정체성 표명. 절제가 정책임을 알린다 |

### 착지 지점 — `/meetings/{id}`가 아니라 `/my`

두 후보 화면의 실제 배치를 코드로 대조한 결과다.

| | `/meetings/{id}` | `/my` |
|---|---|---|
| 담기 스트립 위치 | **맨 마지막** (히어로·모임정보·참여자명단·액션버튼 다음) | **위쪽** (내 정보 바로 아래) |
| 서재("담으면 여기 쌓인다") | 없음 | 스트립 **바로 아래** |
| 지난 모임 표시 | 히어로가 `"8/5(수) 만나요"` — 이미 다녀온 모임에 미래형 | 해당 없음 |
| 대상 모임 특정 | 정확 (`isAskPendingForMeeting`) | 최근 미해소 1건 (`getPendingAsk`) |

`/meetings/{id}`는 모바일에서 **스크롤해야 담기 버튼이 나온다.** "아래 버튼을 눌러 담아주세요"라고 해놓고 도착하면 안 보인다. `/my`는 스트립과 서재가 붙어 있어 콜드스타트 B안이 설계로 명시한 배치 그대로다.

대상 모임 특정이 느슨해지는 건 실질 손실이 없다 — 알림톡이 **모임 다음날** 나가므로 그 시점의 "최근 미해소 1건"은 사실상 항상 그 모임이다.

부수 효과로 `#{모임ID}` 변수가 불필요해지고, `/my` 링크는 기존 4개 템플릿에서 이미 승인받은 경로다.

### 대안 — 더 친근한 톤 (2026-08-06 개정)

심사 관점에서 아래도 동등하다. 첫 문장만 바꾸고 나머지 구조(근거·목적·요청·절제 고지)는 유지한다.

```
#{회원명}님, #{모임일} 『#{모임명}』에서 함께 읽어주셔서 고맙습니다.

모임에 참여하신 분께 안내드립니다.
그날 읽은 책을 회원님의 서재에 담아 두실 수 있습니다.
아래 버튼을 눌러 책을 담아주세요.

담아 두신 책은 마이페이지에서 다시 보실 수 있습니다.

▪ 이 안내는 모임당 한 번만 발송됩니다.
```

> **개정 사유** — 원래 대안의 첫 문장은 `『#{모임명}』 어떠셨어요?`였다. `VOICE.md` §3 레드라인 **"알림톡 첫 문장 의문형 금지"** 위반이다(4050 회원이 발신전용 채널에 답장을 쓰고 "씹혔다"로 기억한다). 친근함은 유지하되 의문형만 평서형 감사로 교체했다. 심사 리스크는 여전히 최종안과 동등하다.

**총괄 판단**: 최종안을 권한다. 다만 이제는 "심사 때문"이 아니라, 계좌이체 입금 확인 알림까지 일부러 끄고 있는 이 서비스의 목소리와 일관되기 때문이다. 친근한 쪽을 고르셔도 심사 리스크는 같다.

## (참고) 초안 단계의 A·B안 — 폐기

아래는 벤치마킹 전에 작성한 것으로, **발송 근거·목적 명시가 빠져 있어 그대로 제출하면 안 된다.** 판단 이력 보존용.

### A안 — 안내형 (초안, 폐기)

```
#{회원명}님, 지독해입니다.

#{모임일} 『#{모임명}』에서 읽으신 책을 서재에 기록하실 수 있습니다.

기록해두시면 올해 읽은 책이 한 곳에 모입니다.

▪ 마이페이지 > 내 서재에서도 기록하실 수 있습니다.
```

- **버튼 1개(웹링크)**: `서재에 담기` → `https://brainy-club.com/meetings/#{모임ID}`

~~권하는 이유: 심사 통과 확률 / 알림 정책 일관성 / 4050 눈높이~~ → **첫 번째 근거(심사 통과 확률)가 벤치마킹으로 반증됨.** 말투는 심사 분류와 무관하다. 나머지 두 근거는 유효하나 그것만으로는 A안을 택할 이유가 못 된다.

### B안 — 친근형 (초안, 폐기)

```
#{회원명}님, 어제 『#{모임명}』 어떠셨어요?

함께 읽은 그 책, 서재에 담아두시면 올해 읽은 책이 한 권씩 쌓입니다.

▪ 마이페이지 > 내 서재에서도 담으실 수 있습니다.
```

- 버튼 동일
- ~~열람률은 이쪽이 높을 수 있으나 광고성 분류 리스크를 감수한다.~~ → **리스크 차이 없음이 확인됨.**

### 두 안 공통 — 의도적으로 뺀 것

- **투표·책 선정 언급 없음.** 패널 경고 — 참여자 전원에게 매번 보내면 "책 선정 냄새"가 나고, 개인 기록 프레임과 충돌한다.
- **재촉 표현 없음.** 미응답 재발송이 없으므로 "지금 바로", "마감" 같은 표현을 쓸 이유가 없다.
- **권수·순위 언급 없음.** 서재가 비어 있는 회원에게 압박이 된다.

## 발송 조건 (문안과 함께 심사에 설명될 내용)

| 항목 | 값 | 근거 |
|---|---|---|
| 발송 시점 | 모임 **다음날 오전 10시**(KST) 크론 | 기존 리마인드 19:00 / 대기 환불 18:30과 겹치지 않음 |
| 대상 | 그 모임 **참여자**(`confirmed` + `pending_transfer`) | `PARTICIPATED_STATUSES` — 계좌이체 미입금자 누락 사고(PR #44) 재발 방지 |
| 제외 | 이미 `answered` 또는 `dismissed` | `book_asks` 상태 |
| 횟수 | **모임당 1회, 재발송 없음** | 패널 경고 — 반복 발송은 채널 차단·피로 유발 |
| 중복 차단 | `notifications` 부분 UNIQUE INDEX | 기존 5종과 동일 패턴(INSERT pending → 발송 → UPDATE) |
| 모임 종류 | **정기모임만** | `isAskEligibleMeeting` 자격 판정 재사용 |

## 변수

| 변수 | 예시 | 출처 |
|---|---|---|
| `#{회원명}` | 초록고래 | `profiles.real_name \|\| nickname` (기존 5종과 동일) |
| `#{모임일}` | 8월 12일 | `formatKoreanDate(meeting.date)` — ⚠️ 기존 5종은 전부 `#{모임일시}`(날짜+시간)다. 6번째는 시간이 무의미해 **의도적으로 다른 신규 변수**를 쓴다 |
| `#{모임명}` | 8월 정기모임 | `meetings.title` |

버튼이 `/my` 고정이라 `#{모임ID}`는 필요 없다.

## 구현 시 필요한 것 (심사 승인 후)

- `SOLAPI_TEMPLATE_BOOK_ASK` env 추가 (Vercel Production + Preview 양쪽)
- `notifications.type` CHECK에 `'book_ask'` 추가 + 부분 UNIQUE INDEX `(recipient_id, meeting_id) WHERE type = 'book_ask'`
- `GET /api/cron/book-ask` + `vercel.json` 크론 등록 (UTC `0 1 * * *` = KST 10:00)
- `sendBookAskNotification()` — `notification.ts` 기존 래퍼 패턴 그대로
- 재사용: `getPendingAsk` / `isAskEligibleMeeting`(`asks.ts`), `PARTICIPATED_STATUSES`(`registration-status.ts`)

> DB 마이그레이션 SQL은 프로젝트 규칙에 따라 **코드 확정 후** 전달한다(코드보다 먼저 실행되면 불일치 발생).

### 선행 조건 — 딥링크 복귀 (PR #48)

버튼 링크는 로그인이 필요한 `(main)` 라우트다. 미들웨어가 원래 목적지를 버리고 있어서, 카카오톡 인앱 브라우저처럼 세션이 없는 환경에서는 회원이 홈에 떨어진다. **PR #48이 머지·검증되기 전에는 이 템플릿을 발송해도 새어나간다.**

버튼명도 `서재에 담기` → **`책 담기`** 로 바꿨다. 회원이 카톡에서 누른 버튼과 **도착 화면(`AskStrip`)의 버튼이 같은 이름**이어야 같은 기능으로 읽힌다. 남은 불일치는 `LibrarySection`의 `+ 책 검색해서 담기` 하나인데, 이건 인앱 코드 수정 건이라 별도 작업(`VOICE.md` 🟡 항목)으로 둔다. **심사 제출을 막지 않는다.**

### 기존 템플릿 실물 대조 후 추가 정정 (2026-08-06)

Solapi API로 승인된 템플릿 23건의 본문·버튼을 직접 열어 대조했다. 두 건을 정정한다.

**① `www.` 도입 제안 철회.** 앞서 "canonical이 `www.brainy-club.com`이니 apex는 리다이렉트 한 홉이 붙는다"고 지적했으나, **기존 5종이 전부 apex(`https://brainy-club.com/...`)로 이미 승인·운영 중**이다. 심사는 통과한다. 운영 중인 패턴을 신규 건 때문에 흔들 이유가 없다 — **apex 유지**한다. (리다이렉트 한 홉은 실재하지만, 그건 도메인 설정 차원에서 따로 볼 일이다.)

**② 버튼이 1개가 아니라 2개여야 한다.** 기존 템플릿의 표준 구성은 `채널 추가`(AC) + 웹링크(WL) 2개다. 6번째만 1개면 튄다. 같은 구성을 따른다.

부수 확인 — `#{모임ID}`를 링크에 넣는 방식은 `MEETING_REMIND`·`WAITLIST_PROMOTED`에 선례가 있어 안전하다. 다만 착지 지점을 `/my`로 바꾸면서 이 변수는 쓰지 않게 됐다.
