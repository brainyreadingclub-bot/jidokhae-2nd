### 2-3. 🟩 "정기모임 1회 이상"을 세는 쿼리 — RPC는 필요 없다

**결론: SECURITY DEFINER RPC 불필요.** 이유가 셋이다.

| 지점 | 클라이언트 | RLS를 타나 |
|---|---|---|
| `payment.ts:36` | `createServiceClient()` | ❌ 우회 |
| `transfer/route.ts:51` | `createServiceClient()` | ❌ 우회 |
| `MeetingDetailContent.tsx:21` | `createClient()` (anon + 세션) | ✅ 탄다 — 그런데 **통과한다** |

세 번째가 관건인데, RLS가 이미 열려 있다:

```
supabase/migration.sql:118-120
  CREATE POLICY "registrations_select_own"
    ON public.registrations FOR SELECT
    USING (auth.uid() = user_id);

supabase/migration.sql:101-103

```

자격 판정은 **본인 이력만** 세면 되므로 `registrations_select_own`으로 충분하고, 조인 대상 `meetings`는 전체 공개다. `get_meeting_participant_nicknames` RPC가 필요했던 이유는 **남의 행(다른 신청자 닉네임)**을 읽어야 했기 때문이다 — A-2는 그 상황이 아니다.

**만들 필요가 없는 또 하나의 이유 — 같은 쿼리가 이미 있다.** `lib/asks.ts:28-32`가 물어보기 자격을 그렇게 센다:

```
asks.ts:28-32
  .from('registrations')
  .select('meeting_id, user_id, meetings(date, meeting_type, status)')
  .eq('user_id', userId)
  .in('status', PARTICIPATED_STATUSES)
```

판정은 순수 함수로 분리돼 있고(`asks-pure.ts:17-26` — 정기 + active + 과거 + 윈도우), 상수는 `registration-status.ts:18` `PARTICIPATED_STATUSES = ['confirmed','pending_transfer']` 하나다.

> 🔴 **`PARTICIPATED_STATUSES`를 반드시 재사용할 것.** 그 파일 `:13-16`에 사고 기록이 붙어 있다 — 리마인드 크론이 `confirmed`만 세서 `pending_transfer` 회원이 알림톡을 못 받았다(2026-07-30, 당시 27명). 자격 판정에서 같은 실수를 하면 **계좌이체로 참여해 온 회원이 통째로 자격을 잃는다.**

**차이 하나 — 윈도우.** `asks-pure.ts:5`는 60일 윈도우(`ASK_WINDOW_DAYS`)를 쓰는데, A-2 자격은 **평생 기준**이다(2026-08-14 결정). 이 차이를 어떻게 다룰지는 §2-5에 따로 적었다.

### 2-4. 🟩 삭제된 모임의 과거 참여 — 셀 수 없고, **셀 것도 없다**

**(a) 구조:** 모임 삭제는 소프트 삭제다(`meetings.status='deleted'`, 행 유지). 그런데 삭제 시 신청 행의 status가 바뀐다:

**(d) 🟩 `meeting_type` NULL 행 — prod 실측 0건** (관리자가 넘긴 한 줄 쿼리, 2026-08-22)

[토론자격 판정규칙 §1-3](2026-08-22-토론자격-판정규칙.md)이 마이그레이션 파일(`supabase/migration-meeting-type.sql:28,35` — `NOT NULL DEFAULT 'regular'` + CHECK)만 보고 *"해당 데이터 없음"*으로 판정했고, **제약이 prod에 실제로 붙었는지는 그 부서가 확인할 수 없었다.** 읽기 조회로 확인했다.

| 확인한 것 | 값 |
|---|---|
| `meeting_type IS NULL` | **0건** |
| `meeting_type` 값 분포 (전 43건) | **`regular` 43 — 그것뿐** |

**→ §1-3의 판정이 성립한다. 자격 판정에 `meeting_type` null 분기를 만들지 않는다.** `refund.ts:120`의 `string | null | undefined`는 함수 시그니처 방어일 뿐 데이터 상태가 아니라는 설명도 실측과 일치한다.

🟨 **한 가지는 여전히 못 봤다** — NULL 행이 0이라는 것과 `NOT NULL` 제약이 실제로 붙어 있다는 것은 다른 명제다. 지금 데이터가 깨끗한 것은 확인했고, **앞으로 NULL이 들어올 수 있는지**는 확인 못 했다(제약 조회에는 임의 SQL이 필요한데 이 세션에 그 도구가 없다). 다만 화이트리스트(`= 'regular'`)를 쓰면 **NULL이 들어와도 자격에 잘못 잡히지 않으므로** A-2 판단은 어느 쪽이든 안전하다.

**조회 방법(재현):** 프로젝트 루트(`jidokhae-web/`)에 임시 ESM 스크립트를 두고 `node`로 SELECT만 실행한 뒤 삭제했다. `scripts/` 아래 기존 스크립트는 실행하지 않았다(부작용 위험 — 공통규약 §6). Supabase MCP 도구는 이 세션에 **주어지지 않았고**, `supabase` CLI는 토큰이 없어 `LegacyPlatformAuthRequiredError`로 막혔다. **쓰기는 한 건도 하지 않았다.**

### 2-5. `isAskEligibleMeeting`과 모양이 같은 함정 — **재사용하지 않고, 테스트로 굳힌다**

[토론자격 판정규칙 §1-1](2026-08-22-토론자격-판정규칙.md)이 짚은 함정이다: 자격 판정이 `isAskEligibleMeeting`(`lib/asks-pure.ts:17-26`)과 **모양이 거의 같은데 윈도우(60일)만 없다.** 나란히 두면 다음 사람이 재사용하다 윈도우를 딸려 보낸다. 관리자가 처리 방식을 개발 판단으로 넘겼다.

**판단: 재사용하지 않는다. 독립 함수로 두고, 회귀 테스트로 못 박는다.** 주석만으로 끝내지 않는다.

**(1) 왜 재사용하지 않나 — 우연히 닮은 것이지 같은 규칙이 아니다.** 두 판정은 이유가 다르다:

| | `isAskEligibleMeeting` | 토론 자격 |
|---|---|---|
| 왜 정기·과거만 보나 | 물어보기는 **모임 다음날 책을 묻는 기능**이라 지난 정기모임이 대상 | 자격은 **"정기에 와 봤는가"**를 묻는다 |
| 왜 윈도우가 있나/없나 | `asks-pure.ts:4` — *"과거 소급 스팸 방지"* (물어보기만의 이유) | 없음. 평생 기준 (2026-08-14 결정) |
| 바뀌는 계기 | 물어보기 전환율·스팸 민원 | 토론모임 정책 |

**한쪽이 바뀌어야 할 이유가 다른 쪽에는 없다.** 합쳐두면 물어보기 윈도우를 30일로 줄이는 작업이 **토론 자격을 조용히 좁힌다.** 지금 통합하면 아끼는 것은 네댓 줄이고, 잃는 것은 그 연결이 안 보인다는 점이다.

**(2) 공유하는 것은 상수 하나뿐** — `PARTICIPATED_STATUSES`(`lib/registration-status.ts:18`). 이건 반대로 **반드시 공유해야 한다.** 그 파일 `:13-16`에 사고 기록이 있다(리마인드 크론이 `confirmed`만 세서 `pending_transfer` 회원 27명이 알림톡을 못 받음). 여기서 별도 배열을 새로 쓰면 같은 사고가 자격 판정에서 재현된다.

**(3) 🔴 실수를 테스트로 굳힌다 — 이게 주석보다 강하다.** A-2 PR에 회귀 테스트 한 개를 넣는다:

> *"60일보다 오래된 정기모임 참여도 자격을 준다"* — 예: 1년 전 정기모임 `confirmed` 1건만 가진 회원이 자격 통과.

누가 나중에 `isAskEligibleMeeting`을 재사용하거나 윈도우를 딸려 보내면 **이 테스트가 즉시 깨진다.** 주석은 지워지지만 테스트는 CI가 지킨다. 이 저장소는 이미 같은 방식을 쓴 적이 있다(`16121af` — *"실전에서 나온 것을 전부 시험으로 굳힌다"*).

**(4) 이름은 모양이 아니라 이유로 짓는다.** `isDiscussionEligibleMeeting` 같은 이름은 `isAskEligibleMeeting` 옆에 두면 **둘이 같은 가족처럼 보여** 재사용을 부른다. *"정기모임에 실제로 다녀왔는가"*를 그대로 말하는 이름을 쓴다(예: `countsAsRegularAttendance`). 위치는 `lib/asks-pure.ts`가 아니라 토론 소관 파일(`lib/discussion-rules.ts` 또는 새 파일).

> ⚠️ 최종 함수명·파일명은 구현 시점에 정한다. 여기서 정하는 것은 **원칙 셋**이다 — 재사용 금지 · 상수만 공유 · 회귀 테스트 필수.

### 게이트 2 — 정확히 무엇이 없는가

### 게이트 4 — 왜 순서가 뒤집혀야 하는가

런북 §1 1행(`:30`):

> **PR #50 머지 확인** → 알림톡 템플릿 env 6개를 V2로 교체 + 재배포

**"머지 → env 교체 → 재배포"** 순서다. Vercel은 머지 즉시 자동 배포하므로 이 순서에서는 **「새 코드 + 구 템플릿 ID」로 도는 창**이 생긴다. 그 창의 길이는 사람이 env를 갈아 끼우는 시간(수 분)이고, 그 사이 발생하는 신청·취소·승격은 알림톡이 실패한다.

반대로 **env를 먼저 갈면 창이 0이다** — 🟨 Vercel에서 env만 바꾸는 것은 재배포를 유발하지 않으므로, 구 코드는 **빌드 시점에 주입된 구 env**로 계속 돈다. 그다음 머지하면 새 코드와 새 env가 **한 번의 빌드에서 동시에** 들어간다.

> **권고 순서: (1) `migration-welcome-notification.sql` prod 실행 → (2) env 6+1개 교체(재배포 안 함) → (3) #50 → #49 → #53 머지(자동 배포가 새 env를 집어감) → (4) 플래그 flip.**
>
> ⚠️ 런북 `:30`의 경고문 *"#50 없이 env만 바꾸면 리마인드·승격·환불 알림톡이 실패한다"*는 **틀린 말은 아니지만 전제가 하나 빠졌다** — "env만 바꾸고 **재배포하면**"이다. 재배포하지 않으면 env 교체는 무해하다. 이 한 단어 때문에 순서가 위험한 쪽으로 굳었을 가능성이 있다.
> 🟨 이 마지막 판단은 Vercel 동작에 대한 것으로, **이 세션에서 Vercel 콘솔·CLI로 확인하지 않았다.** 외부 SaaS 동작 단언 금지 원칙(교훈 `feedback_external_saas_ui_no_assert`)에 따라 추정으로 표시한다.

> **교훈 한 줄: 스택 PR을 형제 브랜치로 재면 충돌이 없는데도 나온다.** 세 파일이 하필 *두 PR이 공통으로 건드리는 파일 전부*와 일치한 것이 그 신호였다.
>
> 🟨 문서총괄이 실제로 어떤 명령을 썼는지는 확인하지 못했다(그 세션 기록을 볼 수 없다). 위는 **같은 증상을 재현하는 조건을 찾은 것**이지, 그 부서가 그 명령을 썼다는 증거는 아니다. 다만 **충돌 파일 목록이 정확히 일치**하므로 원인은 이 계열로 본다.
>
> 부수적으로 확인한 것 둘 — `merge-tree`에 **트리 OID를 넘기면** `expected commit type` 오류로 죽고, **부모 없는 커밋**을 넘기면 `refusing to merge unrelated histories`로 죽는다. 둘 다 이번 증상과는 다른 모양이다.

## 4-c. 🟨 쓰기 가드 오탐 2건 — **재현되지 않았다. 원인은 가드가 아니다**

관리자 세션에서 읽기 전용 Bash 두 개가 막혔다고 했다. 내 세션에서 **같은 명령을 그대로 돌렸더니 둘 다 통과했다.**

| 관리자가 막혔다는 명령 | 내 세션 |
|---|---|
| `git show origin/main:jidokhae-web/src/lib/notification.ts \| grep -c "real_name"` | 🟩 **통과** — `7` 출력 |
| `sed -n '19p' "검토문서/DECISIONS.md"` | 🟩 **통과** — 해당 줄 출력 |

**가드 소스를 읽어보니 이 둘을 막을 토큰이 없다** (`.claude/hooks/manager-write-guard.mjs`):

| 검사 | 내용 | 두 명령이 걸리나 |
|---|---|---|
| `BASH_WRITE_TOKENS` (`:66-71`) | `tee` · **`sed -i`** · `mv ` · `cp ` · `rm ` · `truncate` · `dd ` · **`git checkout/restore/reset/clean/rm/mv/apply/stash/revert/cherry-pick`** | ❌ `sed -n`은 `sed -i`가 아니고, `git show`는 목록에 없다 |
| `REDIRECT_TO_FILE` (`:64`) | 파일로 나가는 `>`·`>>`만. `2>&1`과 `=>`는 이미 제외돼 있다 | ❌ 두 명령 다 리다이렉션이 없다 |
| `INTERPRETERS` (`:81-88`) | 쓰기 힌트가 **함께** 보일 때만 | ❌ 해당 없음 |

**→ 진단: 이건 쓰기 가드 오탐이 아니라 권한 허용목록 미스일 가능성이 높다.** `.claude/settings.local.json`을 보면 `deny`·`ask` 규칙이 **하나도 없고** `allow`만 194건인데, 그 안에 **`git show`도 `sed`도 없다**(`grep`은 24건 있으나 전부 다른 명령에 딸린 형태). 허용목록에 없는 명령은 세션 권한 모드에 따라 막힌다 — **그건 훅이 아니라 권한 시스템이고, 세션마다 다르게 동작한다.** 내 세션에서 통과한 것도 그 설명과 맞는다.

> **권고: 가드를 고치지 않는다.** `16121af`가 잡은 오탐 3건과는 성격이 다르다 — 그때는 가드 정규식이 실제로 잘못 물었고(`=>`를 리다이렉션으로 읽음), 이번엔 **가드가 물 수 있는 토큰 자체가 없다.** 잘못된 원인에 손대면 가드가 느슨해지기만 한다.
>
> 대신 값싼 조치 하나 — `.claude/settings.local.json` allow에 `Bash(git show:*)`와 `Bash(sed -n:*)`를 넣으면 같은 막힘이 안 난다. `.claude/**`는 관리자 소관이라 **내가 고치지 않았다**(§6-8).
>
> 🟨 **한계**: 관리자 세션에서 실제로 무엇이 막았는지(훅 출력인지 권한 거부인지)는 그 세션 기록을 볼 수 없어 확인 못 했다. 위는 **가드 소스와 권한 설정에서 도출한 추론 + 내 세션 재현 실패**다.
