### §1-2. 왜 env가 머지보다 먼저인가 (2026-08-22 순서 정정)

**근거 — Vercel 공식 문서:**

> *"Changes to environment variables are not applied to previous deployments, they only apply to new deployments. **You must redeploy your project to update the value of any variables you change in the deployment.**"*
> — [Managing Environment Variables](https://vercel.com/docs/environment-variables/managing-environment-variables) (문서 갱신일 2026-04-27)

env를 저장해도 **새 배포가 뜨지 않고**, 돌고 있는 배포는 빌드 시점에 주입된 옛 값을 계속 쓴다. 그래서 **env 교체는 그 자체로 무해하다.** 머지가 일으키는 배포가 새 코드와 새 env를 동시에 집어간다 → **창이 0**.

반대 순서(머지 → env → 재배포)는 사람이 env를 갈아 끼우는 **수 분 동안 「새 코드 + 구 템플릿 ID」**로 돌고, 그 사이 발생한 신청·취소·승격의 알림톡이 실패한다.

> ⚠️ **왜 위험한 쪽으로 굳었나 — 한 단어가 빠져 있었다.** 이 표 1행에 원래 *"#50 없이 env만 바꾸면 리마인드·승격·환불 알림톡이 실패한다"*(2026-08-18 문서총괄 발견)라고 적혀 있었다. **틀린 말은 아니지만 전제가 빠졌다 — "env만 바꾸고 재배포하면"이다.** 재배포하지 않으면 아무 일도 안 일어난다. 그 한 단어가 없어서 *"env를 먼저 바꾸면 위험하다"*로 읽혔고, 순서가 반대로 굳었다.
>
> 그래서 표 1행에 🔴 **재배포 금지**를 명시했다. 위험한 것은 **env 교체가 아니라 그 뒤의 재배포**다.

**경위:** 개발·운영이 [코드지형 §4](2026-08-22-A2A3-코드지형.md)에서 순서 정정을 권고했으나 근거를 🟨 추정으로 달았다(Vercel 콘솔·CLI 미확인). 제품기획은 **추정 위에서 배포 순서를 뒤집지 않고** 관리자에게 올렸고, 관리자가 공식 문서로 확정해 이 절이 됐다.

### §1-3. 왜 `#49` → `#53` 순서가 제약인가 (2026-09-10 retarget 후 신설)

**2026-09-10에 `#53`의 base를 `feat/book-ask-cron` → `main`으로 옮겼다** — 루트 `CLAUDE.md`가 *"명령이 실행되기 전까지 닫힌 것이 아니다"*로 남겨둔 그 건이다(결정이 난 날과 리모트가 바뀐 날이 18일 벌어져 있었다). 그 직후 GitHub에서 `#53`의 변경 파일이 **11개로 늘었다** — `book-ask` 크론·마이그레이션 등 **`#49`의 파일이 함께 뜬다**(`gh pr view 53 --json files` 실측).

**버그가 아니다.** `#53`의 브랜치가 `#49`의 브랜치 **위에 얹혀 있어서**, 비교 대상을 `main`으로 바꾸면 그 아래 깔린 `#49`의 커밋까지 "새로 추가되는 것"으로 보인다. **`#49`를 먼저 머지하면 `#53`은 다시 환영 알림톡 파일만 남는다.**

🔴 **그래서 순서를 어기면 retarget으로 얻으려던 것을 그대로 잃는다.** `#53`을 `#49`보다 먼저 머지하면 환영 알림톡과 물어보기 크론이 **한 머지 커밋에 묶여** 들어간다. 그러면 §3 롤백에서 *환영 알림톡 하나가 문제인데 물어보기 크론까지 같이 내려가는* 상황이 된다 — [코드지형 §4](2026-08-22-A2A3-코드지형.md)가 경로 B를 기각한 이유와 정확히 같다.

### §1-4. 플래그 SQL 원문 — 켜는 것과 끄는 것

> 🔴 **여기에 원문을 박아두는 이유는 롤백이다.** 끄는 SQL은 **급할 때 쓰는 물건**이라, 그 자리에서 바로 복사돼야 한다. 찾아서 조립하게 두면 사고 시간이 는다([코드준비 판정 §5-1](2026-08-21-켜는날-코드준비-판정.md)).
> ⚠️ **prod DB 쓰기다 — 대표님 승인 후에 실행한다**([DECISIONS](DECISIONS.md) 2026-08-22). admin 설정 화면에는 이 세 키의 필드가 **없다**(`SiteSettingsForm`에는 `notice_text`만 있다). 그래서 SQL이다.

**켜기 (§1 표 4행)** — 세 키 모두 **행이 없어 `INSERT`다.** `ON CONFLICT`를 붙여 두 번 돌려도 안전하게 만든다.

```sql
-- 켜는 날: next_ui · library_enabled = on
insert into site_settings (key, value) values
  ('next_ui', 'on'),
  ('library_enabled', 'on')
on conflict (key) do update set value = excluded.value, updated_at = now();

-- discussion_meeting_enabled: 값과 무관하게 행은 만든다 (사고 시 UPDATE 한 줄로 끝나야 한다)
-- 첫 토론모임 준비가 끝났으면 'on', 아직이면 'off'.  A-2·A-3 PR 미머지면 이 문장을 건너뛴다
insert into site_settings (key, value) values ('discussion_meeting_enabled', 'off')
on conflict (key) do update set value = excluded.value, updated_at = now();

-- 확인
select key, value from site_settings
where key in ('next_ui', 'library_enabled', 'discussion_meeting_enabled');
```

**끄기 (§3 롤백)** — 행이 이미 있으므로 `UPDATE`다. **범위가 좁은 것부터** 끈다(§3 표).

```sql
-- 토론모임에서만 증상이 날 때
update site_settings set value = 'off', updated_at = now() where key = 'discussion_meeting_enabled';

-- 5탭 전반
update site_settings set value = 'off', updated_at = now() where key = 'next_ui';
update site_settings set value = 'off', updated_at = now() where key = 'library_enabled';   -- 필요할 때만
```

🔴 **재배포하지 않는다. `getSiteSettings()`는 요청 단위 React `cache()`만 쓰므로 다음 요청부터 즉시 반영된다**(지속 캐시 없음).

## 3. 롤백 기준·절차

**기준 (하나라도 발생 시 일단 끄고 본다):**
- "화면이 안 열려요/이상해요" 문의 **2건 이상** (새로고침 안내로 해소 안 될 때)
- 신청·결제 실패 신고 **1건** (돈 관련은 즉시)
- 5xx 에러 지속 발생

**절차 — 🔴 범위가 좁은 것부터 끈다.** 증상이 토론모임에서만 나는데 개편 전체를 되돌리지 않는다.

| 증상 범위 | 끌 것 |
|---|---|
| **토론모임에서만** 발생 | 🤖 `discussion_meeting_enabled='off'` ← A-2·A-3 PR 머지 후 생기는 선택지 |
| 5탭 전반 | 🤖 `next_ui='off'` (+ 필요 시 `library_enabled='off'`) |

**수 초 내 복귀, 재배포 불필요.** DB(발제·서재 데이터)는 그대로 남으므로 원인 수정 후 재개 가능.

> 🔴 **env 템플릿을 되돌릴지는 「무엇으로 롤백했나」에 달렸다 — 조건 없이 "되돌릴 필요 없다"고 읽지 말 것.**
>
> | 롤백 방식 | env 템플릿 ID |
> |---|---|
> | **플래그 flip** (위 표 — `next_ui`·`library_enabled`·`discussion_meeting_enabled` `off`) | **그대로 둔다.** 코드가 `main`에 남아 V2 변수를 계속 보내므로 V2 ID가 맞다 |
> | 🔴 **코드 `git revert`** (#50·#49·#53 중 하나라도 되돌릴 때) | **env도 V1으로 함께 되돌린다.** 구 코드는 V2가 요구하는 변수(`#{결제상태}`·`#{모임일시}` 등)를 **안 보낸다** → 치환 오류로 **발송이 통째로 막힌다**. 되돌린 뒤 재배포까지 끝난 다음에 env를 갈아 끼운다(§1-2의 순서 논리가 역방향으로 똑같이 적용된다) |
>
> 원래 이 자리는 *"env 템플릿은 되돌릴 필요 없음(V2도 승인 문구)"* 한 줄이었다. **승인 여부는 맞지만 변수 정합을 안 본 문장이다** — [코드준비 판정 §5-5](2026-08-21-켜는날-코드준비-판정.md)가 지적한 그 건이고([전체목록 C3](../docs/agent-team/2026-09-19-켜기전-전체목록.md)), 변수 목록은 [변수 대조표](2026-08-13-알림톡-변수-대조표-및-배포-순서.md)에 있다.

> 🔴 **토론 플래그를 끌 때 돈은 자동으로 움직이지 않는다.** 화면을 내린 것이지 모임을 취소한 것이 아니다. 이미 결제한 회원의 **조회·취소·환불은 플래그와 무관하게 계속 살아 있다** — 끈 상태에서 취소가 막히면 환불 경로 자체가 사라진다. 진행 중인 토론모임이 있으면 🙋 운영자가 참여자에게 카톡 채널로 상황을 알린다. 모임 자체를 취소해야 하면 기존 **모임 삭제(100% 환불)** 경로를 쓴다. 상세: [자격·플래그 규칙 §2-2](2026-08-22-토론자격-판정규칙.md)

### ~~4-1. 예고 스트립 — 2단으로 나눠 10일간 게시~~ 🚫 **취소됨 (2026-09-23)**

|---|---|

**왜 「이번 주 일요일」이 아니라 「이번 일요일」인가** (디자인 판정). 한국어 달력은 일요일이 주의 **첫날**이라, 금요일(10/9)에 「이번 주 일요일」을 읽으면 **지나간 10/4**로도 읽힌다. 「이번 일요일」은 다가오는 쪽으로만 읽힌다.

**렌더 실측 — 1단·2단 둘 다 320px 최협폭에서 한 줄이다.** 2단은 디자인 실측(`strip-2dan-320.png`), 1단은 **2026-09-11 관리자 실측** — `NoticeStrip`을 재현한 정적 렌더를 `320px 컨테이너 + (main)/page.tsx의 px-5` 조건으로 돌려 나란히 쟀고, **두 문구 모두 텍스트 영역 201px · 1줄**이었다(`Math.round(height / lineHeight)`, Pretendard 로드 확인). 🔴 **기각한 초안(「이번 주 일요일」)도 360px에서 한 줄로 들어갔다**(`strip-2dan-rejected-360.png`) — **길이가 아니라 뜻 때문에 기각했다.** 길이를 근거로 이 결정을 다시 열지 말 것.

> 🔴 **이 문서로 문구를 다시 재는 사람에게 — 좁은 폭 렌더 검증은 컨테이너가 실제로 그 폭인지 먼저 측정한다. 눈으로 본 줄 수보다 `getBoundingClientRect()` 값이 먼저다.**
> 위 관리자 실측도 **첫 시도에서 「둘 다 두 줄」이 나왔고, 하마터면 「디자인 검증이 틀렸다」고 결론 낼 뻔했다.** 원인은 문구가 아니라 재현 하네스였다 — 컨테이너에 `width:320px`만 주고 flex 부모에 넣었더니 `flex-shrink` 기본값 때문에 **실제 폭이 262px로 찌그러져 있었다**(텍스트 영역 143px). `flex:0 0 320px`로 고정하고 다시 재니 201px·한 줄이었다.


- 🔴 **`👉 brainy-club.com`을 일부러 뺐다.** 예고 시점에 누르면 **아직 옛 화면**이 나온다 — 예고해놓고 아무것도 안 바뀐 화면을 보여주는 꼴이다. **켠 날 카톡(§4-2)에는 그대로 둔다.**
- **`똑똑!`을 안 붙였다.** 확정된 §4-2가 `똑똑!` 없이 `[지독해]`로 열기 때문 — 같은 주에 나가는 두 메시지의 형식이 다르면 두 사람이 보내는 것처럼 읽힌다.

### 4-2. 카톡 채널 공지 (켜는 날) 🙋
> [지독해] 화면이 새로워졌어요 🌿
>
> 오늘부터 지독해가 5개 탭으로 단장했어요.
> · 홈 — 지금 나에게 필요한 것만
> · 이야기 — 토론모임 이야기를 나누는 곳이에요
> · 서재 — 모임에서 읽은 책이 쌓여요
>
> 접속했을 때 화면이 이상하게 보이면, 앱을 완전히 닫았다가 다시 열어주세요.
> 👉 brainy-club.com

> 🔴 **「이야기」 줄을 2026-09-11에 고쳤다 — 확정 사안 변경이다.** 원문은 *"· 이야기 — 토론모임 발제문에 미리 생각을 남겨요"*였다.
> **왜 — 첫날 토론모임을 못 연다.** 자격 판정(A-2)과 `discussion_meeting_enabled`(A-3) 코드가 **둘 다 0건**이다(DECISIONS 2026-08-22 두 행). 그 상태로 이 문장을 보내면 회원이 카톡을 읽고 이야기 탭을 눌러 **빈 화면**을 본다 — 없는 것을 약속하는 문장이었다. 약속을 낮춰 **탭의 성격만** 말하게 했다.
> **경위** — 디자인이 §4-3을 고치다 확정 사안인 §4-2에도 같은 결함이 있음을 발견했고, **확정 사안이라 손대지 않고 보고했다.** 변경은 관리자 결정(2026-09-11).

### 4-3. 알림함 첫 공지 (admin → 공지 보내기) 🙋
- 제목: `화면이 새로워졌어요`
- 내용: `모임 신청은 '모임' 탭, 내 신청 내역은 '나' 탭에 있어요. 신청·취소 방법은 전과 같아요`
- 이동할 화면: **`/meet`**

- **왜 `/talk`이 아니라 `/meet`인가.** 첫날 토론모임이 없으면 `/talk`은 「다음 토론모임을 준비하고 있어요」 빈 상태다(`TalkView.tsx:205`) — 크래시는 아니지만 **눌러서 아무것도 없는 화면**이다. `/meet`는 정기모임 행이 있어 비지 않고, 본문이 §4-4 문의 3종 중 2건(「뭐가 바뀐 거예요」·「내 신청 내역이 안 보여요」)을 **미리 답한다.**
- ✅ **전제 충족 — `/meet`가 비지 않는다.** 10월 정기모임 **4건 등록됨**(10/07 · 10/14 · 10/21 · 10/28, 2026-10-07 확인 → §0 해당 행). ⚠️ **당일 아침에 한 번 더 본다** — 이 공지가 보내는 `/meet`에 **켜는 날(10/11) 이후의 모임**이 남아 있어야 한다. 10/07·10/14가 등록돼 있으므로 통과하지만, 세는 것은 "10월 몇 건"이 아니라 **"오늘 이후 active 모임이 있는가"**다.
- 길이 실측(2026-09-11): 제목 **10자** / 내용 **52자** — `AnnouncementForm.tsx:56,70`의 `maxLength` **60 / 120** 안에 들어간다.

### 4-4. 문의 대응 답변 3종

> 보관: 문의가 오는 곳이 카톡이므로 **카카오 채널 관리자센터에 저장**해두고 복사해 쓰는 것을 권장 (자주 쓰는 답변 기능이 있으면 거기에). 원문은 이 런북이 원본.
- **"화면이 이상해요/옛날 화면이에요"** → `앱을 완전히 종료했다가 다시 열어보시겠어요? 홈 화면에 설치한 앱은 이전 화면이 잠깐 남아 있을 수 있어요.`
- **"뭐가 바뀐 거예요?"** → `홈이 5개 탭으로 나뉘었어요. 모임 신청은 '모임' 탭, 토론책 이야기는 '이야기' 탭에서 하실 수 있어요. 신청·취소 방법은 전과 같아요.`
- **"내 신청 내역이 안 보여요"** → `'나' 탭 → 신청 내역에서 보실 수 있어요. 이전과 같은 내용이 그대로 있어요.`
