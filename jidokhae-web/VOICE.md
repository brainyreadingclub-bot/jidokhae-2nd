# VOICE.md — 지독해 보이스 & 톤

> 2026-08-03 제정 | 근거: `docs/expert-panel/2026-08-03-voice-tone-behavioral.md`
> `DESIGN_TOKENS.md`와 같은 층위의 규범 문서. 카피를 쓰기 전에 읽는다.

지독해는 경주·포항의 250명 오프라인 독서모임이다. 회원 다수가 4050 비IT다.
**우리는 재촉하지 않는다. 대신 한 번에 하나만, 무엇을 하면 되는지 끝까지 말한다.**

## 0. 레드라인 (최우선 — 다른 모든 규칙에 우선)

> **거절 경로는 응답 경로보다 항상 같거나 더 쉬워야 하며, `dismissed`는 영구 존중된다(재노출·재발송 금지).**
> **이 두 줄을 깨는 어떤 전환율 개선도 채택하지 않는다.**

북극성 지표가 `answered ÷ exposed`이고 분모에 `dismissed`가 들어간다(`asks-pure.ts`). 즉 **닫기 버튼을 없애면 숫자가 오른다.** 이 구조적 유혹은 카피 규칙으로 막을 수 없어 최상단에 못박는다.

| # | 금지 | 왜 |
|---|---|---|
| L1 | 거절 경로를 어렵게 만들기 — 닫기 버튼 축소·저대비·숨김, "정말 안 담으시겠어요?" 재질문 | 위 구조적 유혹의 직접 발현 |
| L2 | `dismissed` 회원 재노출·재발송 | 한 번의 거절이 존중되지 않으면 넛지가 아니라 압박 |
| L3 | 타 회원 행동의 집계·비교 — "N명이 이미 담았어요", 명단·순위·랭킹 | 안면 커뮤니티에서 사회적 증거 = 동조 압력. `shouldMaskConfirmedCount` 정책과 자기모순 |
| L4 | 운영자 1인칭 요청 — "제가 궁금해요", 운영자 실명·개인 이미지 | 아는 사이의 부탁은 거절 비용이 비대칭. 발신 주체는 항상 **"지독해"** |
| L5 | 결핍·죄책감·손실 프레이밍 — "서재가 비어 있어요", "지금 안 담으면 사라져요", 스트릭 카운터 | 서재가 빈 회원(대개 신규·저참여)에게 정확히 역방향 |
| L6 | 무료 기능 응답을 유료 권리와 연결 — 책 선정 투표권·우선 신청·할인 시사 | 자발적 기록이 서비스 접근권의 대가가 되는 순간 자율성이 사라진다 |
| L7 | 긴급성·마감 표현 — "오늘까지", "지금 바로", 카운트다운 | 재발송 없는 기능에 시한을 만들 이유가 없다 |
| L8 | 물어보기 알림톡 증편 — 모임당 1회 상한, 예외 없음 | "입금 확인 알림 금지"로 세운 알림 정체성과 일관 |

**허용선(명시)**: 발송 타이밍 최적화, 마찰 제거, 개인 편익 프레이밍, 발송 근거·목적 명기, 대체 경로 안내, 절제의 자기공시("모임당 한 번만 발송됩니다"). **친근함 자체는 조작이 아니다.**

## 1. 판정 규칙 8개

형용사는 가이드가 아니다. grep으로 위반을 잡을 수 있는 것만 규칙으로 둔다.

| # | 규칙 | 판정 |
|---|---|---|
| R1 | **인앱 평서문 종결은 `~어요/~해요`.** `~습니다`는 `app/policy/*`(법정 고지)와 알림톡에서만 | `grep "습니다" src/components` → 0 |
| R2 | **상태 라벨은 `STATUS_LABEL` 상수 단일 소스.** 띄어쓰기까지 고정 | 라벨 하드코딩 = 위반 |
| R3 | **호칭은 `닉네임 + 님` 한 종류.** 인앱·알림톡 동일 | `real_name \|\| nickname` 폴백 = 위반 |
| R4 | **요청형은 `~해주세요` 붙여쓰기** | `grep "해 주세요"` → 0 |
| R5 | **이모지 0, 느낌표 0.** 허용 기호는 `✓`(완료 상태 한정). 텍스트 화살표 `→ › ▸ —` 금지 → 인라인 SVG | 정규식 |
| R6 | **1문장 40자 이하, 한 블록 2문장 이하.** 한글 텍스트는 `break-keep` | 길이 카운트 |
| R7 | **에러 = `[동사]하지 못했어요 + 다시 시도해주세요`.** 사과어·원인 설명 금지 | 형태 일치 |
| R8 | **빈 상태 = 사실 1문장 + 다음 행동 1개.** `~없습니다` 금지, `아직 ~이 없어요` 형 | `grep "없습니다"` → 0 |

> R1·R4·R5·R8은 문서가 아니라 **빌드가 판정**하게 한다 — `prelaunch`에 grep lint 추가 예정.

## 2. "친근함 한 스푼"의 정량화

형용사로는 재현되지 않는다. **예산 + 좌표 + 닫힌 사전** 셋으로 고정한다.

### 예산
**한 화면당 친근한 문장 1개까지.** 2개면 초과다.

### 좌표 — 이게 핵심

**붙는 자리 3곳만**
1. 이름 부르는 인사 1회
2. 완료 토스트
3. 빈 상태의 격려 1문장 / 회원이 실수했을 때의 허가 문구

**절대 안 붙는 자리**: 금액·환불·입금·오류·법적 고지

> **판정 질문 한 줄 — "이 문장에 돈, 시간, 실패가 나오는가? 나오면 친근함 금지."**

친근함은 **회원이 실수했을 때**와 **이미 끝난 일을 알릴 때** 자산이고, **돈과 상태를 확정하는 순간**에는 부채다. 현재 코드에서 가장 잘 쓴 문구가 이 원리를 증명한다 — `BookSearchInput`의 "책 제목 일부만 넣어도 돼요"는 친근한 어미가 **"틀려도 된다"는 허가**를 주기 때문에 작동한다. (다만 이 문구는 `text-[11px] text-neutral-400`이라 정작 노안 연령대에 안 보인다 → **친근한 안내는 최소 13px, 본문 색**.)

### 닫힌 사전
새 표현을 매번 창작하지 않는다. 여기 없는 표현은 **이 문서에 먼저 추가한 뒤** 사용한다.

- **허용**: `만나요`, `함께 읽어요`, `쌓여요`, `담았어요`, `읽으셨어요?`(인앱 한정), `~해도 돼요`, `반가워요`
- **금지**: `앗`, `헉`, `~용`, 물결표, 느낌표, 이모지, 신조어

## 3. 채널 차이 — 명사·동사는 같고, 어미는 다르다

| | 알림톡 | 인앱 |
|---|---|---|
| 종결 | `~습니다` | `~어요` |
| 발송 근거·목적 문장 | **필수** (심사 요건 + 단발 설계) | 불필요 (문맥이 이미 있음) |
| CTA | **정확히 1개** | 1개 권장 |
| 첫 문장 | **의문형 금지** ⚠️ | 의문형 허용 |

### ⚠️ 알림톡 첫 문장을 의문형으로 쓰지 않는다

4050 비IT 회원은 **카톡에 온 질문에 답장을 쓴다.** 발신전용 채널이라 그 답장은 아무도 읽지 않고, 회원은 "말 걸어놓고 씹혔다"로 기억한다. 친근함을 넣고 싶다면 의문형이 아닌 다른 자리에 넣는다.

### 명사·동사는 채널이 갈려도 하나

같은 행동을 **담다** 하나로 부른다. `기록하다`와 병용 금지.
`서재에 담기` / `책 담기` / `+ 책 검색해서 담기`처럼 갈라지면 4050에게는 **서로 다른 기능**으로 읽힌다.

## 4. 상태 → 라벨 고정표

같은 상태를 화면마다 다르게 부르는 것이 이 서비스 카피의 가장 큰 결함이다. `STATUS_LABEL` 상수와 1:1로 유지한다.

| 상태 | 라벨 | 비고 |
|---|---|---|
| `confirmed` | **신청 완료** | 띄어쓰기 포함 고정 |
| `pending_transfer` | **입금 확인 중** | ⚠️ 아래 참조 |
| `waitlisted` | **대기 중** | |
| `cancelled` | **취소됨** | |
| 모임 종료 | **지난 모임** | |

### ⚠️ `pending_transfer` — 돈이 걸린 최우선 결함

현재 회원은 같은 상태를 화면마다 다른 이름으로 만난다 — 모임 상세에서 **"신청 접수됨"**, 마이페이지에서 **"입금 대기"**, 뱃지에서 **"입금대기"**. 세 가지 상태로 오해할 수 있다.

> ⚠️ **`pending_transfer`를 "미입금"으로 해석하지 말 것.** 운영자가 입금 확인을 **월말에 하루 몰아서** 처리하므로, 이 상태의 회원은 대부분 **이미 입금했고 확인 처리만 안 된 것**이다. 회원 입장에서도 사실상 신청 완료 상태이며, 앱 전반이 이를 `confirmed`와 동등 취급한다(`PARTICIPATED_STATUSES`). 문구가 회원을 "돈 안 낸 사람"으로 취급하면 안 된다.

**규칙**: 이후 화면은 전부 **`입금 확인 중`** 하나로 통일. 회원의 행동이 아니라 **운영자 처리 단계**를 가리키는 표현이어야 한다. "입금 대기"는 회원이 아직 안 냈다는 뉘앙스라 부정확하다.

### 내부 용어 금지
`승격` → **`자리 나면 확정`**. "승격"은 개발 용어다. 같은 사건을 위 문장에서 "확정", 아래에서 "승격"으로 부르면 회원은 두 개의 다른 일로 읽는다.

## 6. 행동과학 원칙 — 무엇에 베팅하고 무엇을 버리는가

**베팅하는 것 4개**

| 기제 | 적용처 |
|---|---|
| **이행 의도** — 언제·어디서·무엇을 들고 | 모임 전날 리마인드 (유일한 적용처) |
| **확정감** — 소유 상태의 불안 해소 | 신청 확인, 대기 승격 |
| **정체성·소속** — 개인 기록 프레임 | 전 메시지 발신 프레임, 물어보기 |
| **디폴트·마찰 제거** | 물어보기 (아래) |

**버리는 것**: 사회적 증거(L3), 희소성·카운트다운(L7), 사회적 비교(L3), 손실 프레이밍(L5)

> **긴급색은 상태를 알릴 뿐, 재촉 문장과 결합하지 않는다.** 정원 80% 도달 시 accent 코럴, D-3 이하 강조는 정보라 괜찮다. 여기에 재촉 문구가 붙는 순간 희소성 압박으로 승격된다.

**물어보기의 진짜 레버는 카피가 아니다**: 응답률을 지배하는 것은 동기가 아니라 **빈 검색창에 타이핑해야 하는 마찰**이다. 어떤 문구도 이걸 못 이긴다. 그 모임의 책을 후보로 미리 띄워 탭 1회로 담게 하는 편이 훨씬 큰 레버다(출처는 `meetings.reading_link` 같은 **운영자 지정 값**이어야 한다 — "다른 참여자가 담은 책"은 L3 위반).

## 7. 알림톡 6종 공통 규칙

재발송이 없다 = 각 메시지가 캠페인이 아니라 **자기완결적 단발 사건**이다.

1. **발송 근거를 본문에 명기** — "○○에 참여하신 분께 안내드립니다"
2. **목적 명시** — 이 메시지가 무엇을 위한 것인지
3. **CTA는 정확히 1개** — 두 번째 요청은 첫 번째의 전환율만 깎는다
4. **시간 압박 표현 금지** — "지금 바로"는 재발송 있는 시스템의 문법이다
5. **첫 문장 의문형 금지** (§3)
6. **앱 설치 유도로 읽힐 표현 금지** — 웹 경로 표현만 (카카오 심사 반려 사유)
