## 1. 이 영상의 핵심 주장 한 줄

> **디자인 시스템을 먼저 세우고, 그걸 AI가 읽게 해라.** 화면부터 그리게 하면 AI가 매번 다른 걸 만든다.

---

## 2. 하이서의 작업 순서 (그대로 따라 할 수 있는 형태)

```
① Figma에 「스타일 가이드」와 「컴포넌트」를 각각 섹션으로 묶어 준비
        ↓
② Figma Dev Mode 켜고 MCP 연결
        ↓
③ 스타일 가이드 섹션을 선택하고 →
   "지금 선택한 섹션 정보 전체를 읽어보고
    spacing · color · text style을 토큰으로 구성해 주세요"
        ↓
④ 컴포넌트 섹션을 선택하고 →
   "앞에서 구성한 변수를 토대로,
    지금 선택한 컴포넌트를 React 코드로 구현해 주세요"
        ↓
⑤ 결과 검토 → 수정
```

**③④를 나눠서 하는 게 핵심이다.** 토큰을 먼저 만들고 그걸 "토대로" 컴포넌트를 만들라고 해야 값이 하드코딩되지 않는다.

---

## 3. 영상에서 나온 실전 팁

| # | 팁 | 왜 |
|:--:|---|---|
| 1 | **섹션(Section)으로 묶어라** | 섹션 하나만 선택하면 그 안의 스타일 정보를 **한 번에** 읽어온다. 컴포넌트를 하나씩 클릭할 필요가 없다 |
| 2 | **Variables·스타일 토큰이 Figma에 먼저 정의돼 있어야 한다** | 없으면 MCP가 읽어올 게 없다 |
| 3 | **"프로퍼티를 반영해서 재사용 가능하게 구성해 달라"고 명시하라** | 컴포넌트에 variant/property를 걸어놨어도 **말 안 하면 AI가 빠뜨린다.** 사소한 프롬프팅 차이인데 결과가 갈린다 |
| 4 | **언어를 지정하라** ("React로") | 더 정확해진다 |
| 5 | **Plan(계획) 모드를 쓴다** | agent 모드로 두면 *"의도하지 않은 걸 계속 구현한다."* 계획을 먼저 보고 승인 |
| 6 | **레이어명·컴포넌트가 정리돼 있을수록 쉽다** | 엉망이면 고생하고 **LLM 토큰도 훨씬 많이 쓴다.** 본인도 MVP 때 이것 때문에 토큰을 많이 태웠다고 |
| 7 | **가끔 하드코딩해 버린다 → 검토 필수** | 결과물 자체는 *"거의 보이는 화면 그대로"* 나오지만 완전 자동은 아니다 |
| 8 | **Figma의 AI 레이어명 변경(Rename Layers)** | `Frame 3, 4, 5...`를 한꺼번에 정리. 규칙을 입력하는 수준은 아니지만 "아예 엉망인 것보단 낫다" |
| 9 | **MCP가 스크린샷을 같이 보여준다** | "네가 선택한 이 화면 맞아?" 하고 확인시켜 준다 (예전엔 없던 기능) |

### 왜 토큰화(디자인 시스템)를 먼저 하나 — 영상의 근거

- 하드코딩하면 나중에 바꿀 때 **하나하나 다 수정**해야 한다
- AI로 고쳐도 그 과정에서 **토큰(LLM 사용량)과 시간을 엄청나게 소모**한다
- 토큰화해두면 참조값만 바꾸면 되고, 컴포넌트를 가져다 쓰듯 재사용된다
- **MVP·기술검증 단계에선 생략해도 된다.** 다만 규모가 커지면 관리·소통 부채가 쌓인다

## 5. ⚠️ 영상과 현재 공식 문서가 다른 점 — 확인 필요

영상에서 진행자가 *"Dev Mode는 유료 사용자만 켤 수 있나요?"* 라고 묻자 **"네, Pro 이상부터 제공합니다"** 라고 답한다.

그런데 **2026-09-20 기준 Figma 공식 문서**(`help.figma.com` 「Guide to the Figma MCP server」)는 이렇게 적고 있다:

| 서버 종류 | 요구사항 |
|---|---|
| **Remote 서버** (권장) | **모든 시트·모든 플랜** — 무료 포함 |
| Desktop 서버 | 유료 플랜의 Dev 또는 Full 시트 |

**영상은 Desktop(Dev Mode 안에서 켜는) 방식 기준으로 말한 것**으로 보인다. 그 사이 Remote 서버가 나와 문턱이 내려갔다.
→ **우리는 Remote를 쓰면 되고, 유료 플랜이 아니어도 된다.**

영상에서 알려준 무료 우회법(플러그인으로 `Variables JSON` 추출)은 이제 굳이 필요 없을 가능성이 크다. 다만 **실제로 연결해 보기 전까지는 단정하지 않는다.**

## 6. 지독해에 적용하면 — 이 영상을 그대로 따라 하면 안 되는 지점

영상은 **Figma → 코드** 방향이다. **우리는 반대다.** 코드가 먼저 있고, 디자인 시스템도 이미 **코드 안에** 있다.

| 영상의 전제 | 우리 상황 |
|---|---|
| Figma에 디자인 시스템이 있고, 코드는 없다 | **코드에 디자인 시스템이 있다** — `globals.css`의 `@theme inline` + `DESIGN_TOKENS.md` |
| 처음부터 만든다 | **이미 돌아가는 서비스가 있다** (결제·환불 포함) |
| React 코드를 새로 뽑는다 | 뽑은 코드를 기존 Next.js 16 코드베이스에 **그대로 넣을 수 없다** |

### 그래서 우리에게 유효한 것만 골라내면

**✅ 가져올 것**

1. **"디자인 시스템 먼저"라는 원칙** — 우리는 이미 갖고 있다. 이걸 Figma Make의 `Guidelines.md`에 넣으면 영상이 말하는 효과를 그대로 얻는다
2. **③④를 나누는 프롬프트 패턴** — 토큰 먼저, 그다음 "그 토큰을 토대로" 화면. Make에서도 같은 순서가 통한다
3. **"프로퍼티 반영해서 재사용 가능하게"를 명시하는 습관** — 안 적으면 빠뜨린다
4. **Plan 모드 / 계획 먼저 보기** — Figma Make에도 `plan.md` 패턴이 있다(공식 문서 확인됨)
5. **레이어명 정리가 결과 품질을 좌우한다** — 나중에 Figma에 화면을 그릴 일이 생기면 이것부터

**❌ 그대로 따라 하면 안 되는 것**

1. **Figma에서 뽑은 React 코드를 우리 저장소에 붙이기** — 스택이 다르고, 우리 결제·환불 로직을 덮어쓸 위험
2. **Figma에 디자인 시스템을 새로 구축하기** — 이미 코드에 있는 것과 **두 벌이 된다.** 두 벌이 되면 어긋난다 (이 프로젝트가 반복해서 겪은 문제)

> 🔴 **우리가 조심할 것 하나 더.** 이 저장소의 `DESIGN_TOKENS.md`는 스킨이 **두 벌**(`(next)` 토스 스킨 / 구 잉크그린)이라고 명시한다. Figma든 Make든 새로 만드는 회원 화면은 **`(next)` 토스 스킨 기준**이다. 두 스킨을 섞으면 브랜드가 흔들려 보인다.

## 7. 덤 — 영상에서 소개된 도구 「스크린플로우(ScreenFlow)」

게스트가 만든 서비스. 우리한테 쓸모가 있을 수 있어 적어둔다.

- **하는 일:** 웹사이트 URL을 넣으면 **PC·태블릿·모바일 해상도별로 일괄 캡처**. 링크 트리(depth)를 따라 여러 페이지를 한 번에
- **Figma로 가져오기:** 전용 플러그인으로 **이미지 또는 HTML 원본 레이어**로 붙여넣기. 원본이라 수정 가능하고 팝업까지 읽어온다
- **쓸 데:** 레퍼런스 수집. *"이런 느낌"이라고 말로 하면 서로 다른 걸 상상하는데, 비주얼로 맞추면 정확하다*
- **상태(영상 시점):** 오픈베타 무료 · 3월 유료화 예정 · Cursor 등으로 바로 보내는 기능 준비 중

우리 쓸모 — **우리 사이트를 통째로 캡처해서 Figma에 올려두면**, 「지금 화면 vs 새 시안」을 나란히 놓고 비교할 수 있다. 지금은 대표님이 한 장씩 캡처해 주셔야 하는 일이다.
