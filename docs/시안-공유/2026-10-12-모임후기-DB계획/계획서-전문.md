## 2. ① 새 표·칸

### 2-1. `meeting_reviews` — 후기 (회원+모임당 1행)

| 칸 | 타입 | 제약 | 뜻 |
|---|---|---|---|
| `id` | uuid | PK, `gen_random_uuid()` | |
| `user_id` | uuid | NOT NULL, FK `profiles` ON DELETE CASCADE | 쓴 사람 |
| `meeting_id` | uuid | NOT NULL, FK `meetings` ON DELETE CASCADE | 그 모임 |
| `did_not_attend` | boolean | NOT NULL DEFAULT false | 「못 갔어요」 |
| `mood` | smallint | NULL 허용, `mood IS NULL OR mood BETWEEN 1 AND 5` | 표정 1(별로였어요)~5. **총괄운영자(admin)만** |
| `regret_codes` | text[] | NOT NULL DEFAULT `'{}'`, 8개 코드의 부분집합 | 아쉬운 점(여러 개). **총괄운영자(admin)만** |
| `regret_other` | text | NULL, 1~50자, `'other'`가 코드에 있을 때만 | 「기타」 짧은 글. **총괄운영자(admin)만** |
| `comment` | text | NULL, 1~100자 | 한 줄 소감(선택) |
| `comment_public` | boolean | NOT NULL DEFAULT **false**, 소감이 있을 때만 true | 공개 동의 |
| `comment_published_at` | timestamptz | NULL | 마지막으로 공개한 시각 (공개 소감 정렬 기준) |
| `comment_unpublished_at` | timestamptz | NULL | **회원이** 마지막으로 내린 시각 (요구: 내린 시각 기록) |
| `comment_hidden_at` | timestamptz | NULL | **운영자(admin)가 내린 시각.** 채워져 있으면 「운영자 내림」 상태 — **판정은 이 칸으로 한다** |
| `comment_hidden_by` | uuid | NULL, FK `profiles` ON DELETE SET NULL, `comment_hidden_at`이 있을 때만 | 내린 운영자. 기록용 |
| `created_at` / `updated_at` | timestamptz | NOT NULL DEFAULT now() | `updated_at`은 기존 `public.update_updated_at()` 트리거 재사용 |

**표 단위 제약**
- `UNIQUE (user_id, meeting_id)` — 회원+모임당 1건. 「다음」에서 바로 저장(시안 가정)은 **같은 행을 upsert**한다
- 표정 xor 못 갔어요: `(did_not_attend AND mood IS NULL) OR (NOT did_not_attend AND mood IS NOT NULL)`
- 아쉬운 점은 낮은 표정일 때만: `cardinality(regret_codes) = 0 OR (mood IS NOT NULL AND mood <= 2)` — 🔴 `mood <= 2`만 쓰면 mood가 NULL일 때 CHECK가 **통과**해 버린다(NULL은 위반이 아니다). 그래서 `mood IS NOT NULL`을 같이 건다
- 못 갔어요면 나머지 없음: `NOT did_not_attend OR (comment IS NULL AND cardinality(regret_codes) = 0)`
- 공개는 소감이 있어야: `NOT comment_public OR comment IS NOT NULL`
- **운영자가 내린 소감은 공개 상태일 수 없다**: `comment_hidden_at IS NULL OR NOT comment_public`
- 내린 사람은 내린 시각과 함께만: `comment_hidden_by IS NULL OR comment_hidden_at IS NOT NULL`

**운영자 내림 — 판단과 권고**
- **권고: 운영자가 내린 소감은 회원이 다시 공개하지 못한다.** 다시 켤 수 있으면 운영자 내림이 「회원 한 번 클릭」으로 무력해져, 남의 실명이 든 소감을 내린 이유(§7-4)가 사라진다. 그래서 앱 코드 판정만이 아니라 **DB CHECK로 막는다**(위 첫 줄) — service_role 코드 실수로 `comment_public=true`를 써도 `23514`로 거절된다
- 회원 화면에서는 그 소감의 공개 스위치 대신 「운영자가 공개를 내렸어요」 한 줄(문구는 디자인 몫). **회원이 할 수 있는 것** = 소감 수정(기간 안) 또는 그대로 두기 — 비공개로는 계속 본인·운영자에게 남는다
- **되살리기는 운영자만** — `comment_hidden_at`·`comment_hidden_by`를 NULL로 비운다(내림 해제). 해제해도 자동으로 공개되지 않고 `comment_public=false` 상태로 돌아간다 — 다시 공개할지는 회원이 정한다(공개 동의는 회원 것이다)
- 판정 칸을 `hidden_by`가 아니라 `hidden_at`으로 둔 이유 — `hidden_by`는 운영자 계정이 지워지면 `SET NULL`로 비는데, 그때 내림이 저절로 풀리면 안 된다
- 운영자가 내릴 때 `comment_public=false`, `comment_hidden_at=now()`, `comment_hidden_by=운영자 id`를 **한 UPDATE로** 쓴다(CHECK가 셋을 함께 요구한다). `comment_unpublished_at`은 건드리지 않는다 — 그 칸은 **회원이** 내린 시각이다

**코드 목록 (코드 ↔ CHECK 동기 필수 — `pricing.ts` ↔ SQL 스텝 할인 동기와 같은 종류)**

| 코드 | 문구 (시안 README) |
|---|---|
| `short_time` | 이야기할 시간이 짧았어요 |
| `long_talk` | 몇 사람 이야기가 길었어요 |
| `unsmooth` | 진행이 매끄럽지 않았어요 |
| `hard_to_join` | 대화에 끼기 어려웠어요 |
| `space` | 공간이 불편했어요 |
| `book_fit` | 책이 잘 안 맞았어요 |
| `info` | 시간·장소 안내가 헷갈렸어요 |
| `other` | 기타 (→ `regret_other`) |

> 문구는 DB에 넣지 않는다 — 코드만 저장하고 문구는 코드 상수(예: `src/lib/review-codes.ts`)가 갖는다. 문구를 고쳐도 DB를 안 건드린다. 코드를 **늘릴** 때만 CHECK를 넓힌다.

**인덱스**
- `UNIQUE (user_id, meeting_id)`가 회원 기준 조회를 덮는다
- `idx_meeting_reviews_meeting (meeting_id)` — 운영자 모임별 집계
- `idx_meeting_reviews_public (meeting_id, comment_published_at DESC) WHERE comment_public` — 공개 소감 읽기 (운영자가 내린 행은 CHECK상 `comment_public=false`라 이 인덱스에 들어오지 않는다)

## 3. ② RLS · ③ 함수/RPC

### 3-1. RLS

| 표 | SELECT | INSERT/UPDATE/DELETE |
|---|---|---|
| `meeting_reviews` | **본인**(`user_id = auth.uid()`) + **총괄운영자**(`public.is_admin()`) | 정책 없음 → service_role(API Route)만 |
| `meeting_praises` | **받은 사람만**, 그리고 **모임 4일 뒤부터**(§3-2 이유) | 정책 없음 → service_role만 + UPDATE 트리거 |

- **열람 = 총괄운영자(admin)만** (대표님 답, 2026-10-12). ~~admin + editor~~(초판)에서 좁혔다. editor는 RLS로도, 화면으로도 못 본다
  - **운영자 후기 화면도 admin 전용 메뉴로** — `src/components/admin/adminMenu.ts`에서 `adminOnly`(정산·회원 개인정보·사이트 설정과 같은 칸). 메뉴만 숨기지 말고 **페이지·API도 admin 판정**을 한다(layout 역할 체크 + `is_admin()` 이중, 기존 「Admin access dual-layered」 규칙)
  - 🔴 **문구 어긋남 — 디자인 몫:** 시안 알림톡 안 A·B와 운영자 화면 머리말이 「표정은 **운영진**만 봐요/보고」라고 쓴다. 역할 매트릭스에서 「운영진」은 **editor**를 뜻하므로, 이대로 나가면 회원에게 틀린 말이 된다 → **「운영자만 봐요」로 바꿀 필요가 있다.** 알림톡은 심사 대상이라 **템플릿 제출 전에** 고쳐야 한다(승인 뒤 고치면 재심사). 이 문서는 문안을 고치지 않는다 — 디자인에 넘길 사항
- **공개 소감 내리기도 admin만** — 쓰기는 service_role API이므로 API가 `is_admin` 판정 후 §2-1의 세 칸을 쓴다
- **칭찬에는 운영자 정책이 없다** — 요구 「운영자 화면 어디에도 개수·순위 없음」. 운영자 계정으로 앱을 통해 읽을 길이 0이다. ⚠️ DB 콘솔(service_role)에서는 누구든 볼 수 있다 — 막을 수 없는 층이고, **화면에 안 띄우는 것**이 이 결정의 실행 범위다
- **보낸 사람의 「내가 보낸 칭찬」**(시안 07 선택 표시 · 11 재방문)은 RLS로 열지 않는다. API가 service_role로 `sender_id = 로그인 사용자`만 걸어 돌려준다 — 받은 사람이 아닌 사람에게 SELECT 정책을 열면 「받은 사람만」이 깨진다

### 3-2. 읽기 RPC 2개

**(가) 공개 소감 — `get_region_public_comments(p_meeting_id uuid, p_limit int default 3)`**
- 대상 모임(보통 「같은 지역 다음 정기모임」 상세)을 받아, **같은 지역 · 정기 · active · 그 모임 날짜보다 앞선 모임 · 최근 180일 안(KST 오늘 기준, 관리자 결정)**의 공개 소감을 최근순으로
- **운영자가 내린 것은 거른다** — `comment_hidden_at IS NULL`. CHECK상 내린 행은 `comment_public=false`라 이미 빠지지만, 공개 경로는 두 겹으로 막는다(CHECK가 나중에 바뀌어도 이 함수가 새지 않게)
- 반환 = `nickname`, `comment`, `meeting_date` **셋뿐.** `user_id`·`real_name`·표정·아쉬운 점은 돌려주지 않는다
- `anon, authenticated` 둘 다 실행 — 비로그인 공개 모임 상세(`policy/meetings/[id]`, anon server client)에서도 부른다. 같은 결의 선례: `get_member_count()`(anon 허용, PII 0)
- 「더 보기」는 `p_limit`을 키워 부른다(함수 안에서 1~20으로 잘라 무한 조회를 막는다)
- 뷰가 아니라 RPC인 이유 — 뷰로 열면 `meeting_reviews`의 다른 칸(표정)을 실수로 같이 열 위험이 있고, `profiles` RLS를 우회하려면 어차피 SECURITY DEFINER가 필요하다

**(나) 받은 칭찬 — `get_my_received_praises()`**
- `auth.uid()`가 받은 칭찬을 모임별로: `meeting_id`, `meeting_date`, `phrase_code`, `sender_nickname`
- 보낸 사람 닉네임을 붙이려면 `profiles`를 읽어야 해서 SECURITY DEFINER가 필요하다(회원은 남의 프로필을 RLS로 못 읽는다)
- **모임 날짜 + 4일 이후의 것만** — 4일 뒤 앱 알림 한 번(시안 17 → 18)이 「도착」이려면 그 전엔 안 보여야 한다. 크론이 실패해도 날짜로 열리므로 칭찬이 갇히지 않는다
- `authenticated`만 실행

> 날짜 비교는 DB 쪽에서 `(now() AT TIME ZONE 'Asia/Seoul')::date`로 한다. `kst.ts` 규칙은 TypeScript 코드의 `new Date()` 금지이고, SQL 안에서는 이 식이 같은 역할이다(기존 쿼리 문서들도 같은 식을 쓴다).

- `meeting_praises_block_update()` — `notified_at` 외 칸이 바뀌면 예외. DELETE는 막지 않는다(§5-3 정정 경로 — 운영자가 SQL로만, 승인 뒤)

### 3-4. 운영자 화면 숫자 — 함수 없이, 코드(service_role)에서 계산

`lib/dashboard.ts`·`settlement.ts`처럼 service_role로 읽어 순수 함수로 계산한다(단위 테스트 대상). 계산 정의를 여기 적어 두고, 숫자 정의를 화면마다 따로 만들지 않는다 — 물어보기 응답률 100% 초과 사고(DECISIONS 2026-07-24)가 분자·분모를 다른 곳에서 가져와 났다.

| 숫자 | 분자 | 분모 |
|---|---|---|
| 후기 남긴 비율 | 그 모임 `meeting_reviews` 중 `did_not_attend = false` | 그 모임 참여자(confirmed+pending_transfer) — 시안 A1 「28 / 42명」 |
| 표정 평균·분포 | `mood` (못 갔어요 제외) | 같은 행들 |
| 아쉬운 점 | `unnest(regret_codes)` 집계 | 낮은 표정(1·2)을 고른 사람 수 |
| **첫 모임 회원** (관리자 결정) | 그 모임이 그 회원의 **DB상 처음 참여한 정기모임**(정기 · active · 참여 = confirmed·pending_transfer)인 사람. 토론모임 참여는 「첫 모임」 판정에 넣지 않는다 | — |
| **14일 안 재신청** (관리자 결정) | 첫 모임 회원 중 둘 중 하나라도 해당: **(가)** 그 모임 **다음 날 ~ 14일 뒤**(KST, `created_at` 기준)에 **다른 모임** 신청 행이 새로 생겼다 · **(나)** 그 모임 **전에 이미 신청해 둔 다음 모임**(그 모임보다 날짜가 뒤인 다른 모임)이 있다. 둘 다 **status 무관**(취소해도 신청은 한 것, 시안 A2 · DECISIONS 2026-08-26 온보딩 북극성과 같은 규칙) · 모임 유형 무관(토론모임 신청도 재신청) | 첫 모임 회원 수. (나)가 없고 기한이 안 끝난 사람은 「아직 · N일 남음」 |

```sql
-- 계산이 되는지 보이는 초안 (읽기 전용). 코드는 이 정의를 순수 함수로 옮긴다
with part as (
  select r.user_id, r.meeting_id, m.date
  from public.registrations r
  join public.meetings m on m.id = r.meeting_id
  where r.status in ('confirmed', 'pending_transfer')
    and m.status = 'active'
    and m.meeting_type = 'regular'          -- 첫 모임 = DB상 처음 참여한 「정기」모임
),
first_meeting as (
  select distinct on (user_id) user_id, meeting_id, date
  from part
  order by user_id, date, meeting_id
)
select fm.user_id, mr.mood, mr.did_not_attend,
       exists (
         select 1
         from public.registrations r2
         join public.meetings m2 on m2.id = r2.meeting_id
         where r2.user_id = fm.user_id
           and r2.meeting_id <> fm.meeting_id
           and (
             -- (가) 그 모임 뒤 14일 안에 새로 신청
             (    (r2.created_at at time zone 'Asia/Seoul')::date >  fm.date
              and (r2.created_at at time zone 'Asia/Seoul')::date <= fm.date + 14)
             -- (나) 그 모임 전에 이미 신청해 둔 「다음」 모임
             or (    (r2.created_at at time zone 'Asia/Seoul')::date <= fm.date
                 and m2.date > fm.date)
           )
       ) as reregistered_14d
from first_meeting fm
left join public.meeting_reviews mr
  on mr.user_id = fm.user_id and mr.meeting_id = fm.meeting_id
where fm.meeting_id = :meeting_id;
```

> ✅ **초판에서 갈렸던 두 해석은 관리자가 닫았다(2026-10-12)** — (a) 미리 신청해 둔 다음 모임 = 재신청으로 센다(위 (나)) (b) 「첫 모임」은 **DB상** 첫 정기 참여로 본다. 구글폼 시절 참여 이력은 DB에 없어 오래된 회원이 「첫 모임」으로 잡힐 수 있다는 한계는 **받아들인 것**이다 — 화면 머리말에 「DB 기록 기준」을 적어 두면 읽는 사람이 오해하지 않는다(문구는 디자인 몫).
> ⚠️ (나)의 「다음 모임」은 날짜가 더 늦은 모임이면 기간 제한 없이 센다(14일 밖 먼 모임을 미리 신청해 둔 경우 포함). 지시문 「이미 신청해 둔 다음 모임」을 글자 그대로 옮긴 것이다 — 14일 안의 모임으로 좁힐 필요가 생기면 `m2.date <= fm.date + 14` 한 줄을 더한다.

### 3-5. `/my` 분기 순서 (코드 계획 — DB가 받쳐야 하는 판정)

알림톡 버튼은 새 주소 없이 **기존 `/my`**(DECISIONS 시안 확정). 순서:

```
/my 진입
├─ next_ui 꺼짐 → 지금 구 화면 그대로 (후기 분기 없음 — 후기 화면은 (next) 그룹 안이라 next_ui 뒤에 있다.
│                 크론도 next_ui 꺼져 있으면 후기 알림톡을 안 보낸다 → 이 경우 버튼으로 올 사람이 없다)
└─ next_ui 켜짐 + 로그인
   ├─ ① review_enabled 켜짐 AND 미완료 후기 있음 → /review/{meetingId}   ← 새로 끼우는 자리
   │      미완료 후기 = 참여(confirmed·pending_transfer) · 정기 · active · 오늘이 D+1~D+3(KST)
   │                    · meeting_reviews 행 없음 → 그중 가장 최근 모임 1건
   ├─ ①' review_enabled 켜짐 AND 기간 지난 후기 있음 → /review/{meetingId} (시안 12 「기간 지남」)  ← 관리자 결정으로 추가
   │      기간 지난 후기 = 위와 같은 참여·정기·active · 오늘이 D+4~D+7(KST) · meeting_reviews 행 없음
   │                      · 🔴 그 (회원, 모임)에 meeting_review 알림톡이 나갔다(notifications.type='meeting_review')
   │                      → 그중 가장 최근 모임 1건
   ├─ ② 미해소 물어보기 있음(library_enabled) → /shelf     ← 지금 그대로
   └─ ③ 그 외 → /me                                        ← 지금 그대로
```

- **「완료」 = `meeting_reviews` 행이 있다 = ①(표정 또는 못 갔어요)을 마쳤다** (관리자 결정, 2026-10-12). ②③④를 건너뛰어도 완료다(시안 「건너뛰기」). 그래서 한 번 ①을 마친 사람이 알림톡을 다시 누르면 ②(물어보기 띠)로 간다 — ④를 건너뛴 사람에게 책 담기 안전망이 그대로 남는다
- ①을 ②보다 앞에 두는 이유 — 후기 기간(3일) 안의 같은 모임은 물어보기도 열려 있다. ②가 앞이면 후기 알림톡을 누른 사람이 서재로 간다
- **①'(기간 지남, D+4~D+7)** — 알림톡을 늦게 누른 사람에게 「왜 아무것도 없지」 대신 시안 12번을 보여준다. 조건에 **「후기 알림톡을 받았다」를 넣은 이유** — 스위치를 켜기 전(`book_ask` 시절) 모임의 참여자는 후기를 요청받은 적이 없는데, 이 조건이 없으면 켠 첫 주에 그들이 「기간이 지났어요」 화면을 받는다. D+7 뒤에는 ②·③으로 간다
  - 12번 화면은 막다른 길이면 안 된다 — 물어보기가 열려 있으면 서재로 가는 버튼을 같이 두는 것이 맞다(②가 ①' 뒤로 밀렸으므로). 화면 구성은 디자인 몫
  - `/my`는 `next_ui` 켜짐 상태에서 하단 탭이 가리키지 않는 주소라(나 탭은 `/me`) 실제로 들어오는 길은 거의 알림톡 버튼뿐이다 → D+4~D+7 동안 「들어올 때마다 12번」이 반복돼도 범위가 좁다. 🟨 단 구 링크·북마크로 `/my`에 오는 사람이 있는지는 재지 않았다
- 판정 함수 `getPendingReview(userId)`는 **표가 없거나 조회가 실패하면 null을 돌려 ②로 떨어진다.** 🔴 단 실패를 조용히 삼키지 않고 `console.error`로 남긴다 — 「조회 실패」와 「대상 없음」을 합쳐 덮은 것이 결제 사고를 몇 달 숨겼다(루트 `CLAUDE.md` 「결제 안전망」). 여기는 돈이 아니라 화면 분기라 500으로 끝내지는 않는다

### 3-6. 크론 (10:00 교체 · 칭찬 모음 신설)

| 크론 | 시각 | 무엇 |
|---|---|---|
| `/api/cron/book-ask` (기존, 이름 유지) | KST 10:00 (UTC `0 1 * * *`) | `review_enabled` 켜짐 + `next_ui` 켜짐 + `SOLAPI_TEMPLATE_MEETING_REVIEW` env 있음 → **`meeting_review`** 발송, 대상에서 `meeting_reviews` 행 있는 사람 제외. 하나라도 아니면 → 지금처럼 **`book_ask`**. 한 모임에 둘 다 가지 않는다. 정기만은 `isAskEligibleMeeting`이 이미 보장 |
| **`/api/cron/praise-digest` (신설)** | **KST 12:00 (UTC `0 3 * * *`)** — 관리자 확정(2026-10-12) | 모임 날짜가 `오늘−14 ~ 오늘−4`이고 active인 모임의 `notified_at IS NULL` 칭찬 → (받은 사람, 모임)마다 `app_notifications` 한 행(`praise_received`) → 그 칭찬들 `notified_at = now()` |

- **12:00을 고른 이유** — 기존 10:00 · 18:30 · 19:00과 겹치지 않는다. 프로필 기록상 Hobby 크론 실행 정밀도가 **±59분**이라 10:00 크론은 10:59까지 밀릴 수 있다 → 11:00은 붙어 있고 12:00이면 한 시간 띄운다. 낮 시간이라 알림 확인이 자연스럽고, 저녁 두 크론(18:30·19:00)과 묶이지 않는다
- **오늘−14까지 보는 이유** = catch-up. 4일째 크론이 실패하면 다음 날 다시 줍는다(`waitlist-refund`의 `date <= tomorrow` catch-up과 같은 모양). 14일로 상한을 둬서 아주 옛 칭찬이 갑자기 알림으로 튀지 않게 한다
- **중복 차단** — `app_notifications`에 부분 UNIQUE `(user_id, (payload->>'meeting_id')) WHERE type = 'praise_received'`. 크론이 두 번 돌아도 `23505`로 걸린다(알림톡 `idx_notifications_book_ask_unique`와 같은 수법). 순서는 INSERT(on conflict do nothing) → `notified_at` UPDATE. 중간에 죽어도 다음 실행이 알림을 또 만들지 않는다
- **payload에 개수·보낸 사람을 넣지 않는다** — `{ meeting_id, meeting_date }`만. 시안 17 「칭찬이 왔어요」(개수 없음)
- 알림톡 아님 — `notifications` 표를 건드리지 않는다

## 4. ④ 실행 순서와 코드 배포 순서

🔴 **원칙** — (1) 코드가 확정된 **뒤에** SQL을 안내한다 (2) `CREATE FUNCTION`은 표 DDL과 **따로** 돌린다 (3) CHECK를 넓히는 SQL은 그 타입을 보내는 코드보다 **먼저** (4) prod에 돌린 SQL은 **같은 PR에 파일로 커밋**한다(`migration-meeting-review.sql` + `-rollback.sql`) (5) 모든 prod 쓰기는 **대표님 승인 뒤**.

### 4-0. 사전 점검 (읽기만 — 돌리기 전에 반드시)

```sql
-- (1) 넓힐 CHECK의 지금 정의 — 아래 4-2의 목록이 이것과 「지금 것 + 새 1개」로 정확히 맞아야 한다.
--     prod에 저장소 파일과 다른 타입이 더 들어가 있으면 4-2를 그대로 돌리는 순간 그 타입 INSERT가 깨진다
select conrelid::regclass as tbl, conname, pg_get_constraintdef(oid)
from pg_constraint
where conname in ('notifications_type_check', 'app_notifications_type_check', 'book_asks_status_check');

-- (2) 이름 충돌 없음 확인 (기대: 0행)
```

### 4-3. 3회차 — 함수 (따로 돌린다)

```sql
-- (가) 공개 소감 — 비로그인도 읽는다. 닉네임·소감·모임일만
create or replace function public.get_region_public_comments(
  p_meeting_id uuid,
  p_limit integer default 3
)
returns table(nickname text, comment text, meeting_date date)
language sql
security definer
set search_path = ''
stable
as $$
  select p.nickname, r.comment, m.date
  from public.meetings t
  join public.meetings m
    on m.region = t.region
   and m.meeting_type = 'regular'
   and m.status = 'active'
   and m.date < t.date
   and m.date >= ((now() at time zone 'Asia/Seoul')::date - 180)   -- 최근 180일 (관리자 결정)
  join public.meeting_reviews r on r.meeting_id = m.id
  join public.profiles p on p.id = r.user_id
  where t.id = p_meeting_id
    and t.meeting_type = 'regular'
    and r.comment_public = true
    and r.comment_hidden_at is null          -- 운영자가 내린 것 제외 (CHECK와 두 겹)
    and r.comment is not null
    and r.did_not_attend = false
    and coalesce(p.nickname, '') <> ''
  order by m.date desc, r.comment_published_at desc nulls last
  limit least(greatest(coalesce(p_limit, 3), 1), 20);
$$;

revoke execute on function public.get_region_public_comments(uuid, integer) from public;
grant execute on function public.get_region_public_comments(uuid, integer) to anon, authenticated;
```

```sql
-- (나) 받은 칭찬 — 본인 것만, 모임 4일 뒤부터, 보낸 사람은 닉네임만
create or replace function public.get_my_received_praises()

              sender_nickname text, created_at timestamptz)

set search_path = ''
```

```sql
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  if new.meeting_id   is distinct from old.meeting_id
  or new.sender_id    is distinct from old.sender_id

  end if;
```

## 5. ⑤ 되돌리는 SQL

**1순위는 SQL이 아니다** — `review_enabled`를 `off`로(또는 행 삭제). 10:00은 다음 날부터 `book_ask`로 돌아가고, /my 분기와 후기 화면이 닫힌다. 데이터는 남는다. 코드 문제면 `git revert -m 1 <merge-sha>`(코드만, DB 그대로 — 저장소 롤백 원칙).

표까지 걷어야 할 때만 아래. 🔴 **지우기 전에 두 표를 떠 둔다**(`select * from …` 결과 저장) — 회원이 쓴 후기·받은 칭찬은 되살릴 수 없다.

```sql

-- 전제: 스위치 off + 코드 revert 완료 (코드가 아직 이 표를 읽으면 화면이 깨진다)

-- 4회차·3회차 되돌리기

drop function if exists public.meeting_praises_block_update();
drop function if exists public.get_my_received_praises();
drop function if exists public.get_region_public_comments(uuid, integer);

-- (부분) 운영자 내림 기능만 걷을 때 — 표는 남기고 칸·제약만
--   🔴 먼저 할 일: 운영자가 내린 행을 떠 둔다
--      select id, user_id, meeting_id, comment, comment_hidden_at, comment_hidden_by
--      from public.meeting_reviews where comment_hidden_at is not null;
```

## 6. 책 담기 전환율(북극성)이 어떻게 흔들리나 — 세는 법 제안

**지금 정의** (DECISIONS 2026-07-24 · `computeAskStats`): 분모 = 60일 정기 자격 참여, 노출 = 그중 `book_asks` 행 있음(viewed+answered+dismissed), **전환율 = 담음 ÷ 노출**, 노출 30건 미만은 판단 유보.

**바뀌는 것**
1. **노출 경로가 바뀐다.** 지금은 「알림톡 → /shelf 띠(첫 화면이 책 담기)」. 후기 뒤에는 「알림톡 → ① 표정 → ② → ③ → **④ 책 담기**」. ④까지 오는 사람은 ①~③을 지나온 **걸러진 사람들**이다 → **전환율은 오르고 노출률은 떨어질 가능성이 크다.** 두 시기 숫자를 한 줄로 이으면 「후기를 붙였더니 전환율이 올랐다」는 착시가 생긴다
2. **「못 갔어요」가 분모에 남는다.** 그들에게는 ④가 안 뜬다(시안 04). 노출률 분모에서 빼야 노출률이 정직하다 — 지금은 못 간 사람을 셀 방법이 없었고, 이제 생긴다
3. **30건 게이트가 다시 0부터다.** 경로가 바뀐 뒤 숫자는 다른 모집단이다

**제안 — `book_asks`를 계속 쓴다** (새 장부를 만들지 않는다. 장부를 둘로 나누면 분자·분모를 다른 곳에서 가져오는 그 사고가 다시 난다)

| 할 일 | 어떻게 |
|---|---|
| ④를 열면 노출 기록 | 지금 띠와 똑같이 `recordAskViewed` (첫 1회, `first_viewed_at` 보존) |
| ④에서 담으면 | 지금 `answer` 경로 그대로 + **`answered_surface = 'review'`**. 띠에서 담으면 `'strip'`·`'meeting_detail'` |
| ④ 「건너뛰기」 | **아무것도 안 쓴다**(`viewed`로 남는다). `dismissed`로 쓰면 서재 띠 안전망이 닫힌다 — 건너뛰기는 「책 얘기 싫다」가 아니라 「지금은 아니다」다 |
| 시기를 가르는 기준 | **칸을 새로 만들지 않고** 그 (회원, 모임)에 **어떤 다음 날 알림톡이 나갔는지**로 가른다 — `notifications.type`이 `book_ask`면 옛 경로, `meeting_review`면 새 경로. 이미 쌓이는 기록이라 소급도 된다 |
| 운영자 미니 카운트(`/admin/library`) | `computeAskStats`에 시기 구분을 더해 **두 줄로** 보여준다(옛 경로 / 후기 경로). 후기 경로 줄은 노출 30건 미만이면 「판단 유보」 |
| 새로 볼 깔때기 (후기 경로 전용) | 후기 알림톡 발송 → ① 완료(`meeting_reviews` 행, 못 갔어요 제외) → ④ 노출(`book_asks` 행) → 담음(`answered`). 각 단계 분모는 바로 앞 단계 |

> ⚠️ 이 정의를 데이터가 게이트로 봐야 한다(부서정의 — 데이터는 심기 전에 「이게 되는지 어떻게 알 건가」를 검토). 데이터 부서는 지금 ⛔ 관리자 대행이다 → §8.

## 7. ⑥ 사후 잔재 점검 4가지

### 7-1. 며칠 방치

| 방치된 것 | 어떻게 되나 |
|---|---|
| 후기를 안 씀 | D+3 끝나면 저절로 닫힌다 — 코드가 날짜로 판정, 행이 안 생길 뿐 남는 잔재 없음. 홈 「할 일」 줄도 마감일까지만(시안 01). D+4~D+7에 알림톡 버튼으로 오면 「기간 지남」(시안 12, §3-5 ①'), D+7 뒤로는 그 분기도 끝난다 |
| 운영자가 내린 소감 | 내림은 풀릴 때까지 계속된다(기간 없음). 운영자 후기 화면에 「운영자가 내림 · 날짜」로 남아 있어야 해제할 수 있다 — 숨김 목록이 화면에서 사라지면 해제 경로가 없어진다(4시나리오 3번) |
| ①만 하고 나감 | 행이 있으니 「완료」. /my는 다음부터 ② 물어보기로 간다. 표정은 이미 저장돼 운영자 숫자에 들어간다 |
| 칭찬 알림 크론 실패 | 다음 날 catch-up(최대 14일). 받은 칭찬 보기는 날짜로 열려 크론과 무관 |
| `book_asks` `viewed` | 지금과 같다 — 60일 창이 지나면 띠에서 사라진다(`ASK_WINDOW_DAYS`) |
| 공개 소감 | 내리기 전까지 공개 동의는 유지되지만, **모임 날짜가 180일을 넘으면 공개 소감 RPC에서 저절로 빠진다**(관리자 결정). 행·동의는 남는다 — 본인 「내가 남긴 후기」에서는 계속 보인다 |

### 7-2. 모임 삭제 후

- 모임 삭제는 행을 지우지 않고 `status = 'deleted'`로 바꾼다(`active → deleting → deleted`). 그래서 **FK CASCADE는 안 터지고 후기·칭찬 행이 남는다.**
- 그래서 **읽는 모든 자리가 `m.status = 'active'`를 건다** — 공개 소감 RPC(✅ 초안에 있음) · 받은 칭찬 RPC(✅) · 10:00 크론(✅ 기존 그대로) · 칭찬 크론(계획에 명시) · /my 판정 · 운영자 목록. 삭제된 모임은 전액 환불된 모임이라 「없던 모임」으로 다루는 것이 맞다
- 받은 사람 쪽 — 삭제된 모임에서 받은 칭찬은 「받은 칭찬」에서 사라진다. 의도
- 운영자 — 삭제된 모임의 운영자 상세 접근 가능 여부(4시나리오 2번)는 기존 화면 규칙을 따른다. 후기 목록에는 안 넣는다
- SQL 콘솔에서 모임 행을 진짜 지우면 CASCADE로 후기·칭찬도 같이 사라진다(되살릴 수 없음)
- 회원 탈퇴(프로필 삭제) → 그 회원이 쓴 후기·보낸 칭찬·받은 칭찬 모두 CASCADE

### 7-3. 잘못 누른 것 정정

| 실수 | 정정 경로 |
|---|---|
| 「못 갔어요」를 잘못 누름 | 시안 04의 되돌아가기 → 같은 행을 `did_not_attend=false, mood=N`으로 UPDATE. CHECK가 둘 다 허용(xor) |
| 표정을 잘못 고름 | **기간 안에서는** 다시 고를 수 있다(같은 행 upsert). 🔴 표정을 3 이상으로 올리면 코드가 `regret_codes`·`regret_other`를 **같이 비워야 한다** — 안 비우면 CHECK `23514`로 저장 실패(시안 13 저장 실패 화면으로 간다). 기간 뒤 수정은 막는다(운영자 숫자가 확정된 뒤 흔들리지 않게) |
| 공개를 잘못 켬 | **언제든**(기간 뒤에도) 내리기/다시 공개 — `comment_public` + 시각 칸. 「내 활동 → 내가 남긴 후기」(시안 15·16). 단 **운영자가 내린 소감은 회원이 다시 공개 못 한다**(CHECK) |
| 운영자가 잘못 내림 | 운영자가 해제(`comment_hidden_at`·`comment_hidden_by` NULL). 해제 뒤 `comment_public=false`로 남고 **다시 공개할지는 회원이 정한다** — 운영자가 회원 대신 공개로 돌리지 않는다(공개 동의는 회원 것) |
| 소감 오타 | 기간 안에서만 수정. 🟨 기간 뒤 「소감 지우기」를 열지 →§8 |
| 칭찬을 엉뚱한 사람에게 | **바꿀 수 없다**(결정). 트리거가 UPDATE를 막는다. 유일한 길 = 회원이 운영자에게 말하고 **운영자가 SQL로 그 행 DELETE**(prod 쓰기 — 승인 뒤). 받은 사람에게 이미 알림이 갔으면 알림 행은 남는다(「칭찬이 왔어요」인데 열면 하나 적음 — 개수를 안 보여주므로 드러나지 않는다) |
| 책을 잘못 담음 | 기존 서재 관리(`/shelf/manage` 빼기)로. `book_asks`는 `answered`로 남는다 — 지금 띠에서 잘못 담았을 때와 같다 |
