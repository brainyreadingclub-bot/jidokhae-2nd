# 모임 후기 — DB 변경 계획 (실행 전, 대표님 확인용)

> 2026-10-12 · 아직 실행하지 않았다. 대표님이 보고 답한 뒤에만 실행한다.
> SQL 전문과 되돌리는 SQL은 `계획서-전문.md`에 있다(§4 실행 SQL, §5 되돌리는 SQL).

## 무엇이 생기나 (쉬운 말)

- 새 표 둘 — 「후기」(회원 한 명이 모임 하나에 한 장)와 「칭찬」(보낸 사람·받은 사람·모임마다 한 번)
- 기존 「책 담기 기록」에 칸 하나 — 어느 화면에서 담았는지(후기 화면인지 서재 띠인지)
- 알림 종류 둘 추가 — 후기 알림톡, 칭찬 도착 앱 알림
- 기능 스위치를 켜기 전에는 회원 화면·알림톡이 지금과 똑같다. 표만 먼저 생긴다

## 누가 무엇을 읽을 수 있나 (가장 중요)

**표정·아쉬운 점** — 쓴 본인과 총괄운영자만. 다른 회원은 못 읽는다. 운영진(편집 권한)도 못 읽는다. 데이터베이스 규칙으로 막고, 운영자 화면도 총괄운영자 전용 메뉴로 둔다.

**한 줄 소감** — 쓴 본인과 총괄운영자만 통째로 읽는다. 다른 회원과 로그인 안 한 사람이 볼 수 있는 것은 「공개해도 좋아요」를 켠 소감뿐이고, 그것도 **닉네임 · 소감 문장 · 모임 날짜 세 가지만** 따로 꺼내 주는 창구로만 나간다. 표정·아쉬운 점·실명은 그 창구로 나가지 않는다. 운영자가 내린 소감, 180일이 지난 소감은 그 창구에서도 빠진다.

**칭찬** — 받은 사람만 읽는다. 그것도 모임 4일 뒤부터. 보낸 사람은 자기가 보낸 것만 서버를 거쳐 확인한다. **다른 회원은 물론 운영자 화면에도 칭찬은 없다** — 개수·순위를 셀 화면이 없다. (데이터베이스를 직접 여는 관리 콘솔에서는 볼 수 있다. 이 층은 막을 수 없고, 화면에 띄우지 않는 것까지가 이번 약속이다)

**쓰기** — 회원 브라우저가 이 표들에 직접 쓰는 길은 없다. 전부 서버를 거쳐 쓰고, 서버가 「본인인지 · 그 모임 참석자인지 · 기간 안인지」를 확인한다. 보낸 칭찬은 서버도 고칠 수 없게 막아 둔다.

## 실행 전 점검 (2026-10-12, 읽기만)

기존 알림 종류 목록이 계획서 전제와 같고, 새 이름이 겹치는 것도 없다. 필요한 기존 함수도 다 있다.
