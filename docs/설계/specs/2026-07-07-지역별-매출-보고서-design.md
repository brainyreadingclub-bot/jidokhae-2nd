# 지역별 매출 보고서 — 설계서

- 날짜: 2026-07-07
- 상태: 승인됨 (구현 대기)
- 브랜치: `feat/settlement-region-revenue`

## 배경 / 목적

운영자가 공간대여비를 지급할 근거로, **지역별로 실제 걷힌 매출과 참여 인원**을 보고 싶다.
- 경주 → '우연히 책방', 포항 → '공간지그시'에 대여비 지급
- 나중에 대구 등 지역이 추가될 수 있으므로 **지역 목록을 하드코딩하지 않는다**

## 매출/참여 정의 (확정)

- **참여 인원** = 해당 지역 모임의 `status='confirmed'` 등록자 수
- **매출** = 그 confirmed 등록자들의 `paid_amount` 합계 (스텝 50% 할인가 그대로 반영)
- 취소(cancelled)·미입금(pending_transfer)·대기(waitlisted)는 제외
- 앱 대시보드의 "순매출"(환불 차감 계산)과 다름 — 이건 **실제 결제된 총액(gross)**. 환불을 빼지 않는다.

## 집계 축

- **월별** — `meeting.date` 기준 (`getMonthRange` 사용, 신청 시각 아님)
- **전체 누적** — 전 기간 합계
- 두 축을 화면에서 토글로 전환

## 위치

`/admin/settlements`에 3번째 탭 **"지역별 매출"** 추가. admin 전용 게이트(`profile.role !== 'admin'`) 그대로 재사용.

## 데이터 설계

신규 함수 `getRegionRevenueData(supabase)` — `src/lib/settlement.ts`

- confirmed 등록 + 모임(region, date) 조인, 등록 1건 = 결과 1행
- 반환: `RegionRevenueEntry[]` = `{ region: string; month: string /* YYYY-MM */; meetingId: string; paidAmount: number }`
- 삭제된 모임(status='deleted')은 제외 (confirmed와 공존 불가하지만 방어적으로 필터)
- 지역 목록은 결과에서 동적 추출

클라이언트(`RegionRevenueTable`)가 in-memory로 그룹핑:
- 월별/전체 선택에 따라 필터
- 지역별: 모임 수(distinct meetingId), 참여 인원(행 수), 매출 합계
- 합계 행 추가
- **API route 불필요** — 서버가 전체 데이터를 1회 페치, 월 전환은 클라이언트 계산 (데이터 규모 작음)

- 모바일: 지역별 카드(지역명 + 모임/참여/매출), 데스크톱: 테이블 — 기존 두 탭과 동일 반응형 패턴
- 금액: `formatFee()` + '원' (숫자만 반환 규칙 준수)
- 빈 월: "이번 달 매출 없음" 안내
- 월 네비: 데이터 최소월 ~ 현재 KST월 범위, prev/next 버튼

## 범위 밖 (YAGNI)

- 공간(venue) 단위 세분화 — 지역=공간 1:1이라 불필요
- 그래프/차트 — 지역 2~3개엔 과함
- CSV 내보내기 — 요청 없음
- **DB 마이그레이션 불필요** — 기존 컬럼(meetings.region, registrations.status/paid_amount)만 사용

## 리스크 / 기존 기능 영향

- `getRegionRevenueData`는 순수 신규 함수 — 기존 쿼리 무수정 → 입금/환불 탭 무영향
- `SettlementTabs`의 tab union에 `'region'` 추가 — 기존 두 탭 분기 유지, 신규 조건만 추가
- `page.tsx` Promise.all에 페치 1개 추가 — 실패 시 페이지 전체가 실패하므로 쿼리 안정성 확인 필요
- 서버 컴포넌트에서 fetch, 클라이언트는 계산만 — 민감정보(연락처 등) 미노출 (지역 집계라 개인정보 없음)
