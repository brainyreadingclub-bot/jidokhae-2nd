## 0. 대표님용 요약

1. 지금 권한은 **세 군데에 흩어져 있다.** 운영진 지정·스텝 지정은 「회원 관리」 목록의 작은 배지를 눌러서 하고, 총괄 지정은 SQL로만 하고, **역할마다 무엇이 열리고 잠기는지는 어디에도 한눈에 안 보인다**(코드 30여 곳에 나뉘어 있다).
2. 새 화면 「권한 설정」(운영 화면 › 시스템, **총괄만**)을 하나 둔다. 여기서 ① 운영진·스텝 명단을 보고 ② 회원을 찾아 역할을 바꾸고 ③ 역할별로 열린 일·잠긴 일을 표로 보고 ④ 누가 언제 바꿨는지 기록을 본다.
3. 역할은 **네 칸 사다리**로 보여 준다 — 회원 < 스텝 < 운영진 < 총괄. 기능마다 켜고 끄는 스위치는 두지 않는다(사람마다 권한이 달라지면 아무도 전체를 모르게 된다).
4. **DB 변경 없이 만들 수 있다.** 바꾼 기록은 이미 있는 공통 기록표(`app_events`)에 남긴다.
5. 조사하다 **결정과 코드가 다른 곳 4개**를 찾았다(§2-3). 가장 큰 것은 **운영진이 모임 상세에서 「환불 필요」 신청자의 전화번호를 본다**는 것이다. 이 화면을 만들 때 같이 닫는다.

**대표님이 정할 것 3개** — §6

### 3-1. 스텝의 토론·발제 권한 — 이 목록에서 새로 확정하는 것

스텝(`is_staff`)은 원래 「할인 받는 회원」이었다. 2026-08-17부터 큐레이터 묶음에 들어가 **할인 말고 다섯 가지가 같이 따라온다.** 지정하는 사람이 이걸 알고 눌러야 하므로 바꾸기 확인 창에 그대로 적는다.

1. 발제문 쓰기·고치기·공개 — 결정됨(2026-08-17). 들어올 문은 아직 없다 → §6 ①
2. **모든 토론모임의 답변 전부 읽기** — 자기가 신청하지 않은 모임도, 공개 전(작성 중) 발제도. 결정 2026-10-13·10-15의 「운영진(curator)」에 스텝이 들어 있다. 답변이 사적인 내용이라는 점(2026-10-13 결정 이유)을 알고 지정해야 한다
3. 답변 「모임에서 이어가요」 고정 — 결정됨, 버튼 없음
4. 토론모임 참여 자격 면제 — 결정됨(2026-08-22, 「발제는 쓰는데 신청은 못 하는 사람을 만들지 않는다」)
5. 반짝모임 신고 처리 — 결정됨(2026-08-17 「번개 신고 처리」), 기능은 11월 뒤

스텝에게 **잠긴 것**: 운영 화면의 발제문 화면 말고는 전부. 모임 만들기·고치기, 신청자 실명, 회원 목록, 돈, 설정. 개인정보·정산은 2026-08-17 결정 그대로 불가.

> 잠금 목록은 **코드 한 곳의 표**로 둔다(구현 때). 지금처럼 기능마다 `role === 'admin'`을 따로 쓰면 다음 기능에서 또 어긋난다. 화면의 「역할별 할 수 있는 일」 표는 그 코드 표를 그대로 그린다 — 문서·화면·코드가 같은 표 하나를 본다.

## 4. 화면

### 4-1. 자리와 문

- 주소 `/admin/permissions`, 사이드바 **시스템 › 권한 설정**, `adminOnly`
- **화면 자체도 총괄인지 확인한다.** 레이아웃만 믿지 않는다(위 공지 보내기 화면이 레이아웃만 믿다가 운영진에게 열렸다)
- 「회원 관리」의 역할 배지·스텝 알약은 **보기만** 하게 바꾸고, 목록 위에 「역할 바꾸기는 권한 설정에서」 한 줄 링크를 둔다. 바꾸는 곳을 한 곳으로 모은다

### 4-2. 화면에서 할 수 있는 일

**① 운영진·스텝 명단** — 맨 위. 총괄·운영진·스텝인 사람만 모아 보여 준다. 줄마다 닉네임 · 지역 · 지금 역할 · 지정한 날(⑤ 기록에서 — 기록이 없으면 「기록 전」) · 「바꾸기」.
- 총괄 줄에는 「바꾸기」가 없다 — 「총괄은 SQL로만 바꿉니다」
- 내 줄에도 없다(지금 API도 자기 자신을 거부한다)

**② 회원 찾아 권한 주기** — 명단 위 검색칸(닉네임). 결과 줄에 「바꾸기」.

**③ 바꾸기 확인 창** — 세 칸 중 하나를 고른다: 회원 / 스텝 / 운영진.
- 고르면 아래에 **「새로 열리는 일」「잠기는 일」**이 잠금 목록에서 계산돼 나온다. 스텝을 고르면 §3-1의 다섯 가지가 그대로 보인다
- 「바꾸기」를 누르면 저장 + 기록 한 줄

**④ 역할별 할 수 있는 일** — §3 표를 그대로. 데스크톱은 4열 표, 폰은 역할 칩(총괄·운영진·스텝·회원)을 눌러 「할 수 있는 일 / 잠긴 일」 두 목록으로 본다. **보기 전용이다** — 기능별로 켜고 끄는 스위치는 두지 않는다.

**⑤ 바꾼 기록** — 날짜 · 누가 · 누구를 · 이전 → 이후. 최근 순, 10줄 + 「더 보기」.

### 4-3. 바꾸기 규칙

| 바꾸기 | 저장되는 값 | 비고 |
|---|---|---|
| → 회원 | `role='member'`, `is_staff=false` | |
| → 스텝 | `role='member'`, `is_staff=true` | |
| → 운영진 | `role='editor'`, `is_staff=false` | 운영진은 스텝 권한을 이미 다 가진다. 남은 `is_staff=true`가 나중에 회원으로 내릴 때 스텝으로 남는 사고를 막는다 |
| → 총괄 | 화면에서 불가 | SQL만. 총괄이 화면에서 늘거나 줄면 되돌리기 어렵다 |

- 바꾸는 사람은 **총괄만**(지금 API 그대로)
- 자기 자신·총괄 대상은 바꿀 수 없다(지금 API 그대로)
- 스텝을 해제해도 **이미 할인으로 낸 신청은 그대로**다. 돈을 되돌리지 않는다. 확인 창에 「이미 신청한 모임의 할인은 그대로예요」 한 줄
- 운영진을 내려도 그가 쓴 발제문은 그대로 남는다
- 바뀐 사람이 운영 화면을 열어 둔 채라면, 다음에 페이지를 열 때 레이아웃이 다시 확인해 돌려보낸다(지금 동작)

### 4-4. 바꾼 기록 — 새 표를 만들지 않는다

2026-10-14 결정 「공통 기록표 `app_events`를 쓰고 기능마다 기록표를 만들지 않는다」를 따른다.

- 이벤트 이름 `admin_role.change` (코드 `lib/app-events.ts` `APP_EVENTS`와 `docs/agent-team/기록표-이벤트-목록.md`에 추가)
- `user_id` = 바꾼 사람(총괄), `props` = `{ target_id, before, after }` — `before`·`after`는 `member`·`staff`·`editor` 중 하나. 실명·전화는 넣지 않는다
- 화면의 ⑤는 이 행을 서버(service_role)로 읽어 닉네임을 붙여 그린다
- **기록 실패가 바꾸기를 막지 않는다**(`recordAppEvent`가 실패를 삼킨다 — 2026-10-14 결정)
- 보관 1년 → §6 ③
- 기록은 화면이 생긴 뒤부터 쌓인다. 그전 지정 이력은 없다

### 4-5. 사후 잔재 점검 (운영자 UI 4시나리오)

| | 답 |
|---|---|
| 며칠 방치되면 저절로 만료되는가 | 해당 없음. 역할은 만료가 없다 |
| 대상 회원이 탈퇴하면 | 명단에서 빠진다. 기록의 `target_id`는 남고 화면엔 「탈퇴한 회원」으로 그린다. 바꾼 사람이 탈퇴하면 `app_events`가 그 사람 기록을 같이 지운다(`ON DELETE CASCADE`) — 총괄이 탈퇴할 일은 사실상 없다 |
| 잘못 눌렀을 때 되돌리는 길 | 같은 창에서 다시 바꾼다. 양방향이다 |
| 바뀐 회원에게 운영자 식별 정보가 보이나 | 아니다. 회원에게 알림을 보내지 않는다(조용히 바뀐다) |

## 5. DB 변경

**이 화면에는 DB 변경이 없다.** 역할 값은 지금 칸(`role`·`is_staff`)을 그대로 쓰고, 기록은 이미 있는 `app_events`에 남는다.

같이 언급했지만 **이 작업에 넣지 않는 DB 일** (따로 계획한다):

- §2-3 ② 운영진의 `profiles` 행 전체 읽기 — 칸 권한을 거두기 전에 본인 프로필·총괄 화면의 읽기 경로를 먼저 옮겨야 한다. SQL 초안은 그 계획에서 쓴다
- §2-3 ④ 배너 정책 — 배너 화면을 만들 때 `banners_admin_all`을 `is_editor_or_admin()`로 바꾼다
