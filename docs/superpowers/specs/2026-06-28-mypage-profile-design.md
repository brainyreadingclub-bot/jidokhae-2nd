# 마이페이지 — 프로필 보기/수정 설계서

> 2026-06-28 | Status: Draft (사용자 검토 대기)
> 배경 토론: `docs/expert-panel/2026-06-25-20-04-mypage-design.md`

## 1. 목적 (왜 만드는가)

회원이 가입 시 입력한 닉네임에 오타가 나도 **스스로 고칠 방법이 전혀 없다.** 현재는 가입 직후 `ProfileSetup` 전체화면에서 1회 입력 후 모든 정보가 고정되며, 운영진이 수동으로 DB를 고쳐야 한다.

이를 해결하기 위해 기존 `/my`("내 신청") 화면에 **내 정보(프로필) 보기/수정 섹션**을 추가한다. 닉네임 오타 수정이 핵심 동기이며, 전화·지역·이메일 자가 수정까지 함께 열어 운영 부담을 줄인다.

서비스 3원칙 부합: **보여야 한다**(내 정보를 볼 단일 지점 제공), **쉬워야 한다**(운영진 문의 없이 셀프 수정).

## 2. 범위 (Scope)

### 포함 (v1)
- `/my` 상단에 **프로필 섹션** 추가 — 새 페이지·새 BottomNav 탭 없음
- 프로필 **보기**(요약) → **[수정하기]** → 인라인 편집 → 저장
- 필드별 수정 정책:
  | 필드 | 정책 |
  |---|---|
  | 닉네임 | **가입 후 1회만** 변경. 단 `pending_transfer`(입금 대기) 보유 시 잠금 |
  | 전화번호 | 자유 수정 |
  | 지역 | 자유 수정 |
  | 이메일 | 자유 수정 |
  | 실명 | **읽기전용**(운영진 문의로 변경) |

### 제외 (v1에서 명시적으로 안 함)
- 참여 횟수·출석 통계, 뱃지 (스펙 Out-of-scope, 요청 누적 시 v2)
- 약관/환불/개인정보 링크 모으기 (이미 `/policy/*`에 있음)
- 로그아웃 이동 (이미 헤더에 있음)
- 본인인증 (비용·가입 마찰·개인정보 부담 대비 실익 없음 — 검토 후 제외)
- 회원 탈퇴 자동화

## 3. 결정 사항 (확정)

1. **실명 = 읽기전용.** 실명은 알림톡 인사말(`real_name || nickname`)과 관리자 회원 식별(`실명 (닉네임)`)에 쓰여 운영 식별자 역할을 하므로 본인 자유 수정에서 제외. 변경은 운영진 문의.
2. **닉네임 = 1회 제한 + 입금 대기 시 잠금.** 입금자명("M/D 닉네임")이 프로필에서 라이브로 읽히므로, `pending_transfer` 신청이 있는 동안 닉네임을 바꾸면 운영자 입금 대조가 깨진다. 해당 상태에서만 변경 차단(업계 사례: 레딧 "활동 시작 후 잠금"과 동일 발상).
3. **기존 250명 전원 = 1회 기회 부여.** 지금껏 수정 경로가 없었으므로 변경 횟수 0회. 마이그레이션 시 `nickname_changed_at`을 NULL로 둔다. (가입 시 최초 입력은 "변경"이 아님)
4. **1회 제한은 앱 레벨로만 강제.** DB CHECK 제약은 "1회"를 표현할 수 없으므로 두지 않는다. 서버가 `nickname_changed_at IS NULL` 확인.

## 4. 현재 상태 (코드 근거)

- `/my/page.tsx` → `MyRegistrationContent`만 렌더 (신청 목록). 프로필 보기/수정 UI 없음.
- `ProfileSetup.tsx` → 가입 직후 `fixed inset-0` 전체화면 게이트. 전 필드 required 강제. (인라인 부분 수정에 부적합 → 재사용 안 함, 단 RegionPicker/검증 로직은 참고)
- `/api/profile/setup/route.ts` → 온보딩용. 닉네임 **중복 체크는 있으나 1회 제한 로직 없음**. `profile_completed_at` 기록.
- `profiles` 스키마 → `nickname`(UNIQUE 부분 인덱스 `idx_profiles_nickname_unique`, 빈 문자열 제외), `real_name`, `phone`, `region`, `email`, `role`, `is_staff`, `welcomed_at`, `profile_completed_at`. **`nickname_changed_at` 없음 → 추가 필요.**
- `getProfile()`(`lib/profile.ts`) → 9개 컬럼 캐시. `nickname_changed_at` 추가 선택 필요.
- `BottomNav.tsx` → 탭 2개(모임 일정/내 신청), 로그아웃 없음.
- `notification.ts` → 알림톡 인사말 `real_name || nickname` (실명 우선).

## 5. 유저 흐름

```
/my 진입 (BottomNav "내 신청" 탭)
  │
  ▼
[내 정보] 섹션 (요약, 읽기 전용)
  닉네임 / 실명 / 전화 / 지역 / 이메일 표시
  │  [수정하기] 클릭
  ▼
인라인 편집 폼
  · 닉네임: 변경 가능하면 입력칸 / 이미 변경했거나 입금대기면 잠금 + 안내문구
  · 실명: 잠금(읽기전용) + "변경은 운영진 문의" 안내
  · 전화/지역/이메일: 자유 입력
  │  [저장] 클릭
  ▼
서버 검증 → 저장 → 화면 갱신 + "저장되었습니다" 피드백
  (실패 시 폼 유지 + 에러 메시지)
  │  [취소] → 입력 버리고 보기로 복귀
  ▼
[내 신청] 섹션 (기존 그대로, 하단)
```

### 닉네임 잠금 상태별 안내 문구
- 변경 가능: 일반 입력칸
- 이미 1회 변경함: 잠금 + "닉네임은 1회만 변경할 수 있어요"
- 입금 대기 중: 잠금 + "입금 확인이 끝난 뒤 변경할 수 있어요"

- 편집 폼은 [수정하기] 시 인라인 전개(slideDown). 온보딩 전체화면과 시각적으로 구분.

## 7. 구현 구성요소 (개요)

> 상세 단계는 별도 구현 계획(writing-plans)에서 작성.

1. **DB 마이그레이션** — `profiles.nickname_changed_at TIMESTAMPTZ DEFAULT NULL` 추가. 기존 회원 전원 NULL 유지(별도 UPDATE 불필요). SQL은 코드 확정 후 사용자에게 전달(수동 실행).
2. **신규 API 라우트** `/api/profile/update` (POST) — 부분 수정. 표준 포맷 `{status,message,data}`. 본인 프로필만. 실명은 무시(수정 불가). (기존 `/api/profile/setup`은 온보딩 전용으로 유지)
   - **닉네임 "변경"의 정의 (핵심)**: 제출된 닉네임이 **현재 닉네임과 실제로 다를 때만** 변경으로 취급. 같으면 닉네임/`nickname_changed_at` 일절 건드리지 않음(1회 기회 소비 금지). → 폼이 같은 값을 재전송해도 기회가 날아가지 않음.
   - 닉네임이 실제 변경된 경우에만: `nickname_changed_at IS NULL` 확인 + `pending_transfer` 미보유 확인(`registrations`에서 `user_id` + `status='pending_transfer'` 조회) + 중복 체크(자기 제외 `.neq('id', user.id)`, 빈 문자열 제외 `.neq('nickname','')`) → UPDATE에 **낙관적 가드** `.is('nickname_changed_at', null)` 포함 + 0행 시 동시 변경 충돌로 처리 → 성공 시 `nickname_changed_at = now()` 기록.
   - UNIQUE 인덱스 위반(에러코드 `23505`)은 500이 아니라 "이미 사용 중인 닉네임입니다"(409)로 변환.
   - **부분 업데이트**: 전화/지역/이메일 등 변경된 필드만 set. 닉네임 미변경 시 `nickname_changed_at`을 절대 덮어쓰지 않음.
   - 검증 재사용: real_name 무시 외 phone(`/^010\d{7,8}$/`)·region(`VALID_REGIONS`)·email 정규식은 setup과 동일 규칙.
3. **신규 컴포넌트** `ProfileEditor`(Client) — 보기→편집 토글, 필드별 잠금 처리. **RegionPicker 공용 추출 필수** — 현재 `ProfileSetup.tsx` 내부 로컬 함수(export 안 됨)이므로 `src/components/`로 분리해야 재사용 가능. 지역 칩은 실제 `VALID_REGIONS`(경주·포항 우선 + 11개) 사용 — 목업의 단순화된 칩셋 아님.
4. **`/my/page.tsx` 확장** — 프로필 섹션을 신청 목록 위에 배치. `getProfile()`에 `nickname_changed_at` 추가, `pending_transfer` 보유 여부 조회.
5. **`getProfile()` 갱신** — `nickname_changed_at` 컬럼 추가.

## 8. 작업/배포 방식

- 본 변경은 **회원 화면 변경**(250명 노출) → CLAUDE.md 배포 전략상 가장 신중한 묶음. **Vercel Preview로 검증 후 PR.**
- 로컬 제약: `(main)` 페이지는 Kakao OAuth 필요 → 로컬 검증 불가. Preview 배포로 확인.
- QA: `npm run prelaunch`(lint+tsc+test+build) 통과 후 PR.
- DB 마이그레이션 SQL은 **코드 확정 후** 사용자에게 전달(수동 실행). prod 적용 SQL은 git에 commit.

## 9. 리스크 / 엣지

- **race condition**(닉네임 동시 변경): 250명 셀프 수정 단건이라 실질 위험 낮음. 앱 레벨 `nickname_changed_at IS NULL` 확인 + UPDATE 낙관적 가드(0행 감지) + UNIQUE 인덱스가 최종 방어.
- **RLS 우회**: `/api/profile/update`는 service_role 사용 → 반드시 본인(`user.id`) 프로필만 수정하도록 검증.
- **닉네임 중복**: 기존 setup의 중복 체크 로직 재사용(자기 제외, 빈 문자열 제외). + UPDATE 단계 `23505` 위반도 사용자 친화 메시지로 변환.
- **실명 잠금 부작용**: 실명 오타 시 알림톡 인사말이 고정됨 → 운영진 수동 수정 경로 안내로 갈음(빈도 낮음 가정).
- **미완성 프로필 엣지**: `profile_completed_at IS NULL`(온보딩 미완) 회원은 홈의 `ProfileSetup` 게이트에서 먼저 막혀 `/my`에 정상 도달 못 함. ProfileEditor는 완성된 프로필을 전제. 만약을 위해 빈 값 안전 렌더만 보장.
- **알림 없음**: 프로필 수정은 알림톡/이력 트리거 없음(운영자/회원 모두 무알림). notification·analytics 호출 추가 금지.

## 10. 미해결 (구현 계획에서 확정)
- 저장 방식: 필드별 개별 저장 vs 한 번에 일괄 저장 → 일괄 저장 기본 가정(폼 단순).
- "내 정보"/"내 신청" 섹션 제목·구분선 스타일 디테일 → 디자인 단계.
