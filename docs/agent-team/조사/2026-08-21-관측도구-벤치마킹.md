# 관측 도구 벤치마킹 — 직접 만들기 전에

> 조사일: 2026-08-21 · 조사 방식: 공식 문서 + 웹 조사 (**설치·실행 안 함**)
> 목적: 부서 실행을 눈으로 보는 화면을 **직접 만들지, 갖다 쓸지** 판단한다.
> 표기 규칙: 외부 SaaS 화면은 **직접 본 적 없다.** 화면 관련 서술은 전부 「문서 기준」이다. 확인 못 한 것은 「확인 필요」로 남긴다.

---

## 요약 — 세 줄

1. **가장 큰 발견: 우리가 JSONL을 변환할 필요가 아마 없다.** Claude Code CLI 자체에 OpenTelemetry 계측이 **이미 내장**돼 있다. 환경변수 몇 개만 켜면 도구 호출·모델 요청·서브에이전트를 span으로 뱉는다. 코드를 한 줄도 안 건드린다. ([출처](https://code.claude.com/docs/en/monitoring-usage))
2. 그 span에는 `agent_id`, `parent_agent_id`, `session.id`가 붙는다. **"어느 부서가 언제 동시에 몇 개 돌았는가"에 딱 필요한 재료다.** 서브에이전트 span은 부모의 `claude_code.tool` span 밑에 자동으로 중첩된다. ([출처](https://code.claude.com/docs/en/agent-sdk/observability))
3. 따라서 후보는 "LLM 평가 플랫폼"이 아니라 **"OTLP를 받아 간트로 그려주는 것"**으로 좁혀진다. 1순위 **Jaeger**(도커 한 줄, 간트가 본업), 2순위 **Langfuse 셀프호스팅**(MIT, 타임라인+세션), 3순위 **Grafana otel-lgtm**(도커 한 줄, 나중에 확장용).

> ⚠️ 단, Claude Code의 **트레이스(span)는 베타**다. `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`이 필요하고 "span 이름과 속성은 릴리스마다 바뀔 수 있다"고 문서가 명시한다. 지표(metrics)와 이벤트(logs)는 베타가 아니다.

## 0. 전제가 하나 바뀐다

지시서의 전제는 이랬다 — "우리는 프레임워크가 없으니 SDK 계측을 못 쓴다. 대신 JSONL 전사가 있으니 그걸 변환해야 한다."

**앞부분은 맞고, 뒷부분은 틀렸을 수 있다.** 계측을 심을 곳이 없는 게 아니라, **이미 심어져 있다.** Claude Code CLI에 OTel 계측이 내장돼 있고, Agent SDK조차 자기 텔레메트리를 만들지 않고 "CLI 프로세스에 설정을 넘길 뿐"이라고 공식 문서가 말한다.

> "The CLI has OpenTelemetry instrumentation built in: it records spans around each model request and tool execution, emits metrics for token and cost counters, and emits structured log events for prompts and tool results. The SDK does not produce telemetry of its own."
> — [Observability with OpenTelemetry, Claude Code Docs](https://code.claude.com/docs/en/agent-sdk/observability)

### 켜는 방법 (문서 기준, 실행 안 해봄)

```
CLAUDE_CODE_ENABLE_TELEMETRY=1
CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1     # 트레이스는 베타라 필요
OTEL_TRACES_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp
OTEL_METRICS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf  # 또는 grpc
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

### 나오는 span 4종

| span 이름 | 무엇을 감싸는가 |
|---|---|
| `claude_code.interaction` | 프롬프트 1회 = 루트 span |
| `claude_code.llm_request` | 모델 호출 1회 (모델명·지연·토큰) |
| `claude_code.tool` | 도구 호출 1회. 밑에 `blocked_on_user`(권한 대기)와 `execution` 자식 span |
| `claude_code.hook` | 훅 실행 (추가 베타 플래그 필요) |

### 우리 질문에 직접 답하는 속성

- `agent_id`, `parent_agent_id` — **어느 부서인지, 누가 소환했는지**
- `session.id` — 한 세션 묶기
- `query_source` = `main` / `subagent` / `auxiliary` — **관리자 대 부서 구분**
- `agent.name` — 서브에이전트 종류. 단 **사용자 정의 에이전트는 `"custom"`으로 뭉개진다**(⚠️ 우리 부서는 전부 사용자 정의라 이름이 안 나올 가능성이 크다 → **확인 필요**)
- `tool_name`, `duration_ms`, `success`, `error_type` — 도구·소요시간·성공 여부
- `workflow.run_id`, `workflow.name`

그리고 결정적으로:

> "When the agent spawns a subagent through the Agent tool, the subagent's `llm_request` and `tool` spans nest under the parent agent's `claude_code.tool` span, so the full delegation chain appears as one trace."

**부서 소환 구조가 트레이스 하나로 자동 조립된다.** 간트로 그리면 병렬 실행이 그대로 겹친 막대로 보인다 — 이게 우리가 원한 그림이다.

### 그럼 JSONL은 필요 없나

**보완용으로는 여전히 필요하다.**

| 항목 | OTel로 되는가 |
|---|---|
| 병렬 실행 시각화 | ✅ 된다 (핵심 요구 충족) |
| 도구별 소요시간 | ✅ |
| 토큰/비용 | ✅ |
| **결과 판정** (부서가 뭘 내놨고 통과인가) | ❌ 안 된다. span은 구조만 담는다 |
| 프롬프트/응답 본문 | 옵트인 (`OTEL_LOG_USER_PROMPTS=1` 등) — 로컬이니 켜도 되지만 용량 주의 |
| 부서 이름 | ⚠️ `"custom"`으로 가려질 수 있음 |

즉 **판정·산출물은 우리 로그(`docs/agent-team/logs/`)가, 타이밍·병렬 구조는 OTel이** 맡는 분업이 자연스럽다.

## 2. "에이전트 실행을 레인/간트로 그리는 것"이 있는가

지시서의 3번 질문에 대한 직답.

### ✅ Jaeger — 문서상 가장 명확

> "각 색상 막대가 span을 나타내며, 트레이스 내 다른 span 대비 지속시간과 타이밍을 보여준다... 좌측은 호출 계층, 우측은 각 span의 타이밍을 시각화한 **간트 차트**."
> "**어떤 작업이 순차로 일어났고 어떤 것이 병렬로 일어났는지 볼 수 있다.**"
> — [Better Stack: Jaeger 가이드](https://betterstack.com/community/guides/observability/jaeger-guide/), [Logit.io: Viewing Spans & Traces in Jaeger](https://logit.io/docs/application-performance-monitoring/jaeger/viewing-spans-and-traces/)

우리 요구("어느 부서가 언제 동시에 몇 개 돌았는가")를 **정확히** 그리는 화면이다. 서브에이전트 span이 부모 `claude_code.tool` 밑에 중첩되므로, 부서 3개를 동시에 소환하면 간트에서 **세 막대가 시간축에서 겹쳐 보인다.**

**Anthropic 공식 문서도 로컬 검증용으로 Jaeger를 지목한다:**
> "To inspect telemetry locally, point `OTEL_EXPORTER_OTLP_ENDPOINT` at a local collector or an **all-in-one Jaeger container** instead."
> — [Claude Code Docs](https://code.claude.com/docs/en/agent-sdk/observability)

### ✅ Langfuse — 타임라인이 "병렬성 시각화"를 명시 목적으로 함

> "트레이스 타임라인 차트는 에이전트 흐름을 시각화하고, **지연 병목 식별·병렬성 시각화(visualize parallelism)**·깊게 중첩된 체인의 다단계 추론 이해를 돕는다."
> — [Langfuse Changelog: Trace Timeline View](https://langfuse.com/changelog/2024-06-12-timeline-view)

⚠️ 다만 이 체인지로그 페이지에는 **실제 화면 캡처 설명이 없다.** 막대가 어떻게 생겼는지, 레인이 나뉘는지는 **문서로 확인 못 했다 — 확인 필요.**

⚠️ 그리고 **Agent Graph(그래프 뷰)는 우리 span으로는 안 뜰 가능성이 크다.** Langfuse 문서:
> 그래프는 "`span`·`event`·`generation` 이외의 observation type"이 있을 때 뜬다 → **일반 OTel span만으로는 그래프가 렌더되지 않는다.**
> — [Langfuse: Agent Graphs](https://langfuse.com/docs/observability/features/agent-graphs)
>
> 트리 뷰와 타임라인 뷰는 정상 동작할 것으로 보이나, **이것도 실측 전엔 단정 금지.**

### ✅ AgentOps — Session Waterfall

> "좌측에 모든 LLM 호출·Action 이벤트·Tool 호출·에러의 시간 시각화, 우측에 선택한 이벤트의 상세."
> — [AgentOps Docs](https://docs.agentops.ai/v2/introduction)

화면 형태는 우리 요구에 맞지만, **Claude Code의 OTLP를 그대로 받는 공식 경로를 문서에서 확인하지 못했다.** 파이썬 SDK 중심 문서다.

### 🟡 Honeycomb — Agent Timeline

> "멀티 에이전트·멀티 트레이스 워크플로를 **하나의 일관된 뷰**로 렌더하여, 모든 LLM 호출·도구 호출·**에이전트 핸드오프**·다운스트림 영향을 실시간으로 연결한다."
> — [Honeycomb 블로그](https://www.honeycomb.io/blog/honeycomb-launches-agent-observability-full-visibility-agentic-workflows)

개념상 가장 우리 요구에 가까운 이름이지만 — **레인인지 간트인지 문서에 없다(확인 필요)**, **셀프호스팅이 없다(클라우드 전용)**, 2026-06 기준 Early Access였다.

### ❌ LangGraph Studio — 우리 상황에선 탈락

그래프를 그리긴 하지만 "**LangGraph Server API 프로토콜을 구현한**" 대상만 본다. 우리는 LangGraph를 안 쓴다. 게다가 데스크톱 앱은 macOS 전용이고, 웹 버전도 로컬 LangGraph 서버를 요구한다. ([출처](https://www.langchain.com/blog/langgraph-studio-the-first-agent-ide), [DeepWiki](https://deepwiki.com/langchain-ai/langgraph-studio/5.2-graph-visualization))

## 3. OpenTelemetry GenAI 시맨틱 컨벤션 — 지금 어디까지 왔나

### 상태: **전부 "Development"(구 experimental). Stable 없음.**

- 2026-06-12, semantic-conventions v1.42.0에서 GenAI 규약이 **본체 저장소에서 분리**되어 [open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai) 전용 저장소로 이동했다. 이건 **졸업이 아니라 릴리스 주기 분리**다.
- 해당 저장소의 `gen-ai-agent-spans.md` 상단은 여전히 **"Status: Development"**. ([원문 확인](https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-agent-spans.md))
- 에이전트 span은 이미 정의돼 있다: `create_agent`, `invoke_agent`, `execute_tool`. 속성: `gen_ai.operation.name`, `gen_ai.agent.name`, `gen_ai.agent.id`, `gen_ai.conversation.id` 등.
- 2차 자료 요약: "2026년 7월 중순 기준 모든 `gen_ai.*` 속성·span·metric·event가 Development 배지를 달고 있고 Stable은 하나도 없다." ([DEV Community 분석](https://dev.to/azena-ai/opentelemetrys-genai-semantic-conventions-are-not-stable-yet-heres-what-actually-shipped-in-2026-3mke))

### 우리 판단

**"JSONL → OTLP span 변환"은 현실적이긴 하나, 지금은 안 해도 된다.**

이유 셋:

1. **CLI가 이미 span을 뱉는다.** 변환기를 만들 이유가 사라졌다. 만들면 유지보수 대상이 하나 늘 뿐이다.
2. **표준이 아직 안 굳었다.** 지금 `gen_ai.*`에 정확히 맞춰 변환기를 짜도 규약이 바뀌면 다시 고쳐야 한다.
3. **Claude Code의 span도 `gen_ai.*`가 아니라 `claude_code.*` 자체 네이밍이다.** 즉 GenAI 규약에 특화된 화면(Honeycomb의 `gen_ai.*` 일급 취급, Phoenix의 OpenInference 렌더)의 이점을 온전히 못 받을 수 있다 — **확인 필요.** 반대로 **Jaeger처럼 규약을 안 따지는 범용 간트는 이 문제가 없다.** 이것도 Jaeger를 1순위로 미는 이유다.

**JSONL 변환이 여전히 유효한 경우**: 트레이스 베타를 못 켜거나(회사 정책/버전), **이미 지나간 과거 세션**을 되돌아봐야 할 때. 과거 세션은 OTel로 소급할 수 없고 JSONL에만 남아 있다.

## 5. 직접 만들기 vs 갖다 쓰기

### 갖다 쓸 때 얻는 것

| | |
|---|---|
| **완성된 간트** | 겹침·중첩·확대축소·span 클릭 상세 — 직접 만들면 최소 수백 줄. Jaeger는 0줄 |
| **계측 비용 0** | CLI가 이미 뱉는다. 파서를 짤 필요가 없다 |
| **JSONL 포맷 변경 리스크 회피** | Claude Code 전사 포맷이 바뀌면 우리 파서가 조용히 깨진다. OTLP는 표준이라 안 깨진다 |
| **덤** | 토큰·비용·에러율·MCP 연결 실패까지 같이 온다. 안 만들었는데 생긴다 |

### 갖다 쓸 때 잃는 것

| | 얼마나 아픈가 |
|---|---|
| **"부서 이름"이 안 보일 수 있다** | 🔴 **가장 아프다.** `agent.name`이 사용자 정의는 `"custom"`으로 뭉개진다는 문서 서술이 있다. 그러면 간트에 "부서 A / 부서 B"가 아니라 "custom / custom"이 뜬다. 우회는 가능해 보인다(`OTEL_LOG_TOOL_DETAILS=1`로 Agent 도구 파라미터에서 `subagent_type`을 읽거나, `OTEL_RESOURCE_ATTRIBUTES`로 태깅) — **확인 필요** |
| **"결과 판정"은 안 들어온다** | 🟡 애초에 span의 일이 아니다. 우리 로그가 맡으면 된다 |
| **트레이스가 베타** | 🟡 span 이름·속성이 릴리스마다 바뀔 수 있다고 문서가 명시 |
| **과거 세션 소급 불가** | 🟡 오늘 켜면 오늘부터. 지난 세션은 JSONL에만 있다 |
| **도커가 하나 더 뜬다** | 🟢 비전공자 로컬에 상시 컨테이너. Jaeger는 가볍지만 Langfuse는 무겁다 |
| **우리 어휘가 아니다** | 🟡 화면에 "부서"·"소환"·"판정"이 아니라 "span"·"trace"·"service"가 뜬다 |

### 판단

**직접 만드는 것을 지금 시작하지 말 것을 권한다.** 순서는 이렇게:

1. **먼저 재료가 실제로 나오는지 확인한다.** Jaeger 도커 한 줄 + 환경변수 6개. 부서를 3개 동시에 소환해 보고 **간트에 막대 3개가 겹쳐 보이는지** 눈으로 본다. 여기까지가 반나절이 안 걸린다.
2. **막대가 겹쳐 보이면 → 우리가 만들 것은 "뷰어"가 아니라 "이름표"다.** 부서 이름이 span에 제대로 실리게 태깅하는 작업만 하면 된다. 화면은 Jaeger가 준다.
3. **부서 이름이 끝내 안 실리거나, 판정까지 한 화면에서 봐야 하면** → 그때 직접 만드는 것을 검토한다. 그때도 입력은 JSONL이 아니라 **우리 로그 + OTel** 조합이 낫다.

**직접 만들기의 진짜 비용은 만드는 게 아니라 유지하는 것이다.** Claude Code는 지금도 매주 바뀐다. JSONL 포맷을 따라가는 파서는 조용히 깨지고, 깨진 걸 아무도 모른 채 화면만 비어 있게 된다. OTLP는 표준이라 그 위험이 훨씬 작다.

## 6. 확인 필요 목록 (직접 실행해봐야 아는 것)

이 조사는 **설치·실행 없이** 문서만 본 것이다. 아래는 문서로 답이 안 나온 것들이다.

| # | 확인할 것 | 왜 중요한가 |
|---|---|---|
| 1 | **사용자 정의 서브에이전트 이름이 span에 실리는가.** `agent.name`이 `"custom"`으로 뭉개지는지, `OTEL_LOG_TOOL_DETAILS=1`을 켜면 `subagent_type`이 보이는지 | 🔴 **최우선.** 이게 안 되면 간트가 익명 막대 더미가 된다 |
| 2 | **대화형(interactive) CLI에서도 트레이스가 나오는가.** 공식 문서는 `TRACEPARENT` 관련해 "대화형 CLI 세션은 인바운드 `TRACEPARENT`를 무시한다"고만 말한다 — 자체 span을 안 뱉는다는 말은 아니지만 확인 필요 | 🔴 우리는 `claude -p`가 아니라 대화형으로 쓴다 |
| 3 | Windows(비-WSL) 환경에서 환경변수 설정 위치. 프로젝트 `.claude/settings.json`의 `env` 블록으로 되는지 | 🟡 비전공자 셋업 난이도 |
| 4 | Jaeger 간트에서 부서 3개 동시 실행이 **실제로 겹쳐 보이는지** | 🔴 핵심 요구의 실증 |
| 5 | Langfuse OTLP 엔드포인트에 Claude Code CLI를 직접 꽂았을 때 화면 품질 | 🟡 2순위 후보의 실현성 |
| 6 | Phoenix가 `claude_code.*` span(OpenInference 속성 없음)을 어떻게 렌더하는지 | 🟡 2차 후보 판단 |
| 7 | 트레이스 베타 플래그가 요금제·조직 정책에 걸리는지 | 🟡 |
| 8 | 로컬 저장 용량 — 세션 하나가 span 몇 개인지 | 🟢 Jaeger 기본 인메모리라 오래 못 쌓음 |
| 9 | Honeycomb Agent Timeline의 실제 화면 형태(레인인가 간트인가) 및 GA 여부 | 🟢 클라우드 전용이라 어차피 후순위 |
| 10 | AgentOps에 Claude Code OTLP를 직접 보내는 공식 경로 존재 여부 | 🟢 |
