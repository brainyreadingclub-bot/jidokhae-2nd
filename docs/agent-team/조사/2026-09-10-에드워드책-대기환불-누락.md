### 회원이 원래 어떻게 됐어야 하나

🟩 결제 시각(16:07:33)에 이 모임은 **정확히 만석**이었다 — 정원 12에 `confirmed` 9 + `pending_transfer` 3 = 12, 그 위에 대기 1명(b06d4a14, 8/31부터). 따라서 `confirm_registration()` RPC는 **`waitlisted`를 반환했을 것**이고, 대표님이 들으신 *"대기신청을 했다"*와 맞는다.

대기 줄에서는 b06d4a14가 앞이므로 9/7 22:55 승격은 그대로 b06d4a14가 받는 것이 맞다. 즉 **에드워드 책님은 끝까지 미승격 대기로 남았을 것**이고, **09-08 18:30 크론이 12,000 전액을 자동 환불**했어야 한다.

**잃은 것 = 12,000 전액 + 대기 확인 알림톡 + 앱에서 자기 신청을 볼 권리.**

## 3. 원인 — 파일:줄

### 3-1. 🔴 근본 원인: PortOne 웹훅의 prefix 조회가 **항상 실패**한다

`jidokhae-web/src/app/api/webhooks/portone/route.ts:67-83`

```ts
const [{ data: meetings }, { data: profiles }] = await Promise.all([
  supabase.from('meetings').select('id').like('id', `${meetingId8}%`).limit(1),   // ← 71
  supabase.from('profiles').select('id').like('id', `${userId8}%`).limit(1),      // ← 76
])

if (!meetings?.length || !profiles?.length) {
  console.error(`[portone-webhook] ID 조회 실패: ${paymentId}`)
  return NextResponse.json({ status: 'ignored' }, { status: 200 })   // ← 82
}
```

`meetings.id` · `profiles.id`는 **`uuid` 타입**이다. Postgres에는 `uuid LIKE text` 연산자가 없다.

🟩 **prod에서 이 두 줄을 그대로 재현했다:**

```
{"code":"42883","message":"operator does not exist: uuid ~~ unknown",
 "hint":"No operator matches the given name and argument types..."}
```

`error`는 구조분해에서 버려지고 `data`는 `null` → `!meetings?.length`가 참 → **무조건 `ignored`로 빠져나간다.** `processPaymentConfirmation()`은 **한 번도 호출되지 않는다.**

🟩 **PortOne에 남은 응답 본문이 이를 그대로 증명한다** — 이번 건뿐 아니라 **정상 처리된 다른 건**(`jdkh-20425c26-05cf4950-...`, 08-27)의 `Transaction.Paid` 웹훅 응답도 똑같이 `{"status":"ignored"}`였다. 그 건은 **webhook이 아니라 redirect가 6초 뒤 신청을 만들어서** 살아난 것이다.

🟩 **언제부터인가: 처음부터다.** `git log -S"like('id'"` → `0c68df7`(M4 토스 연동 최초 구현)에 이미 있었고 `0cf1a4f`(PortOne 이관, PR #28)가 그대로 옮겼다. **웹훅 백업 경로는 단 한 번도 작동한 적이 없다.**

> 같은 버그가 레거시 `src/app/api/webhooks/tosspayments/route.ts:76,81`에도 있으나 그 라우트는 미사용이다.

### 3-2. redirect가 왜 끊겼는가

⬜ **단정할 수 없다.** Vercel 런타임 로그를 이 세션에서 볼 수 없다(9/9 점검 §4-4와 같은 제약).

🟩 확실한 것: `PaymentRedirectClient.tsx:55-63`이 `/api/registrations/confirm`을 부르는데, **그 호출이 성공했다면 행이 생겼거나(모든 정상 경로) 결제가 자동취소됐어야 한다**(`payment.ts`의 `safeCancel` 경로 8곳). **행도 없고 취소도 없다** → 확정 로직이 실행 자체를 안 했다는 뜻이다.

🟨 가장 그럴듯한 경로 (근거는 있으나 실측 아님):
1. **카카오톡 인앱 브라우저 ↔ 카카오페이 앱 전환 후 복귀 실패.** `origin.userAgent`가 `KAKAOTALK ... (INAPP)`이다. 이 경로에서 돌아오지 못하면 redirect URL이 열리지 않는다.
2. **복귀는 했으나 세션 쿠키가 없어 미들웨어가 `/auth/login`으로 보냄.** `/meetings/[id]/payment-redirect`는 `(main)` 그룹이라 인증 필수다(`middleware.ts`). 이 경우 `paymentId`가 붙은 URL이 **그대로 버려진다.**

어느 쪽이든 **재시도 장치가 없다** — `PaymentRedirectClient`는 실패 시 2초 뒤 모임 상세로 보낼 뿐이고, 그 뒤 `paymentId`를 다시 확인하는 코드는 어디에도 없다.

## 5. 확인 못 한 것 (모르는 것은 모른다)

- ⬜ **redirect가 실제로 어디서 끊겼는지.** Vercel 런타임 로그 접근 경로가 없다. `vercel logs`는 실시간 스트리밍만 지원한다
- ⬜ **회원이 결제 후 어떤 화면을 봤는지.** "결제를 확인하고 있습니다" 스피너에서 멈췄는지, 로그인 화면으로 튕겼는지, 카카오페이에서 아예 못 돌아왔는지 구분 불가. **대표님이 회원께 여쭤보면 3-2의 두 갈래가 갈린다**
- ⬜ **웹훅이 고장 난 채로 지나간 다른 순간이 있었는지.** 지금은 결과(고아 결제 1건)만 셀 수 있고, "redirect가 아슬아슬하게 살려낸 횟수"는 셀 방법이 없다

## 7. 재현 방법

- **PortOne**: `.env.local`의 `PORTONE_API_SECRET`으로 `@portone/server-sdk` → `payment.getPayment({ paymentId })` 및 `payment.getPayments({ filter: { from, until, timestampType: 'CREATED_AT' } })`. **조회 API만 사용**
- **prod DB**: `SUPABASE_SERVICE_ROLE_KEY` + `@supabase/supabase-js`, **`.select()`만.** 임시 스크립트는 `jidokhae-web/` 루트에 두고(ESM 해석) 실행 후 삭제
- **웹훅 버그 재현**: `supabase.from('meetings').select('id').like('id', '20425c26%')` → `42883 operator does not exist: uuid ~~ unknown`
- **웹훅 응답 확인**: `getPayment()` 응답의 `webhooks[]` 배열에 우리 서버의 **요청·응답 본문이 그대로 보관**돼 있다. `paymentStatus: "PAID"` 항목의 `response.body`를 볼 것
- **코드 근거**: `src/app/api/webhooks/portone/route.ts:67-83` · `src/lib/payment.ts:31-179` · `src/components/meetings/PaymentRedirectClient.tsx:55-110` · `src/app/api/cron/waitlist-refund/route.ts:23-28`
