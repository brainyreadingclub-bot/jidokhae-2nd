## 1. 무슨 일이 일어나는가

```
회원 결제 완료
  → 브라우저가 confirm을 두 번 보냄
  → 1번째: 신청 행 생성 ✅
  → 2번째: RPC가 "already_registered" 반환   ← 방금 1번째가 만든 행을 본 것
  → payment.ts:158  safeCancel('중복 신청으로 인한 환불')
  → 돈은 나가고, 신청 행은 남는다
```

**왜 서버가 못 막나** — 멱등성 체크(`payment.ts:38-50`)는 `payment_id`로 보지만 **락 밖**이다. 두 요청이 거의 동시에 통과한 뒤 RPC의 `FOR UPDATE`(meetings 행)에서 줄을 서고, **두 번째가 중복으로 판정**된다. 락이 race를 막은 게 아니라 **순차적 중복으로 바꿔놓는다.**

**호출 주체는 브라우저다** — `payment_failures.source = 'confirm'`(웹훅 아님). 피해자 모두 카카오톡 인앱 브라우저. 결제 앱 복귀 시 화면이 두 번 뜨는 것으로 보인다. `PaymentRedirectClient.tsx:27`의 `processedRef` 가드는 **재마운트되면 초기화**되므로 클라이언트 가드는 믿을 수 없다.

## 5. 해야 할 일 — 세 갈래

### A. 피 멈추기 (가장 급함, 대표님 판단 불필요)

`payment.ts`의 `already_registered` 분기에서 **환불 전에 한 번 더 확인**한다 —
*"이 `payment_id`로 만들어진 행이 이미 있는가?"* 있으면 **내 결제이므로 환불하지 않고 성공으로 응답**한다. 없을 때만 환불한다(진짜 중복).

- 지금 Layer 1 체크를 **RPC 호출 뒤에 한 번 더** 두는 것과 같다
- 🔴 **`safeCancel` 호출을 지우는 것이 아니다.** 진짜 중복(남의 결제로 만들어진 신청)은 여전히 환불해야 한다
- 담당 개발·운영 · 테스트 필수(동시 호출 재현)

### B. 6명 처리 — ✅ **결정됨 (대표님, 2026-10-06)**

> *"6명은 오류였으니까 그냥 넘어가자."*

**재결제를 요청하지 않는다. 신청을 그대로 두고 72,000원을 포기한다.**

- 회원에게 **연락하지 않는다.** 우리 잘못이고, 알리면 회원이 번거로워진다
- **혁오님**(제보자)께는 **대표님이 커피 기프티콘을 직접 보내신다.** 🔴 **Claude가 할 일이 아니다**
- ⚠️ **두팔님(대기자)은 10/6 18:30 크론이 자동 정리한다** — 이미 CANCELLED인 결제는 크론이 `catch`에서 넘기므로(`waitlist-refund/route.ts:69-77`) **이중 환불이 나지 않는다.** 상태만 `waitlist_refunded`로 맞춰진다
- ⚠️ **혁오·현디님을 취소 처리하면 안 된다** — 자리가 비는 순간 대기자가 **돈 없이 승격**된다

### C. 장부 맞추기 — ✅ **완료 (2026-10-06 19:5x, prod)**

**두팔님은 손대지 않았다** — 10/6 18:30 크론이 `waitlist_refunded` + `refunded_amount=12000`으로 **스스로 정리했다**(예측대로 이중 환불 없음). 남은 **5건**만 처리.

```sql
-- ① 매출 정정: 받은 돈이 0원인 것이 사실이다
update registrations set paid_amount = 0
where payment_id in (…5건) and status='confirmed' and paid_amount=12000;

-- ② 대사 침묵: 돈이 실제로 회원에게 돌아간 사실을 적는다
update registrations set refunded_amount = 12000
where payment_id in (…5건) and status='confirmed' and paid_amount=0 and refunded_amount is null;
```

**왜 이 모양인가** — `paid_amount=0 · refunded_amount=12000`이 얼핏 모순으로 보이지만, 흐름은 *"12,000 받았다가 12,000 돌려줘 최종 0원"*이고 두 칸 다 사실이다.
- **①이 없으면** 매출에 60,000원이 과다 계상된다. 매출 집계는 `status='confirmed'`의 `paid_amount` 합이라 **정상 취소와 달리 자동으로 빠지지 않는다**(취소 건은 `status='cancelled'`가 되어 빠진다)
- **②가 없으면** 대사 도구가 영원히 5건을 띄운다 → **다음 사람이 「환불 안 됐네」로 읽고 또 돈을 보낸다.** 에드워드 책님 건이 정확히 그 위험이었다

**부작용 없음을 확인하고 실행했다**
- 환불 집계(`dashboard.ts:48`)는 `status='cancelled'`만 센다 → 이 5건은 안 잡힌다
- 환불 대기 목록(`settlement.ts:187-189`)도 `cancelled` 조건 → 안 잡힌다
- 회원이 취소해도 `paid_amount=0` → 환불액 0 → `cancel.ts:85`의 `refundAmount > 0` 조건에서 걸려 **`cancelPayment`를 아예 안 부른다**
- 🔴 **신청 행은 그대로 둔다** — `cancelled`로 바꾸면 자리가 비어 **대기자가 돈 없이 승격**된다

**검증** — 대사 재실행 결과 세 검사 **전부 0건**(고아 결제 · 미환불 · 금액 불일치).

**버린 안**
- `settlement_excluded` 플래그 — `pending_transfer` 전용이라 `confirmed`에는 안 먹는다
- 매출 집계에서 `refunded_amount`를 차감하도록 코드 수정 — 정석이지만 **다른 모든 건의 숫자가 같이 움직인다.** 이번 범위를 넘는다

## 6. 재발 방지로 남길 것

- **대사 도구가 금액만 비교하면 가려지는 건이 있다** — 릴라님처럼 뒤에 본인이 취소하면 금액이 맞아떨어져 안 잡힌다. **취소 사유로도 훑어야 전수가 된다**
- **클라이언트 가드(`processedRef`)는 재마운트에 무력하다.** 돈이 걸린 경로는 **서버가 막아야 한다**
- `payment_failures`가 이번 규명의 결정적 증거였다(`source`로 웹훅/브라우저를 갈랐다). **#67이 없었으면 호출 주체를 못 밝혔다**
