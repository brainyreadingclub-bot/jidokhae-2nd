# 부서 공통규약

> **모든 부서가 작업을 시작하기 전에 이 파일을 읽는다.**
> 각 부서 정의(`.claude/agents/*.md`)는 내용을 복붙하지 않고 이 파일을 가리킨다.
> 복붙하면 한쪽만 갱신되어 어긋난다 — 이 프로젝트가 이미 겪은 사고다.
>
> 최종 개정: 2026-08-18

## 0. 시작 전에 반드시 읽을 것

순서대로 읽는다. **훅이 자동으로 넣어줄 것이라고 기대하지 마라** — 팀원 세션에 훅이 도는지 확인되지 않았다. 직접 읽는다.

| 순서 | 파일 | 무엇이 있나 |
|---|---|---|
| 1 | `검토문서/DECISIONS.md` | **이미 정해진 것.** 여기 있는 사안을 "새로 정해야 할 일"로 올리지 마라 |
| 2 | `CLAUDE.md` | 비즈니스 규칙, 아키텍처, 코딩 컨벤션 |
| 3 | `verification-squad/profiles/jidokhae-profile.md` | 기술 스택 + **의도된 설계 / 알려진 미해결 문제** |
| 4 | 이 파일 | 공통규약 |

3번의 마지막 두 절이 특히 중요하다. **거기 적힌 것은 일부러 그렇게 만들었거나 이미 인지된 것이다.**

## 1. 의도 확인 규칙 — 가장 자주 어기는 규칙

"문제다"라고 말하기 전에 **왜 그렇게 되어 있는지** 먼저 찾는다.

| 상황 | 행동 |
|---|---|
| 의도를 못 찾음 | **"의도 불명"**으로 표시한다. "문제"로 단정하지 않는다 |
| 의도가 있고 지금도 유효 | 지적하지 않는다 |
| 의도는 있으나 **당시 전제가 지금과 다름** | ✅ **말한다.** 단 "틀렸다"가 아니라 — *"이건 ○○ 때문에 이렇게 정했는데, 그 전제가 지금은 △△로 바뀌었다"* |

### 왜 이 규칙이 있는가

전문가 패널을 돌렸을 때, **서비스 맥락을 모른 채 강하게 주장해서** 의도적으로 그렇게 둔 설계를 결함이라고 지적한 일이 있었다. 예를 들어 `pending_transfer`를 `confirmed`처럼 보여주는 건 버그처럼 보이지만, 운영자가 입금 확인을 월말에 몰아 처리하기 때문에 **회원을 불안하게 하지 않으려고 일부러** 그렇게 둔 것이다.

맥락 없이 보면 100% 지적당한다. 그리고 그런 보고서는 신뢰를 잃는다.

## 2. 소통 규약

에이전트 팀에는 **전체 공지 기능이 없다.** 여러 명에게 보내려면 한 명씩 보내야 한다. 그래서 라인을 정한다.

| 규칙 | 내용 |
|---|---|
| **산출물은 파일로, 메시지는 포인터로** | *"`경로`에 뒀다, ○○를 봐 달라"*만 보낸다. 내용을 메시지에 담으면 컨텍스트만 먹고 기록도 안 남는다 |
| **직접 소통은 의존 쌍만** | 제품기획↔디자인 · 개발운영↔품질 · 데이터↔제품기획 · 고객VOC↔제품기획. **그 외는 관리자를 거친다** |
| **막히면 즉시 관리자에게** | 팀원끼리 해결하려고 시간을 태우지 않는다 |
| **공지는 관리자만** | 전체에 알릴 게 있으면 관리자가 각자에게 보낸다 |
| **모든 메시지는 로그에 한 줄** | 누가·누구에게·무엇을. **메일함은 세션이 끝나면 사라진다** |

## 3. 파일 소유권 — 겹치면 덮어쓴다

두 부서가 같은 파일을 쓰면 **한쪽이 조용히 사라진다.** 각 부서는 자기 경로에만 쓴다.

| 부서 | 쓸 수 있는 경로 |
|---|---|
| 문서총괄 | `docs/agent-team/문서지도/**` · `docs/agent-team/logs/문서총괄.md` |
| 제품기획 | `검토문서/**` · `roadmap/**` · `검토문서/DECISIONS.md` · 자기 로그 |
| 디자인 | `docs/superpowers/mockups/**` · 자기 로그 |
| 개발·운영 | `jidokhae-web/**` · `supabase/**` · 자기 로그 |
| 품질 | `verification-squad/reports/**` · 자기 로그 |
| 데이터 | `docs/agent-team/데이터/**` · 자기 로그 |
| 성장 | `docs/agent-team/성장/**` · 자기 로그 |
| 고객VOC | `docs/agent-team/voc/**` · 자기 로그 |

> 🔴 **`jidokhae-web/` 아래 코드를 고치는 부서는 개발·운영 하나뿐이다.** 다른 부서가 결함을 찾으면 **보고만 하고 고치지 않는다.** 특히 품질은 도구 단위로 수정이 막혀 있다 — 찾는 사람과 고치는 사람을 분리해야 "고쳤다고 말하고 안 고친" 일이 안 생긴다.

> 🔴 **옵시디언 보관소(`C:\Users\ytyt8\Documents\Sync`)는 읽기 전용이다.** 설정에서 쓰기가 차단돼 있다. 기존 노트 1,295개는 개인 지식 체계이며 이 팀의 소유가 아니다.

## 4. 로그 — 쓰지 않으면 미완료다

위치: `docs/agent-team/logs/<부서>.md` — **덧붙여 쓰고, 최신이 맨 위**

```markdown
## 2026-08-14 — <한 줄 제목>

**한 일**
- (무엇을 했는가)

**왜 그렇게 했는가**
- (판단 근거. 대안이 있었으면 왜 그걸 안 골랐는지)

**안 한 것과 이유**
- (범위 밖이라서 / 막혀서 / 근거가 부족해서)

**주고받은 메시지**
- → 품질: `경로`에 초안 뒀음, 위험 3종 봐달라고 요청

**다음**
- (이어서 할 일. 없으면 "없음")

**관리자 판정**
- (관리자가 채움: 통과/반려 + 근거 + 실제로 연 파일)
```

> 🔴 **세션이 끝나면 팀원도 메일함도 사라진다. 파일에 없는 것은 존재하지 않은 것이다.**
> 로그를 쓰지 않고 유휴 상태로 들어가면 되돌려보내진다.

기존 cockpit 기록(`--did`/`--next`)과는 역할이 다르다 — cockpit은 **세션 단위 상태**, 이 로그는 **부서 단위 작업 기록**이다. 둘을 겹쳐 쓰지 않는다.

## 5. 자가 점검 — 관리자에게 올리기 전에 스스로 채점

**5개 중 4개 이상**을 충족하지 못하면 올리지 않는다. 이 관문이 없으면 관리자가 반려만 하다 끝난다.

| # | 기준 | 확인 질문 |
|---|---|---|
| 1 | **근거** | 주장마다 파일:라인 또는 문서 경로가 붙어 있는가? |
| 2 | **의도 확인** | "문제"라고 쓴 것마다 §1의 3단계를 거쳤는가? |
| 3 | **범위** | 요청받은 것만 했는가? 곁다리로 다른 걸 고치지 않았는가? |
| 4 | **불확실성 표시** | 확인 못 한 것을 "확인 필요"로 남겼는가? 추측을 사실처럼 쓰지 않았는가? |
| 5 | **재현 가능** | 다른 사람이 이 로그만 보고 같은 결론에 도달할 수 있는가? |

## 6. 절대 하지 말 것

| 금지 | 왜 |
|---|---|
| **검증 없이 "완료"라고 말하기** | 명령을 실제로 돌리고 출력을 본 뒤에 말한다 |
| **"아마 될 것"으로 넘어가기** | 확인 못 했으면 "확인 필요"라고 쓴다 |
| 다른 부서의 파일 수정 | §3 위반. 조용히 덮어쓴다 |
| 옵시디언 기존 노트 수정·이동·삭제 | 개인 지식 체계다. 읽기만 한다 |
| `npx tsx scripts/*` 실행 | **실제로 전 회원에게 알림톡이 나가거나** 결제를 건드릴 수 있다. 관리자 승인 없이 금지 |
| MCP로 prod SQL 쓰기 | MCP는 **이제 진짜 prod에 연결돼 있다.** 읽기 조회만 자유롭게 |
| Preview에서 카드결제 테스트 | Preview는 **prod Supabase에 그대로 붙는다.** 테스트 모임을 만들었으면 즉시 삭제 |
| 회원 노출 UI를 시안 없이 구현 | 회원 전체가 본다. 시안 → 합의 → 구현 순서다 |
| 금액에 `원`·`₩` 붙이기 | 숫자만 쓴다 (`"10,000"`). 가격 프레이밍 |
| 새 결정을 `DECISIONS.md`에 안 적기 | **그 세션 안에** 적는다. 다음에 하겠다고 미루면 안 한다 |
| **변하는 값을 문서에 숫자로 박기** | 회원 수, 신청 건수, 매출처럼 계속 변하는 값은 적는 순간 틀리기 시작한다. 아래 §7 참조 |

## 7. 변하는 값은 문서에 적지 않는다

문서에 `회원 250명`이라고 적으면, 그 문서는 **적은 그 순간부터 틀려지기 시작한다.** 회원은 매주 들어오고 나간다. 반년 뒤 그 문장을 읽는 사람은 250명이 지금 값인지 옛날 값인지 알 방법이 없다.

| 대신 이렇게 | 예 |
|---|---|
| 세는 방법을 적는다 | ~~회원 250명~~ → *"회원 수는 `profiles` 테이블을 센다"* |
| 규모가 아니라 **성질**을 적는다 | ~~250명이 본다~~ → *"회원 전체가 본다"* |
| 굳이 숫자가 필요하면 **잰 날짜를 함께** | *"2026-08-17 기준 17개"* |

**예외 — 일부러 박는 숫자도 있다.** 검증 프로필 맨 위의 "테이블 17개"는 낡음을 감지하려고 일부러 고정한 값이다. 어긋나면 "문서가 낡았다"는 신호가 된다. 그런 경우에는 **왜 고정했는지**를 함께 적는다.

## 8. 기준 문서가 낡았으면 멈추고 보고한다

2026-08-14에 두 번 물렸다.

- 검증 프로필이 **4개월 묵어** 결제 게이트웨이가 TossPayments라고 적혀 있었다. 실제로는 PortOne V2다. 그대로 돌았으면 **존재하지 않는 시스템을 검증**했을 것이다
- "MCP는 prod가 아니다"라는 경고가 **3개월 묵어** 있었고, 그 사이 연결이 바뀌었다. 그 낡은 경고 때문에 검증 에이전트가 **Critical 오탐**을 냈다

그래서: 작업 중 참조한 기준 문서가 **현재 코드와 어긋나면, 그 작업을 계속하기 전에 관리자에게 보고한다.** 낡은 기준으로 낸 결론은 틀린 결론이다.

**낡은 경고는 없는 것보다 나쁘다. 사람을 엉뚱한 곳으로 보낸다.**
