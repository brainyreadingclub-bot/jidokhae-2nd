> 작성 2026-08-21 · 대상 독자: **외부 평가자(다른 AI 또는 엔지니어)**
> 이 문서 하나로 판단할 수 있게 자족적으로 썼다. 정의·훅·스킬 원문은 부록에 있다.

## 0. 먼저 — 질문의 전제를 하나 정정합니다

이 진단을 요청한 질문지는 **CrewAI / LangGraph / 파이썬 오케스트레이터 + Playwright 캡처 파이프라인**을 전제하고 있습니다.

**우리 시스템에는 그런 코드가 한 줄도 없습니다.** 프레임워크도, 오케스트레이션 코드도, 에이전트가 호출하는 브라우저 도구 연동도 없습니다.

에이전트 팀 전체가 **마크다운 파일 + Claude Code CLI에 내장된 서브에이전트 기능 + Node 훅 2개**로 되어 있습니다. 실행 코드로 셀 수 있는 것은 **훅 스크립트 2개(합계 약 190행)**가 전부입니다.

| 있을 거라 예상됐을 것 | 실제 |
|---|---|
| CrewAI / LangGraph / AutoGen | **없음** |
| 파이썬·노드 오케스트레이터 | **없음.** 절차가 코드가 아니라 **산문 문서**로 적혀 있고 메인 모델이 그걸 읽고 따른다 |
| 에이전트 간 메시지 버스 | **없음.** 파일 시스템과 git이 유일한 공유 상태다 |
| 벡터 DB / RAG | **없음.** 컨텍스트는 매번 파일을 읽어서 만든다 |
| Playwright 연동 | 저장소에 Playwright가 있으나 **에이전트에 연결돼 있지 않다** (§4) |
| 상태 머신 / 재시도 / 체크포인트 | **없음** |

**그래서 이 진단의 핵심 질문은 "프레임워크를 잘 썼는가"가 아니라 "프레임워크 없이 규율만으로 어디까지 되는가"입니다.**

이게 게으름의 결과인지 합리적 선택인지가 우리가 외부 시선으로 확인받고 싶은 지점입니다. 판단 재료를 아래에 전부 폅니다. §6에 우리가 스스로 아는 약점을 먼저 적어뒀습니다.

### 프로젝트 배경 (판단에 필요한 최소한)

- **제품**: 한국 경주·포항 지역 독서모임의 웹 서비스. Next.js 16 + Supabase + Vercel. 실제 회원이 실제 돈을 결제한다
- **개발 인원**: **비전공자 1명(운영자)** + AI. 전담 QA·PM·디자이너가 없다
- **그래서 이 에이전트 팀의 목적**: 사람 한 명에게 없는 **역할(관점)을 만들어내는 것**이지, 처리량을 늘리는 것이 아니다

## 1. 기술 스택 및 아키텍처

### 1-1. 런타임

| 층 | 실체 |
|---|---|
| **실행 환경** | Claude Code CLI (Windows 11, PowerShell/Git Bash) |
| **모델** | Claude Opus 5 (1M context). 서브에이전트는 `model: inherit` — 전원 같은 모델 |
| **에이전트 생성** | Claude Code 내장 `Agent` 도구. 우리가 만든 코드가 아니다 |
| **에이전트 정의** | `.claude/agents/*.md` — YAML frontmatter + 마크다운 본문 |
| **절차(오케스트레이션)** | `.claude/skills/부서/SKILL.md` — **사람이 읽는 산문 절차서.** 메인 모델이 읽고 따른다 |
| **강제 장치** | Node 훅 2개 (`.claude/hooks/*.mjs`), `.claude/settings.json`에 등록 |
| **공유 상태** | 파일 시스템 + git. DB·큐·버스 없음 |

## 2. 에이전트 역할 및 프롬프트

### 2-1. 부서 8개의 목적 — "무엇이 성공인가"로 정의했다

| 부서 | 목적 | 하지 않는 일 | 정의 파일 |
|---|---|---|:--:|
| **품질** | **"배포해도 되는가"를 판정한다.** 결함 목록을 만드는 게 아니다 | 코드 수정 · 이미 인지된 문제 재보고 · **의도된 설계 지적** | ✗ |
| **제품기획** | 다음에 무엇을 할지 정하고 **`DECISIONS.md`에 남긴다** | 시안 제작 · 구현 · **이미 정해진 것 재논의** | ✅ |
| **디자인** | 회원이 볼 화면을 **합의 가능한 형태로 보여준다**(시안) | 구현 · 새 토큰 생성 · 시안 없는 문구 확정 | ✅ |
| **개발·운영** | 합의된 것을 **동작하는 상태로 만들고 안전하게 내보낸다** | 시안 없는 회원 화면 구현 · 품질 통과 전 배포 | ✅ |
| **데이터** | 다음 판단의 **근거가 될 숫자**를 댄다 + **우리가 모르는 것**을 밝힌다 | **계측 코드 직접 수정** · 숫자로 제품 결정 | ✗ |
| **성장** | 회원이 **오고 남을 이유**를 만든다 | 제품 기능 결정 · 과장·압박 문구 | ✗ |
| **고객VOC** | 회원의 말을 **제품 결정으로 옮긴다** | 회원에게 직접 응답 · **단발 의견을 결정으로 승격** | ✗ |
| **문서총괄** | 같은 사안에 **두 문서가 다른 말을 하지 않게** 한다 | 무엇이 맞는지 내용 판단 · 파일명 일괄 변경 | ✅ |

**설계 의도 두 가지를 짚어둡니다.**

1. **"범위 밖"을 목적과 같은 무게로 적었다.** 우리 경험상 에이전트의 실패는 "못 해서"보다 **"시키지 않은 걸 해서"** 난다. 특히 품질의 `의도된 설계 지적 금지`는 실제 사고에서 나왔다 — 전문가 패널이 맥락 없이 "버그"라고 지적한 것이 사실은 운영 사정 때문에 일부러 그렇게 둔 설계였고, 그 뒤로 보고서 전체가 신뢰를 잃었다.

2. **데이터에서 "계측 코드 수정" 권한을 뺐다.** 심는 사람과 재는 사람을 분리한 것이다. 배경 — 물어보기 응답률이 100%를 넘는 사고가 있었고 원인이 분자·분모 불일치였다. 그건 심는 사람이 같아서가 아니라 **게이트가 없어서** 났다. 그래서 권한을 옮기지 않고 게이트를 세웠다.

### 2-2. 정의 다섯 칸 — 부서마다 새로 쓰는 것은 두 칸뿐

| # | 칸 | 어디에 |
|---|---|---|
| 1 | **목적** — 무엇이 성공인가 | 부서별 (새로 씀) |
| 2 | **시작 전 필독** — 기억이 없으니 먼저 읽는다 | 공통 문서를 가리킴 |
| 3 | **기본 동작** — 지시 없을 때 하는 일 | 공통 표를 가리킴 |
| 4 | **산출물** — 형식·위치·자가 점검 | 공통 문서를 가리킴 |
| 5 | **범위 밖** — 하지 않는 일 | 부서별 (새로 씀) |

> **"매일 할 일"이 아니라 "지시 없을 때 하는 기본 동작"으로 정의했다.** 매일로 정하면 할 일이 없는데도 무언가 지어낸다.

### 2-3. 시스템 프롬프트 원문

**부록 A~D에 4개 전문**이 있습니다. 실제 실행 시 서브에이전트가 받는 것은 다음 합입니다.

```
[관리자가 쓴 소환 프롬프트  — 이번 일·산출물 경로·금지사항·보고 대상]
  ↓ 그 안에 "가장 먼저 .claude/agents/<부서>.md 를 읽어라" 지시
[정의 파일 60~74행]          — 목적·필독·기본동작·산출물·범위 밖
[공통규약 179행]             — 의도 확인·소통·소유권·로그 양식·금지 14종
[부서정의 98행]              — 자기 목적과 범위 밖 재확인
[DECISIONS.md]              — 이미 정해진 것 (원장)
[jidokhae-profile.md 132행]  — 기술 스택 + 의도된 설계 + 알려진 미해결
```

**즉 정의 파일은 프롬프트의 일부일 뿐이고, 나머지는 에이전트가 스스로 읽어서 채웁니다.** 소환 시 주입하지 않고 읽게 하는 이유는 규칙을 두 곳에 두지 않기 위해서입니다.

### 2-4. 공통규약의 핵심 3개 (전문은 부록 E)

**① 의도 확인 규칙** — 가장 자주 어기는 규칙으로 명시

| 상황 | 행동 |
|---|---|
| 의도를 못 찾음 | **"의도 불명"**으로 표시. "문제"로 단정하지 않는다 |
| 의도가 있고 지금도 유효 | 지적하지 않는다 |
| 의도는 있으나 **당시 전제가 지금과 다름** | ✅ 말한다. 단 "틀렸다"가 아니라 *"○○ 때문에 이렇게 정했는데 그 전제가 △△로 바뀌었다"* |

**② 파일 소유권** — 부서마다 쓸 수 있는 경로가 고정돼 있다. 겹치면 조용히 덮어쓰기 때문. 코드(`jidokhae-web/**`)를 고칠 수 있는 부서는 **개발·운영 하나뿐**이다.

**③ 자가 점검 5문항** — 관리자에게 올리기 전 스스로 채점, **5개 중 4개 미달이면 올리지 않는다**: 근거(파일:라인) / 의도 확인 / 범위 / 불확실성 표시 / 재현 가능성.

## 3. 데이터 파이프라인

### 3-1. 한 줄 요약

**메시지로 데이터를 옮기지 않는다. 파일에 쓰고 경로만 알린다.**

공통규약 §2: *"산출물은 파일로, 메시지는 포인터로. 내용을 메시지에 담으면 컨텍스트만 먹고 기록도 안 남는다."*

### 3-2. 실제 흐름 (오늘 실행 기준)

```
① 관리자가 컨텍스트를 조립한다 (코드가 아니라 관리자가 직접 씀)
   · 이번 일 / 산출물 경로 / 금지사항 / 동시 작업 중인 다른 부서의 파일 목록
   · ⚠️ 서브에이전트는 대화 히스토리를 상속하지 않는다 → 필요한 사실을 프롬프트에 다 넣어야 함
        ↓
② Agent 도구로 병렬 fan-out (오늘 최대 4명 동시)
        ↓
③ 각 에이전트가 스스로 컨텍스트를 만든다
   · 정의 파일 + 공통규약 + 부서정의 + DECISIONS.md + 프로필 을 Read
   · 그 위에 Glob/Grep/Bash(git, gh)로 저장소를 직접 조사
   · 일부는 Supabase MCP로 프로덕션 DB를 읽기 전용 조회
        ↓
④ 산출물을 파일에 Write
   · 부서별 고정 경로 (공통규약 §3 소유권 표)
        ↓
⑤ 로그를 docs/agent-team/logs/<부서>.md 에 append (최신이 맨 위)
   · 양식 5항목: 한 일 / 왜 / 안 한 것과 이유 / 주고받은 메시지 / 다음
        ↓
⑥ SubagentStop 훅이 로그 mtime을 검사 → 120분 내 갱신 없으면 exit 2로 되돌려보냄
        ↓
⑦ 관리자에게 최종 텍스트로 요약 보고 (경로 + 결론)
        ↓
⑧ 관리자가 파일을 열고 주장을 재현 → 로그의 `관리자 판정` 칸에 기록
   · "연 파일" 경로가 비면 그 판정은 무효 (규칙)
```

### 3-3. 토폴로지 — 별형(star). 부서 간 직접 통신은 설계돼 있으나 **한 번도 안 썼다**

공통규약은 직접 소통 쌍 4개를 허용한다: 제품기획↔디자인 · 개발운영↔품질 · 데이터↔제품기획 · 고객VOC↔제품기획. 그 외는 관리자를 거친다.

**오늘 6회 실행에서 부서 간 직접 메시지는 0건이었다.** 제품기획이 개발·운영에 넘길 것이 생겼을 때도 규약대로 관리자를 거쳤다(그 쌍이 허용 목록에 없어서). 규칙은 지켜졌지만, **직접 통신 기능이 실제로 쓰일 일이 있는지는 아직 증명되지 않았다.**

### 3-4. 상태 지속성 — git이 전부다

| 무엇 | 어디에 | 세션 끝나면 |
|---|---|---|
| 산출물 | 저장소 파일 | **남는다** |
| 작업 로그 | `docs/agent-team/logs/` | **남는다** |
| 결정 | `검토문서/DECISIONS.md` | **남는다** (+ 다음 세션 시작 시 훅이 자동 주입) |
| 에이전트 대화·메일함 | 메모리 | **사라진다** |
| 서브에이전트 자체 | — | **사라진다** |

공통규약이 이걸 한 문장으로 적어뒀다: **"파일에 없는 것은 존재하지 않은 것이다."** 로그 강제 훅은 이 문장을 장치로 바꾼 것이다.

### 3-5. 스크린샷·바이너리는 파이프라인에 없다

질문지가 "스크린샷 등"의 전달을 물었는데, **에이전트 간에 이미지가 오간 적이 없다.** 시안 검토는 사람이 화면을 보는 방식으로 하고, 에이전트는 HTML 파일 경로만 주고받는다. §4 참조.

## 4. 도구(Tools) 세팅

### 4-1. 부서별 도구 — frontmatter 한 줄이 전부다

```yaml
---
name: engineering
description: "개발·운영. 합의된 것을 동작하는 상태로 만들고 안전하게 내보낸다. ..."
tools: Read, Glob, Grep, Write, Edit, Bash
model: inherit
---
```

| 부서 | tools | 왜 그렇게 |
|---|---|---|
| 문서총괄 | `Read, Glob, Grep, Write, Bash` | **`Edit` 없음** — 어긋남만 보고하고 고치지 않는다. 도구 단위로 막았다 |
| 제품기획 | `Read, Glob, Grep, Write, Edit, Bash` | 문서를 고쳐야 한다 |
| 디자인 | `Read, Glob, Grep, Write, Edit, Bash` | 시안·기준 문서를 쓴다 |
| 개발·운영 | `Read, Glob, Grep, Write, Edit, Bash` | **코드를 고칠 수 있는 유일한 부서** |

> **권한 설계에서 실제로 작동한 것 하나** — 문서총괄에게서 `Edit`를 뺀 것. 검증하는 자가 고치면 "고쳤다고 말하고 안 고친" 일이 생기고, 무엇보다 **문서총괄이 오늘 감사한 문서 중 여럿이 다른 부서 소관**이었다. 도구가 없으니 규칙을 어길 수단 자체가 없었다.

### 4-2. Playwright — **있지만 에이전트에 연결돼 있지 않다**

이 항목이 질문지와 실제가 가장 크게 갈리는 곳이라 정확히 적습니다.

| 존재하는 것 | 상태 |
|---|---|
| `jidokhae-web/package.json` → `playwright ^1.58.2` | devDependency. `npm run screenshot`용 |
| `.claude/skills/screenshot/scripts/capture.mjs` | 사이트 전 페이지 풀페이지 캡처 스크립트 |
| Playwright MCP 서버 (`mcp__playwright__*` 25개 도구) | **세션에 연결돼 있음** |

**그런데 부서 정의 4개 어디에도 Playwright·MCP 도구가 없습니다.** `tools:` 목록에 없으므로 부서 에이전트는 브라우저를 열 수 없습니다.

**의도된 것이 절반, 미완성이 절반입니다.**

- 의도된 쪽 — 이 서비스는 **카카오 OAuth 로그인 뒤에 회원 화면이 있어** 로컬에서 열리지 않는다(콜백이 프로덕션 도메인으로 간다). 캡처를 붙여도 로그인 화면만 찍힌다
- 미완성인 쪽 — 관리자규칙 §4는 *"화면 변경이면 **렌더해서 본다**(Playwright)"*라고 적어뒀는데, **정작 그 도구를 아무에게도 주지 않았다.** 규칙과 도구 세팅이 어긋나 있다. 오늘 디자인 부서는 화면을 렌더하지 않고 CSS 토큰을 `grep`으로 세는 것으로 검증했다

**결과적으로 현재 이 시스템은 "코드와 문서를 읽고 쓰는 에이전트 팀"이고, 시각적 검증 능력이 없습니다.** 이게 이 진단에서 가장 명확한 구멍입니다.

### 4-3. 실제로 많이 쓰인 도구 (오늘 6회 실행 관찰)

| 도구 | 용도 | 비고 |
|---|---|---|
| `Bash` → `git grep` / `git log` / `git show` | 주장 검증의 주력 | 문서를 믿지 않고 코드를 센다 |
| `Bash` → **`git merge-tree`** | **머지 후 결과를 미리 접어보기** | 아래 참조 |
| `Bash` → `gh pr view/diff` | 열린 PR의 실제 내용 확인 | `MERGEABLE` 값을 근거로 쓰지 않기 위해 |
| Supabase MCP `execute_sql` | 프로덕션 DB **읽기 전용** 조회 | 문서 대신 실제 상태 확인 |
| `Read`/`Glob`/`Grep` | 기본 | |

> **`git merge-tree` 사용이 이 팀에서 나온 가장 좋은 패턴입니다.** 개발·운영이 두 번 다 썼습니다. GitHub의 `MERGEABLE`은 각 PR을 base와 1:1로만 보기 때문에 "PR 3건이 서로 충돌하지 않는다"를 증명하지 못합니다. 그래서 브랜치나 ref를 만들지 않고 **세 PR을 순서대로 접은 가상 트리**를 만들어, 그 트리 안에서 변수 누락과 코드 패턴 잔존까지 검사했습니다. *결과가 나올 미래 시점의 코드를 지금 검사한 것*입니다.

### 4-4. 강제 장치 — 훅 2개 (원문 부록 F)

**① `inject-decisions.mjs` (SessionStart, 48행)**
`검토문서/DECISIONS.md` 전문을 세션 시작 컨텍스트에 밀어 넣는다. 배경 — 결정은 원래도 기록되고 있었는데 **작업할 때 아무도 다시 안 읽는 것**이 문제였다. 실제로 "호칭을 닉네임으로" 결정이 문서에 묻혀 있다가 며칠 뒤 "이제 정해야 할 일"로 되살아난 사고가 있었다. *찾아 읽으라는 규칙 대신 눈앞에 올려두는 방식으로 바꾼 것.* 실패 시 조용히 통과(exit 0) — 검증 장치가 세션 시작을 막으면 안 되므로.

**② `teammate-log-guard.mjs` (TeammateIdle + SubagentStop, 119행)**
로그를 안 쓴 부서를 **exit 2로 되돌려보낸다.**

```js
const DEPARTMENTS = {
  librarian: '문서총괄',   product: '제품기획',
  design: '디자인',        engineering: '개발운영',
  quality: '품질',         data: '데이터',
  growth: '성장',          'member-voice': '고객VOC',
}
// agent_type 으로 부서를 식별 → 로그 파일 mtime 검사 → 120분 초과면 차단
```

무한 루프 방지 장치가 들어 있다 — **`agent_id`당 한 번만 막는다.** 로그를 쓸 수 없는 상황(권한·경로 오류)이면 영원히 되돌려보내지기 때문. *"사람이 못 고치게 만드는 안전장치는 안전장치가 아니다"*라고 주석에 적혀 있다.

> 🔴 **이 훅은 오늘 단 한 번도 발동하지 않았습니다.** 이유는 §5-2에 있습니다. **강제 층이 설계돼 있고, 시험도 통과했고, 실전에서는 작동한 적이 없습니다.**

### 5-2. 🔴 미해결 에러 ① — 에이전트 정의가 등록되지 않는다 (강제 층 무력화)

**증상**

```
Agent type 'engineering' not found. Available agents: brand-voice:content-generation,
..., general-purpose, Plan, statusline-setup, superpowers:code-reviewer
```

`.claude/agents/` 에 4개 파일이 정상 frontmatter로 존재하는데 **하나도 목록에 안 뜹니다.** `librarian.md`는 **전날 만들어 하루가 지났고 `/clear`도 거쳤는데** 여전히 안 뜹니다.

**진단** — `/clear`는 컨텍스트만 비우고 **CLI 프로세스를 다시 띄우지 않습니다.** 정의는 프로세스 기동 시 한 번만 스캔되는 것으로 보입니다. (전날 로그에 *"다음 세션부터 작동한다"*고 적어뒀는데 **오진이었고 오늘 정정했습니다.**)

**연쇄 피해가 이 에러의 본질입니다.**

```
정의 미등록 → subagent_type 사용 불가 → general-purpose 로 우회 소환
           → 훅이 받는 agent_type = 'general-purpose'
           → DEPARTMENTS 매핑에 없음 → exit 0 (간섭 안 함)
           → 로그 가드가 부서를 영원히 식별하지 못함
```

**즉 이 시스템의 유일한 강제 장치가 우회 경로에서는 구조적으로 작동하지 않습니다.** 오늘 6개 부서가 전부 로그를 썼지만 그건 프롬프트에 적힌 규칙을 지킨 것이지 장치가 잡은 것이 아닙니다. **규칙과 장치를 구분하려고 만든 훅인데, 정작 규칙으로만 지켜졌습니다.**

**우회책(현재 적용 중)** — `general-purpose`로 부르고 프롬프트 첫 줄에 넣습니다:
> *"너는 **개발·운영** 부서다. 네 정의는 `.claude/agents/engineering.md`에 있다 — **가장 먼저 이 파일을 읽어라.** (정의가 세션에 등록되지 않아 general-purpose로 소환됐다. 너는 general-purpose가 아니라 개발·운영이다.)"*

동작은 합니다. 하지만 **훅은 여전히 죽어 있고**, 로그 확인은 관리자가 매번 수동으로 합니다.

**미해결 이유** — CLI 완전 재시작이 필요한데, 재시작하면 현재 세션 컨텍스트가 사라집니다. 작업이 끝나는 시점에 하기로 미뤄둔 상태입니다.

### 5-3. 🟡 미해결 에러 ② — `Agent` 도구의 `name`이 ASCII만 받는다

```
InputValidationError: name must start with a letter or digit and contain only
letters, digits, underscores, or hyphens (max 64 chars)
pattern: /^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$/
```

한글 부서명(`개발운영`, `문서총괄`)을 `name`으로 주면 4개 호출이 **전부 거부**됩니다. 부서 체계 전체가 한국어인데 호출 이름만 영문이어야 해서, **문서상 이름(`개발·운영`)과 호출용 이름(`engineering`)이 갈립니다.** 훅의 `DEPARTMENTS` 매핑이 이 간극을 메우고 있지만, 이름이 두 벌인 것 자체가 잠재적 어긋남입니다.

### 5-4. 🟡 해결됨 — 워크트리에서 Turbopack 빌드 FATAL

```
Symlink node_modules is invalid, it points out of the filesystem root
```

git worktree에서 `node_modules`를 정션(`mklink /J`)으로 공유하니 Turbopack 빌드가 죽었습니다. **`lint`·`tsc`·`test`는 전부 통과하고 `build`만 깨져서** 원인이 안 보였습니다. `robocopy`로 실복사해 해결. (`node_modules`가 617MB라 워크트리 3개를 안 만들고 하나에서 브랜치를 순차 체크아웃하는 방식으로 우회.)

### 5-5. 실행 품질 관찰 — 숫자보다 이쪽이 중요합니다

**① 서로 모르는 부서들이 같은 구멍을 독립적으로 짚었습니다.**

| 발견 | 짚은 부서 |
|---|---|
| 배포 절차서에 필수 환경변수 하나가 빠짐 | 개발·운영 · 문서총괄 |
| 14일 전 결정이 코드에 없고, **배포 예정 PR들이 그걸 되돌리는 방향으로 코드를 늘림** | 디자인(문서) · 제품기획(반영 시점) · 문서총괄(역행 사실) |

한 부서가 냈으면 "그럴듯한 지적"이었을 것이 세 부서가 각자 다른 경로로 도착해 **행동 가능한 사실**이 됐습니다. 이게 부서를 나눈 실질적 이득으로 관찰된 유일한 항목입니다. 다만 **의도한 설계가 아니라 우연히 관측된 것**입니다 — 교차 검증을 강제하는 장치는 없습니다.

**② 에이전트가 자기 산출물을 제출 전에 실측으로 뒤집었습니다.** 디자인이 *"accent 색은 3단계만 쓴다"*고 써놓고 `grep`으로 세어 보니 8단계가 쓰이고 있어 문장을 교체했습니다. 자가 점검 §5-1(근거)이 작동한 사례입니다.

**③ 에이전트가 관리자(자신을 부른 쪽)의 전제를 정정했습니다.** 관리자가 소환문에 *"작업 트리가 곧 최신"*이라고 썼는데, 문서총괄이 보고서 §0에서 *"`main` 기준으로는 아니다"*라고 바로잡았습니다. 1차 소환 때도 19건 중 5건이 **관리자가 그날 만든 문서의 결함**이었습니다.

**④ 관리자가 두 번 틀렸고 둘 다 기록에 남겼습니다.**
- 부서 주장을 검증하려고 `grep "real_name || nickname"`을 돌려 0건이 나오자 부서를 의심했는데, 실제 코드는 `profile.real_name || profile.nickname`이라 **관리자의 패턴이 틀렸습니다.** 부서가 맞았습니다
- 부서 종료 후 **다른 부서 소관 파일 2개를 관리자가 직접 고쳤습니다.** 사용자가 그 자리에서 지적했고, 관리자규칙에 §7("갱신도 부서가 한다")을 신설한 뒤 **해당 부서를 다시 불러 인수시켰습니다**(위 표 6·7번)

### 5-6. 실제 로그 샘플 (`docs/agent-team/logs/개발운영.md`)

```markdown
## 2026-08-21 (2차) — 호칭 결정을 코드에 반영 (3개 브랜치 7곳, 커밋까지)

**한 일**
- 위치는 지시서 숫자를 믿지 않고 `git grep -n "real_name || " <브랜치>`로 브랜치마다 직접 셌다
- **머지 후 결과를 실제로 접어서 확인했다.** `git merge-tree`로 순차 머지 시뮬레이션
  → 충돌 0, 최종 트리에서 옛 패턴 잔존 0건, 새 패턴 7곳

**왜 그렇게 했는가**
- **`|| ''`는 취향이 아니라 필수다.** 타입이 `nickname: string` / `real_name: string | null`이라
  순서를 뒤집으면 식이 `string | null`이 되고 `Record<string, string>`에서 tsc가 깨진다
- 빈 값 가드는 "타입 좁히기까지만" 넣고 동작 가드는 넣지 않았다. 근거 넷:
  1. 승인된 템플릿 7종이 전부 `똑똑! #{회원명}님,`으로 연다 — 코드로는 `님,`을 뗄 수 없다
  2. 대체 호칭은 **문구 결정**이라 디자인·제품기획 소관이다
  3. "이름 없으면 발송 skip"은 아무도 요청하지 않은 새 실패 모드다
  4. 앱을 통해서는 발생 불가 (경로를 코드로 추적한 근거 4줄)
  - **남는 구멍(보고만 한다)** — DB를 직접 건드린 경우엔 발생한다. 막으려면 템플릿 재심사다

**안 한 것과 이유**
- push·PR 수정 안 함. 커밋까지만
- `VOICE.md`의 표시를 안 지웠다 — 디자인 소관이다. **관리자가 넘겨줘야 한다**

**관리자 판정** — 🟢 통과
- 연 파일: `git show <각 브랜치>` → 7곳 확인 / `git rev-list --left-right --count` → 셋 다 `0 1`
- **관리자 정정 — 넘겨받은 것 중 하나를 그대로 반영하지 않는다.** `✅ 적용`으로 바꾸라고
  넘겼는데 아직 아니다. 커밋만 됐고 머지 전이다. 여기서 `✅`로 적으면 이 파일이 존재하는
  이유인 바로 그 사고를 이 파일 안에서 저지르는 셈이다
```

## 6. 우리가 아는 약점 — 외부 시선으로 확인받고 싶은 것

평가자가 찾아낼 것을 먼저 적습니다. **이 목록에 없는 것을 짚어주시면 그게 가장 값어치 있습니다.**

### 6-1. 오케스트레이션이 코드가 아니라 산문이다 — 재현성이 없다

`/부서` 스킬은 6단계 절차서지만 **실행 주체가 모델**입니다. 같은 입력에 같은 출력이 나온다는 보장이 없고, 단계를 건너뛰어도 아무도 막지 않습니다. 상태 머신도, 재시도도, 체크포인트도 없습니다.

**우리 쪽 논리** — 작업 종류가 매번 다르고(문서 감사·코드 판정·시안·우선순위), 파이프라인으로 굳히면 굳힌 모양 밖의 일을 못 하게 됩니다. 사람이 1명이라 파이프라인 유지보수 비용도 부담입니다.

**물어보고 싶은 것** — 이 규모(1인 + AI)에서 코드형 오케스트레이션으로 옮기는 것이 이득입니까, 아니면 산문 절차 + 강제 훅 조합이 합리적입니까? 옮긴다면 **무엇부터** 옮겨야 합니까?

### 6-2. 강제 층이 실전에서 한 번도 작동하지 않았다

§5-2. 훅은 규칙을 장치로 바꾸려고 만든 유일한 부품인데, 우회 경로에서 구조적으로 무력합니다. **지금 이 시스템은 사실상 "프롬프트에 적힌 규칙을 모델이 잘 지켜주는 상태"**이고, 그건 원래 없애려던 상태입니다.

### 6-3. 평가 지표가 없다 — 반려 0건이 좋은 신호인지 알 수 없다

오늘 5건 전부 🟢입니다. 가능성은 셋인데 구분할 방법이 없습니다.

1. 정의가 잘 돼서 실제로 품질이 좋다
2. **관리자의 판정 기준이 무르다** (관리자와 부서가 같은 모델이라 같은 실수를 그럴듯하게 본다)
3. 애초에 쉬운 일만 시켰다

**가장 걱정하는 것은 2번입니다.** 관리자가 재현 검증을 하긴 하지만, **재현할 항목을 고르는 것도 관리자**입니다. 벤치마크는 2026-08-14에 **한 번, 에이전트 1명**만 측정한 것이 전부입니다(n=1).

### 6-4. 관리자가 병목이자 단일 실패점이다

모든 판정·기록·교차 전달이 관리자 한 명을 지납니다. 오늘 관리자는 **검증 패턴을 한 번 틀렸고, 소유권 규칙을 한 번 어겼습니다**(§5-5 ④). 둘 다 사용자가 아니라 **부서와 사용자가** 잡았습니다.

관리자에게는 **로그 강제 훅이 걸리지 않습니다**(설계상 팀원·서브에이전트만 대상). 규칙을 가장 많이 흘리는 자리에 장치가 없습니다.

### 6-5. 컨텍스트 비용이 크고, 대부분이 중복이다

부서 하나가 15만~22만 출력 토큰을 씁니다. 매 소환마다 **같은 기반 문서 약 600행**(공통규약 179 + 부서정의 98 + 프로필 132 + DECISIONS)을 다시 읽습니다. 4명을 동시에 부르면 같은 문서를 4번 읽습니다.

캐시도, 요약 층도, 선택적 로딩도 없습니다. **의도적으로 안 했습니다** — 요약을 만들면 그 요약이 낡고, 이 프로젝트의 사고는 대부분 "낡은 사본"에서 났기 때문입니다. 그 판단이 맞는지 봐주십시오.

### 6-6. 시각적 검증 능력이 없다

§4-2. 규칙은 "렌더해서 보라"고 하는데 도구를 아무에게도 주지 않았습니다. OAuth 게이트라는 실제 제약이 있지만, 그것과 무관한 정적 시안 렌더조차 안 하고 있습니다.

### 6-7. 8부서 중 4개는 정의가 없다

품질·데이터·성장·고객VOC는 목적과 범위만 정해져 있고 정의 파일이 없습니다. **의도적입니다** — *"실제로 쓰면서 만든다"*가 방침이고, 안 쓰는 부서를 미리 만들면 안 쓰이는 채로 낡습니다. 다만 **품질**은 사정이 다릅니다: 안내판이 "배포 전 검증은 품질"이라고 지정해뒀는데 정의가 없어서, 오늘 배포 판정을 **개발·운영이 자기 코드에 대해** 내렸습니다. **찾는 사람과 고치는 사람을 분리한다는 원칙이 이 대목에서 깨졌습니다.**

### 6-8. 검증 스쿼드 정의가 버전 관리 밖에 있다

§1-4. 8개 정의가 홈 디렉토리에 있어 git에 없습니다.
