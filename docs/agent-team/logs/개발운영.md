**왜 그렇게 했는가**
- id는 UUID — 기존 마이그레이션 대부분(`payment_failures` 포함)이 `UUID DEFAULT gen_random_uuid()`
- 이벤트 CHECK는 **형식만**. 목록까지 넣으면 이벤트 추가 때마다 SQL 재실행 + 코드가 먼저 나가면 기록 전부 거절
- 홈 실패 처리 방식은 `fix/screen-audit-five`(빌드1, 미병합)의 모임·이야기 탭 방식을 그대로 — 조회 에러면 throw해서 그룹 공통 오류 화면. 인원 수 조회도 throw로 둔 이유: 모임 탭이 같은 조회를 throw하고, 틀리면 마감 모임이 신청 가능한 것처럼 뜬다. 알림(`listAppNotifications`)은 공용 lib이 에러를 안 돌려줘 손대지 않음(답글 카드 하나 빠지는 정도)
- 0원 신청은 `registerEntry`가 금액 0이면 'transfer' → 같은 `/api/registrations/transfer` 라우트. RPC 결과 'confirmed'(SQL 후)·'pending_transfer'(SQL 전)·'waitlisted' 모두 기록됨
