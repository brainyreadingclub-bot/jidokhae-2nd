## 3. 실측 — 에이전트 #7 단독 실행

결함 4가 **현재 브랜치에 그대로 살아 있어서** 따로 꾸밀 필요가 없었다(#53이 draft라 미머지).

- 요구사항 문서: 미제공
- 보고서: `verification-squad/reports/2026-08-14-benchmark/07-consistency-report.md`

### 결과: ✅ 적중, 그것도 더 깊게

사람이 미리 찾아둔 건 3곳이었는데 **4곳을 찾았다.**

| 위치 | 정의 |
|---|---|
| `lib/notification.ts:14-19` | 5종 (미export 로컬 타입) |
| `types/notification.ts:3` | **2종** — 2단계 낡음 |
| `lib/notification-log.ts:20-28` | 7종 (`Record<string,string>`) |
| `supabase/migration.sql:505-509` | CHECK 5종 |

추가로 **`types/notification.ts`가 어디서도 import되지 않는 사문(死文)**이라는 것까지 밝혔다. 그래서 union이 2단계나 밀린 것이다. 해결책도 "types를 단일 소스로 승격"으로, PR #53의 방향과 일치한다.

**등급은 Warning.** 자기 기준("런타임 오류를 유발하는 불일치"=Critical)에 비추면 사문이라 지금 깨지지는 않으므로 **정확한 판단이다.**

### ✅ 오탐 방지 장치가 실제로 작동했다

이번에 프로필에 넣은 "의도된 설계" 절을 읽고, 레거시 토스 코드에 대해 이렇게 썼다:

> *"토스 코드 잔존은 의도된 롤백 안전망(프로필)이므로 삭제 대상이 아니나, 알림 디스패치 로직이 두 벌이라 한쪽만 고쳐지는 사고가 난다"*

**삭제하라고 하지 않고, 실재하는 위험만 짚었다.** 이것이 전문가 패널이 못 했던 바로 그 동작이다. 계획서 §5-1 의도 확인 규칙이 프로필 수준에서 구현 가능함을 확인했다.

### ⚠️ 오탐 1건 — 원인은 에이전트가 아니었다

Critical #2로 *"`book_ask` 마이그레이션이 dead project에 적용됐을 수 있다 → 배포 즉시 전건 실패"*를 올렸다.

**검증 결과 오탐이다.** MCP는 현재 `ycqqzzvyixvtdorjxkrn`(= prod) **하나만** 보고, `book_asks` 테이블이 prod에 5행과 함께 존재한다.

그러나 **에이전트를 탓할 수 없다.** 프로젝트 메모리가 "MCP는 봇용 dead project"라고 적혀 있었고, 작업 기록은 "MCP로 prod 실행 완료"라고 적혀 있었다. **문서 두 개가 서로 다른 말을 하고 있었고, 에이전트는 그 모순을 정확히 짚은 것이다.**

→ ✅ 낡은 메모리 정정 완료. 이건 문서총괄 부서(계획 2단계)가 상시로 할 일의 실제 사례다.
