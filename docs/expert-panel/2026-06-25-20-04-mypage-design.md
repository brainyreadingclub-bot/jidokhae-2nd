## 질문
독서모임 웹서비스 JIDOKHAE의 "마이페이지"를 현재 상태 기준으로 새로 기획한다. 현재 /my는 "내 신청"(신청 내역)만 있고 프로필 보기/수정 화면이 없다. 발단은 "회원이 닉네임 오타를 1회 수정하게 해달라"는 요청. 이참에 마이페이지 전반(요소·유저흐름·와이어프레임·각 요소의 목적/가치)을 실무 워크플로우대로 기획한다.

## 라운드 1: 독립 의견

### 🧭 정도현 (PM)
- 핵심: 마이페이지 v1 = "프로필 카드 + 내 신청 + 로그아웃/약관" 3블록. 닉네임 수정은 프로필 카드 안 수정 1건으로 흡수. 기능 전시장 금지.
- 근거: 진입 동기는 (1) 신청 모임 확인(이미 충족·최강 job) (2) 내 정보 확인·수정 (3) 계정 위생뿐. 저빈도 화면에 통계·뱃지 붙이면 Out-of-scope 위반. 프로필 데이터는 이미 다 수집됨 → "보여주기"는 공짜, "수정"만 정책 결정.
- 리스크: 닉네임 UNIQUE + 명단·입금자명 노출 → 자유 수정 시 충돌·식별 혼란. "1회 제한"은 기능이 아니라 정합성 가드.
- 추천: 닉네임 1회 수정 + region/email 자유 수정, real_name/phone은 운영 식별용 잠금. 통계·탈퇴는 v2.

### 🎨 한유진 (UX/IA)
- 핵심: 단일 /my 라우트에서 프로필 섹션(상단) + 내 신청(하단). 보기→인라인 편집→저장. 닉네임은 locked 표시, 실명/지역/이메일은 수정 가능. 새 라우트 만들지 말 것.
- 근거: 현재 /my는 MyRegistrationContent만, 헤더 닉네임엔 편집 진입점 없음, BottomNav 2탭. ProfileSetup은 풀스크린 온보딩 모달이라 인라인 편집과 구분돼야 함. less-ornament-first → 무장식 섹션.
- 리스크: 닉네임 1회 제한이 현재 라우트에 없음. 먼저 검증 로직/컬럼 필요. BottomNav 탭 추가 여부 결정 필요(현재는 불필요).
- 추천: /my = [프로필 요약 read-only] → [수정하기] 토글로 인라인 폼 → [내 신청]. 새 탭·새 페이지 없음.

### ⚙️ 김상우 (엔지니어)
- 핵심: `profiles.nickname_changed_at` 컬럼 추가 + 신규 `/api/profile/update`(setup 재사용 불가) + 신규 ProfileEditor 컴포넌트. 현재 UNIQUE 부분인덱스는 중복만 막고 1회 제한 로직 없음.
- 근거: migration.sql:323-324 부분 UNIQUE 인덱스(빈문자열 제외)는 중복만 방지. setup route는 중복 체크만, 1회 제한 추적 컬럼 부재. setup은 온보딩(전 필드 동시 강제)용이라 부분 수정에 부적합. getProfile은 9컬럼 캐시 — nickname_changed_at 추가 선택 필요.
- 리스크: 기존 회원 마이그레이션 처리(기회 새로 줄지/소비할지), race condition, RLS bypass(서비스키) → 본인 프로필만 수정 검증 필수.
- 추천: 마이그레이션(nickname_changed_at) + 신규 update 라우트(부분 수정, 표준 포맷) + ProfileEditor(닉네임 disabled 조건부). attended 통계는 partial 인덱스 추가 시 저렴.

### ✂️ 서민기 (미니멀리스트, 반대)
- 핵심: 확장은 부당. 닉네임 수정 진입점 1개만 열면 끝. "마이페이지 전체"는 상상된 니즈.
- 근거: 원 문제(오타) 백엔드는 이미 다 있음 — setup route가 중복 체크·검증·UPDATE·prefill 처리. 필요한 건 회원이 다시 띄울 진입점 1개. 참여 이력은 /my에 이미, 정책은 /policy/*에 이미, 로그아웃은 헤더+BottomNav 2곳에 이미. "이참에 모으자"는 순수 중복 생산. 250명 모임에서 프로필 재방문 데이터 없음.
- 리스크: 없던 페이지 만들면 region/phone/email 전체 수정 노출 → UNIQUE 충돌·알림톡 깨짐·email 변경 엣지케이스·유지보수 부채를 1회 오타 때문에 떠안음.
- 추천(바닥선): 기존 ProfileSetup을 "닉네임만 수정" 모드로 재사용, /my 상단에 "닉네임 수정" 링크 1개만. 나머지 전부 버림.

### 🙋 박서연 (운영·회원)
- 핵심: 진짜 핵심은 닉네임이 아니라 "전화번호 자가 수정"(알림톡 안 옴 문제) + "내 참여 이력". 닉네임은 무제한 아닌 명확한 제약 하에.
- 근거: 현장 문의 1순위는 "내 신청 모임 언제", "알림톡 안 와요"(=전화 오타, 지금은 운영진 수동 수정). 전화 자가 수정이 수동 처리를 가장 확실히 줄임. 닉네임은 입금자명("5/17 초록고래")·명단에 이미 노출 → 모임 거친 뒤 변경 시 입금 대조·식별 혼란. 지역은 약한 정보라 자가 수정 부담 거의 없음.
- 리스크: "1회 수정" 단순 허용 시 좋은 닉네임 선점 경쟁 + "또 풀어달라" 예외 문의로 운영진이 횟수 카운터 수동 관리하는 역설.
- 추천: 전화·지역 자가 수정 무제한, 닉네임은 "진행/예정 모임 신청 이력 없을 때만 1회" 조건 + 변경 시점·이전 닉네임 운영자 로그.

## 라운드 2: 토론

### 상호 반박 & 보강

#### 🧭 정도현 → 다른 의견
- 박서연(전화 자가 수정)에: **수용·정정한다.** 내가 phone을 "잠금"하라 한 건 운영 식별 가정이었는데, phone은 명단에 노출되지 않고 알림톡 발송에만 쓰인다. 오타 시 회원이 리마인드를 못 받고 운영진이 수동 수정 → phone 자가 수정은 운영 부담을 **줄인다.** phone은 editable로 전환.
- 서민기(확장 부당)에: 절반 동의. "통계·정책·로그아웃 모으기"는 내 v1에서도 뺐다. 다만 "프로필 보기/수정 섹션"까지 버리는 건 과하다 — 회원이 자기 정보를 볼 단일 지점이 0개인 건 제품 결함이다.

#### 🎨 한유진 → 다른 의견
- 김상우(신규 라우트·컴포넌트)에: 동의. ProfileSetup은 풀스크린 게이트라 인라인 편집과 섞으면 안 됨. 단 필드 검증·RegionPicker 로직은 추출 재사용해 중복 최소화.
- 서민기(링크 1개만)에: 반박. "닉네임 수정 링크"만 띄우면 진입점은 생기지만 회원이 자기 전화/지역이 맞는지 **확인할 화면이 여전히 0개**다. 보기 없는 수정은 IA상 더 나쁘다.

#### ⚙️ 김상우 → 다른 의견
- 박서연(닉네임 조건부)에: 부분 동의하나 비용 경고. "활성 신청 없을 때만"은 registrations 조인 쿼리 + 시점 판단이 필요해 1회 제한보다 복잡. nickname_changed_at 단일 컬럼이 가장 싸고 명확. 조건부는 v1.1 후보.
- 서민기(setup 재사용)에: 반박. setup은 전 필드 required + profile_completed_at 기록 로직이라 부분 수정에 부적합. 억지 재사용이 오히려 부채.

#### ✂️ 서민기 → 다른 의견
- 정도현/한유진(프로필 섹션 필요)에: 한 발 양보. "보기 0개가 결함"은 인정. 단 **여전히 새 페이지·새 탭·통계·정책 모으기는 반대.** 기존 /my에 섹션 하나 얹는 선에서 끝내라.
- 박서연(전화 수정 가치)에: 동의. 그건 "상상된 니즈"가 아니라 운영 비용 절감 근거가 있다. 닉네임보다 phone이 우선순위 높다는 데 동의.

#### 🙋 박서연 → 다른 의견
- 정도현(real_name 잠금)에: real_name은 명단·입금자명에 안 쓰이니 잠글 실익이 약하다. 다만 회원이 건드릴 일도 거의 없어 noise. 잠그든 열든 영향 작음.
- 김상우(조건부 복잡)에: 수용. 운영 현실상 "1회 + 운영자 로그"면 충분. 명단 혼란은 빈도 낮으니 v1은 단순 1회로, 로그만 남겨 사후 추적.

### 핵심 논쟁점
1. **확장 범위**: 미니멀리스트(닉네임 링크 1개) vs PM·UX·운영(프로필 보기/수정 섹션). → "보기 0개는 결함" 논거로 섹션 채택, 단 새 페이지·탭·통계·정책 모으기는 배제.
2. **phone 잠금 vs 수정**: PM 최초 "잠금" vs 운영 "수정 가치 최고". → phone은 알림톡 전용·명단 미노출이므로 **editable로 합의**(PM 정정).
3. **닉네임 자유도**: 운영의 "활성 신청 없을 때만" 조건 vs 엔지니어의 "단일 컬럼 1회". → v1은 **nickname_changed_at 1회 제한**으로 단순화, 운영자 로그 남김. 조건부는 v1.1.
4. **setup 재사용 vs 신규 라우트**: 미니멀(재사용) vs 엔지니어·UX(신규). → 부분 수정·온보딩 분리 위해 **신규 update 라우트 + ProfileEditor** 채택.

## 최종 합의
마이페이지는 "기능 허브"가 아니라 **기존 /my에 얹는 단정한 프로필 섹션**으로 만든다(새 페이지·새 BottomNav 탭·참여 통계·정책 링크 모으기·로그아웃 이동은 v1에서 전부 배제 — 이미 존재하거나 Out-of-scope). 구조는 /my 상단에 프로필 요약(read-only) → [수정하기] 토글로 인라인 편집 → 하단에 기존 내 신청. 편집 가능 필드는 **전화번호·지역·이메일(자유 수정)**, **닉네임(가입 후 1회 제한)**. phone 자가 수정이 "알림톡 안 옴 → 운영진 수동 처리"를 없애는 가장 큰 실질 가치이고, 닉네임 1회 수정은 원 요청을 충족하되 명단·입금자명 정합성을 지키는 가드다. real_name은 잠그든 열든 영향이 작아 디자이너 재량(기본: 운영 식별 위해 읽기전용 표시). 구현은 `profiles.nickname_changed_at` 컬럼 + 신규 `/api/profile/update`(부분 수정, 표준 포맷, 본인 검증) + 신규 ProfileEditor 컴포넌트(ProfileSetup의 필드/RegionPicker 로직 추출 재사용)로 한다.

## 액션 아이템
1. /my를 2섹션으로 확장: [프로필 요약+편집] + [기존 내 신청]. 새 라우트·새 탭 없음.
2. DB: `profiles.nickname_changed_at TIMESTAMPTZ` 추가 (마이그레이션 SQL은 코드 확정 후 안내). 기존 회원 처리 정책 결정 필요(아래 미합의).
3. 신규 `/api/profile/update` 라우트: 부분 수정, `{status,message,data}` 표준 포맷, 본인 프로필만, 닉네임은 nickname_changed_at 가드 + 기존 중복 체크 재사용.
4. ProfileEditor 컴포넌트: 보기→인라인 편집. phone/region/email editable, 닉네임은 변경 가능 시 1회 입력·이후 locked 표시. real_name 읽기전용(기본).
5. 운영자 추적: 닉네임 변경 시 이전 닉네임·시점 로그(최소한 nickname_changed_at). 명단 혼란 사후 대응용.
6. v1 명시적 제외: 참여 통계·뱃지, 정책 링크 모으기, 로그아웃 이동, 탈퇴 자동화. (요청 누적 시 v2)

## 미합의 사항
1. **real_name 잠금 vs 수정**: PM은 운영 식별 위해 잠금, 운영은 영향 작다며 무관. → 디자이너 재량(기본 읽기전용 제안).
2. **닉네임 "활성 신청 없을 때만" 조건**: 운영은 명단 혼란 방지로 선호, 엔지니어는 복잡도로 v1.1 권고. → v1은 단순 1회, 조건부는 후속.
3. **기존 회원 닉네임 1회 기회**: 전원에게 새 기회(nickname_changed_at=NULL) vs 가입 시점으로 소비. → 운영 정책 결정 필요.
